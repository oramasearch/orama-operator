# v0.7.1

**Released:** 2026-10-20 · **Branch:** `main` · **Previous:** [v0.7.0](v0.7.0.md) (2026-10-20).

v0.7.1 is **a patch for Cloud v1 team migrations and Lake's payments**. It adds the operator's half
of copying a team from an existing Orama Cloud v1 deployment into a Cloud v1 stack:
`OramaCloudV1Migration`, which runs the migration tool's steps as Jobs, and team migrations declared
on `OramaCloudV1Set`, so the copy is a committed resource instead of a tool run by hand. It also
carries `Lake.spec.payments` and a Stripe webhook endpoint's deletion that always finishes.

**What changes on every cluster when it rolls:** every Cloud v1 stack gets a `migration` database
role, its Secret, a fourth control DB schema that grants the role read and write on the rows of
`public`, and four sandbox policies. The role cannot sign in until a migration targets the stack.
No migration, `spec.migrations` or `spec.payments` is declared in `config/clusters/`, so nothing
else is used.

Everything in [v0.7.0](v0.7.0.md) is still here. This page lists what is new or changed.

Changes in this release:

- Deleting a `StripeWebhookEndpoint` always finishes: a 5-minute grace, at once on 401 or 403,
  then `EndpointLeftBehind`.
- `Lake.spec.payments`: each Lake its own Stripe webhook endpoint, catalog and provider, its keys
  given once all are Ready.
- `OramaCloudV1Migration`: one team copied into one stack by the migration tool's Jobs.
- `OramaCloudV1Set.spec.migrations`: team migrations declared on the set and applied into its
  members.

## 1. Cloud v1: team migrations

- **`OramaCloudV1Migration`** declares one team copied from a source Cloud v1 deployment into one
  stack. Each `(step, apply, attempt)` is one owned Job running `run-step` of the pinned
  `cloud-v1-migration` image, kept a week as the record; the tool's exit code sets the phase (0
  `Succeeded`, 3 `Blocked`, other `Failed`) and its `status --json` is `status.result`.
- **Guards before a Job:** the stack Ready with `ClusterRowReady` and every control DB schema
  current; no applied seed or catch-up while the dashboard crons or analytics import run; no
  catch-up or verify before an applied seed.
- **The source** is read through a SELECT-only database URL and its engine origins, never SSH.
  Egress to the source (TCP 443 and 5432) exists only while a migration targets the stack.
- **`removeOnDelete`** runs the tool's `remove-target` when the resource is deleted; the tool refuses
  once the team has been switched, and the resource then stays.
- **The `migration` role** on every stack: a CNPG managed role with no superuser, createdb,
  createrole, replication or bypassrls, at most 4 connections, read and write on the rows of
  `public` and use of its sequences, no DDL. Its `login` is on only while a migration targets the
  stack.
- **On a set:** `spec.migrations` entries (`name`, `member`, `secrets`, `spec`) become migrations in
  the member's namespace, with their Secrets copied there and deleted with them. A change the
  migration kind makes immutable, or a move to another member, is reported on the set and the
  applied migration is left alone. Removing an entry deletes its migration (and so runs
  `remove-target` with `removeOnDelete`). A member or set being deleted waits for its migrations.

## 2. Lake: `spec.payments`

Detail: [`docs/lake/payments.md`](../lake/payments.md).

- From one Secret per environment (`accountID`, `operatorKey`, `appKey`) and `mode` (`test` or
  `live`), the operator keeps a `PaymentProvider`, a `PaymentWebhookEndpoint` at
  `https://<host>/billing/stripe/webhook` (seven event types, Stripe API version `2024-06-20`) and
  Lake's `PaymentCatalog` (`lake_usage`, `lake_private_warehouse`, `lake_dedicated_cluster`, no
  prices). It gives the Lake `LAKE_STRIPE_SECRET_KEY` and `LAKE_STRIPE_WEBHOOK_SECRET` only once all
  of them are Ready and Lake's own key is checked. A key of the wrong mode is refused.
- **A Lake's deletion always finishes**, whatever Stripe answers: the endpoint's finalizer retries for
  five minutes (at once on 401 or 403), then records `EndpointLeftBehind` naming the Stripe endpoint
  for a person to delete in the Dashboard.

## What `v0.7.1` does **not** include

Everything under v0.7.0's [*does not include*](v0.7.0.md#what-v070-does-not-include), except
`Lake.spec.payments` and `OramaCloudV1Migration`, which are now in. Also not included: any migration
or `spec.payments` declared in `config/clusters/`; `spec.billing`; Cloud v1's dashboard payments;
egress to a migration source by host name; `0090_billing_contacts`.

## Known issues

- **Removing a set's migration entry removes the copied team** when it has `removeOnDelete`; the tool
  refuses after the switch.
- **Applying `spec.payments` drops a member's `spec.env` Stripe variables at once**, until
  `PaymentsReady`; Lake's side of it is not yet released.
- **A left-behind Stripe endpoint** after a failed deletion is deleted by a person in the Dashboard.
- **The manager can be OOMKilled once at start-up** on a management cluster with many resources,
  then starts and runs normally.
- Unchanged from v0.7.0: the live-endpoint cautions in `payments.md`; nothing had run against real
  Stripe or a real leaf's port-forward through the operator when it was cut; nothing upgrades a
  dedicated cluster after it is made.

Run on the release branch, macOS arm64, Go 1.26, with the Kubernetes 1.30.3 envtest binaries and a
local Postgres:

```

                                   834 test functions, 822 passed, 12 skipped, 0 failed (827 subtests passed)
```

Four opt-in groups ran against Postgres: the Lake schema tests, `TestCloudOrdersPgxStoreAgainstPostgres`,
and the control DB tests `TestControlDBSchemasAgainstPostgres` (all four schemas, the new
`migration-grants` included, applied twice) and `TestControlDBClusterRowAgainstPostgres`. The twelve
skipped are opt-in and were **not run**: ten `*PgxStoreAgainstPostgres` and
`TestConnectionRolesAgainstPostgres` need their own Postgres switches,
`TestEgressGatewayAgainstZettaTunnel` needs a zetta-tunnel binary, and
`TestLiveChartDownloadAndPrerequisiteCheck` needs `LEAF_LIVE=1` and a live cluster. The suite ran with
the version already at 0.7.1, so `TestReleaseVersionIsDocumented` passed against this page.

On upgrade, every Cloud v1 stack runs its new `controldb-migration-grants` schema Job.

The image built from the tag is published as `oramasearch/orama-operator:v0.7.1` (there is no
`latest`), and the chart as `0.7.1` in `oramasearch/orama-operator-chart`.

## Installing it

- **A management cluster** is installed from `helmfile.yaml` ([`docs/install.md`](../install.md)).
  Before the upgrade, `make check-crds`, then the CRDs widened, the upgrade, and the CRDs exactly
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)): this release adds one CRD and
  changes `OramaCloudV1Set`, `LakeSet` and `Lake`.
- **A managed cluster** is installed by its management cluster: an `OramaOperator` at
  `version: v0.7.1`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
