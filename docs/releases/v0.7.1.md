# v0.7.1

**Released:** 2026-10-20 · **Branch:** `main` · **Previous:** [v0.7.0](v0.7.0.md) (2026-10-20).

v0.7.1 is **a patch for the Cloud v1 migration and Lake's payments**. It adds the operator's half of
copying a Prod 1 team into a Cloud v1 stack: `OramaCloudV1Migration`, which runs the migration
tool's steps as Jobs (#653), and team migrations declared on `OramaCloudV1Set` (#654), so the copy is
a committed resource instead of a tool run by hand
([orama-bridge#137](https://github.com/oramasearch/orama-bridge/issues/137)). It also carries
`Lake.spec.payments` (#639) and a Stripe webhook endpoint's deletion that always finishes (#663).

**What changes on every cluster when it rolls:** every Cloud v1 stack, the production members
`v1-eu` and `v1-us` included, gets a `migration` database role, its Secret, a fourth control DB
schema that grants the role read and write on the rows of `public`, and four sandbox policies. The
role cannot sign in until a migration targets the stack. No migration, `spec.migrations` or
`spec.payments` is declared in `config/clusters/`, so nothing else is used.

Everything in [v0.7.0](v0.7.0.md) is still here. This page lists what is new or changed.

## 1. Cloud v1: Prod 1 team migrations

#658 and #660, issues #653 and #654; decisions 81 and 82. Detail:
[`docs/cloud-v1-migration.md`](../cloud-v1-migration.md).

- **`OramaCloudV1Migration`** declares one Prod 1 team copied into one stack. Each
  `(step, apply, attempt)` is one owned Job running `run-step` of the pinned `cloud-v1-migration`
  image, kept a week as the record; the tool's exit code sets the phase (0 `Succeeded`, 3
  `Blocked`, other `Failed`) and its `status --json` is `status.result`.
- **Guards before a Job:** the stack Ready with `ClusterRowReady` and every control DB schema
  current; no applied seed or catch-up while the dashboard crons or analytics import run; no
  catch-up or verify before an applied seed.
- **Prod 1** is read through a SELECT-only database URL, its engine origins and one SSM document
  with a scoped IAM key ([orama-bridge#205](https://github.com/oramasearch/orama-bridge/issues/205)),
  never SSH. Prod 1 egress (TCP 443 and 5432 to public ranges) exists only while a migration
  targets the stack.
- **`removeOnDelete`** runs the tool's `remove-target` when the resource is deleted; the tool refuses
  once the team has been switched, and the resource then stays.
- **The `migration` role** on every stack: a CNPG managed role with no superuser, createdb,
  createrole, replication or bypassrls, at most 4 connections, read and write on the rows of
  `public` and use of its sequences, no DDL. Its `login` is on only while a migration targets the
  stack.
- **On a set:** `spec.migrations` entries (`name`, `member`, `secrets`, `spec`) become migrations in
  the member's namespace, with their Secrets copied there and deleted with them. A change the
  migration kind makes immutable, or a move to another member, is reported on the set and the
  applied migration is left alone. Removing an entry deletes its migration (and so runs
  `remove-target` with `removeOnDelete`). A member or set being deleted waits for its migrations.

## 2. Lake: `spec.payments`

#655 and #670, issues #639 and #663. Detail: [`docs/lake/payments.md`](../lake/payments.md).

- From one Secret per environment (`accountID`, `operatorKey`, `appKey`) and `mode` (`test` or
  `live`), the operator keeps a `PaymentProvider`, a `PaymentWebhookEndpoint` at
  `https://<host>/billing/stripe/webhook` (seven event types, Stripe API version `2024-06-20`) and
  Lake's `PaymentCatalog` (`lake_usage`, `lake_private_warehouse`, `lake_dedicated_cluster`, no
  prices). It gives the Lake `LAKE_STRIPE_SECRET_KEY` and `LAKE_STRIPE_WEBHOOK_SECRET` only once all
  of them are Ready and Lake's own key is checked. A key of the wrong mode is refused.
- **A Lake's deletion always finishes**, whatever Stripe answers: the endpoint's finalizer retries for
  five minutes (at once on 401 or 403), then records `EndpointLeftBehind` naming the Stripe endpoint
  for a person to delete in the Dashboard.

## Known issues

Security first.

- **Security: Prod 1 egress is by port and public range, not by host**, while a migration targets a
  stack (#659: Cilium FQDN policy needs AKS ACNS).
- **Security: a migration copies its Prod 1 Secrets into the member's namespace** (the SELECT-only
  database URL, Prod 1's engine master key and the SSM key) for as long as the entry exists, and the
  commented pilot targets the nonprod `v1-dev`. The master key and the SSM access are an approved
  exception to Prod 1 being read-only (compliance EV-046).
- Unchanged from v0.7.0, all security: authenticated origin pulls use Cloudflare's global
  certificate (#633); apps and environments of a Lake without a `dnsSecretRef` stay on HTTP (#632);
  hostnames that resolve to private IPs pass the hooks deny list (#437); generated broker and Redis
  passwords and the master key have no rotation (#594); `CloudflareTunnel` adopts a CNAME found by
  name (#585); a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller
  (#280); legacy `secret_env_refs` can reference arbitrary Secrets in the Lake namespace (#492).
- **Removing a set's migration entry removes the copied team** when it has `removeOnDelete`; the tool
  refuses after the switch.
- **Applying `spec.payments` drops a member's `spec.env` Stripe variables at once**, until
  `PaymentsReady`; Lake's side (lake#861, lake#862) is not merged.
- **A left-behind Stripe endpoint** after a failed deletion is deleted by a person in the Dashboard.
- Unchanged from v0.7.0: the live-endpoint cautions in `payments.md`; nothing has run against real
  Stripe, a real leaf's port-forward or Prod 1 through the operator; nothing upgrades a dedicated
  cluster after it is made; `v1-prod` readers (#597).

## Installing it

- **A management cluster** is installed from `helmfile.yaml` ([`docs/install.md`](../install.md)).
  Before the upgrade, `make check-crds`, then the CRDs widened, the upgrade, and the CRDs exactly
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)): this release adds one CRD and
  changes `OramaCloudV1Set`, `LakeSet` and `Lake`.
- **A managed cluster** is installed by its management cluster: an `OramaOperator` at
  `version: v0.7.1`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
