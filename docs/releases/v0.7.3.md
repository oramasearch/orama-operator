# v0.7.3

**Released:** 2026-10-20 · **Branch:** `main` · **Previous:** [v0.7.2](v0.7.2.md) (2026-10-20).

v0.7.3 is **a patch that releases the committed cluster files** since v0.7.2. The operator's code,
CRDs and chart are unchanged; what moves is `config/clusters/`:

- Every leaf's `operator.yaml` at `v0.7.2`.
- The Lake set templates at `oramasearch/lake:v0.3.1`.
- A nonprod Cloud v1 set declares a pilot team migration at `step: plan`.

Also a pilot entry merged early and its revert, and the v0.7.2 back-merge. The leaves move to
`v0.7.3` in their own change.

| Measured | Value |
|---|---|
| Resource kinds | 43 (unchanged); no CRD change |
| Lake schema | unchanged: lake `2b39c2f`, through `0090_billing_contacts` |
| Tests | see [Verification](#verification) |

## What it does not include

Everything under [v0.7.1](v0.7.1.md)'s *does not include*.

## Known issues

Unchanged from [v0.7.1](v0.7.1.md#known-issues). Also: a declared migration copies its source
Secrets (the source database URL and engine master key) into the member's namespace once applied,
and at `seed` copies a real team's documents.

## Verification

Run on the release branch, macOS arm64, with the Kubernetes 1.30.3 envtest binaries and a local
Postgres: `go build`, `go vet`, `gofmt -l` (nothing), `make manifests generate` (no diff),
`helm lint chart` (0 failed); `go test ./... -count=1` with the Lake schema, order and control DB
Postgres tests: **834 test functions, 822 passed, 12 skipped, 0 failed** (827 subtests passed).
`cmd`'s tests read every committed file in `config/clusters/` (the platform sync, the same operator
version on every leaf, the sets' CRDs).

The image built from the tag is the same as v0.7.2's (no code change), published as
`oramasearch/orama-operator:v0.7.3` (there is no `latest`); the chart is published as `0.7.3` in
`oramasearch/orama-operator-chart`.

When applied, the pilot migration's `plan` step succeeded and the seed dry run was refused by the
tool, writing nothing.
