# v0.10.3

**Released:** 2026-10-25 · **Branch:** `main` · **Previous:** [v0.10.2](v0.10.2.md) (2026-10-25).

A patch with one fix: the **Cloud v1 writer embeds 64 texts per batch, not 50,000**, so a CPU writer's memory
stays bounded during a copy. `v1-eu`'s writer was OOM-killed three times during the cutover copy
([orama-bridge#257](https://github.com/oramasearch/orama-bridge/issues/257)).

| Measured | Value |
|---|---|
| Resource kinds | 49 CRDs in `chart/crds` (unchanged) |
| CRD changes | none |
| Lake schema | unchanged |
| Tests | see [Verification](#verification) |

## What it includes

| PR | Change |
|---|---|
| [#1023](https://github.com/oramasearch/orama-operator/pull/1023) | **The Cloud v1 writer embeds 64 texts per batch.** The engine's `embedding_queue_limit` drops from 50,000 (Prod 1's value, set for a GPU writer) to 64, in the writer's config and in the readers' local writer side, through one named constant, `writerEmbeddingBatch`. A batch's working memory grows with the number of texts, and at 50,000 the writer took every queued text of a collection into one batch: `v1-eu`'s CPU writer reached 12.5 GB at a 12Gi limit and 16.7 GB at 16Gi, and was OOM-killed each time, losing uncommitted writes and leaving 5 teams with broken copies. 64 keeps a batch to a few hundred MB, and the setting is also the queue in front of the writer, so a copy runs at the writer's pace. The same value on every cluster. Issue [orama-bridge#257](https://github.com/oramasearch/orama-bridge/issues/257) |

Since v0.10.2, `dev` also holds YAML changes under `config/clusters/`. They are resources applied from their files,
not part of the operator image:

- **Leaf operator pins:** every leaf on v0.10.2 (`1840811`), and the v0.10.2 back-merge (#1022).
- **`lake-nonprod` on lake v0.7.1 and the agents' releases:** `dev` (`f0ed3cf`), then `testing` (`de76213`), then
  the template, which `staging` follows, with the `dev` and `testing` pins removed (`080672f`).
- **`lake-prod` on lake v0.7.1 and the agents' releases:** `eu.lake.live` (`742d8b7`), then the template, which
  `us.lake.live` follows, with the EU pin removed (`35c3d00`).

## Upgrading

**No CRD changes.** Roll as for every release: CRDs widened, then `helm upgrade`, then CRDs exactly
([`../operations/crd-rollout.md`](../operations/crd-rollout.md)).

**What restarts, once, on the first reconcile after the roll:** every Cloud v1 stack's **writer and readers**
(#1023), because their rendered engine config changes. `v1-prod` included: on `orama-production-cluster-02`, rolling
there is a production change, so confirm the set `v1-prod` and its members are `Ready` afterwards, and that the
writer and readers restarted once and not again. The `v1-eu` cutover copy is paused until this roll.

Nothing else changes in what the operator renders.
