# v0.11.1

**Released:** 2026-10-29 · **Branch:** `main` · **Previous:** [v0.11.0](v0.11.0.md) (2026-10-29).

A patch release: **production's observability hub runs on the management cluster**, and the `prod-support` cluster
purpose is removed. Steve Sperandeo, 2026-10-29, reviewing #1044: *"let's put the observability databases and
functionality on the management cluster instead of provisioning a prod support cluster"*.

| Measured | Value |
|---|---|
| Resource kinds | 54 CRDs in `chart/crds` (unchanged) |
| CRD changes | `ObservabilityHub.spec.clusterRef` becomes optional (still immutable); `prod-support` leaves the `purpose` enums of `PixieCloud` and `PixieVizier`; descriptions on `ObservabilityAgent` |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

| PR | Change |
|---|---|
| [#1064](https://github.com/oramasearch/orama-operator/pull/1064) | **Production's hub on the management cluster** ([#1059](https://github.com/oramasearch/orama-operator/issues/1059), DESIGN decision 105). A hub with no `clusterRef` runs on the managing cluster, which counts as production. Production agents report only to that hub, and nonprod agents only to a hub on a nonprod cluster. A hub on a production cluster is refused, so nothing runs beside customer workloads. The agents still reach the hub over their `PeerLink`, whose hub end is the managing cluster. `prod-support` is removed: its enum values, the set refusal `SupportCluster` and its credential tier. Listing production credentials no longer looks up a `KubernetesCluster` with an empty name, which would have failed every nonprod Secret copy once such a hub existed |

Since v0.11.0, `dev` also holds `config/clusters/` YAML: every leaf on v0.11.0.

## What it does not include

- No observability resource exists on any cluster. Creating production's hub is a later step: the private image
  mirrors and the Pixie build ([#455](https://github.com/oramasearch/orama-operator/issues/455)), the platform
  releases, then the hub and agents (rollout steps 1, 3, 5 and 6 in
  [observability.md](../infrastructure/observability.md)).
- The hub has no public ingress. People reach its UIs with `kubectl port-forward` until an authenticated tunnel is
  added.
- When the hub is created, its storage is billed on the management cluster (hub Prometheus 100 Gi by default, plus
  OpenSearch, CloudNativePG and NATS volumes).

## Upgrading

- **CRDs in two steps around the roll** ([crd-rollout.md](../operations/crd-rollout.md)): widened before the operator
  starts, exact once it alone runs. Removing `prod-support` from the enums is safe: nothing was ever created with it.
- **What rolls on each cluster:** the operator, and the zetta-tunnel mesh pods, which carry a container from the
  operator image. No Lake or Cloud v1 workload changes.

## Known issues

- The managing cluster counts as production because a hub without `clusterRef` names it. A cluster that manages only
  nonprod clusters has no production agent that could report to such a hub.
- The hub's own metrics carry the hub's name as their `cluster` label, because the operator does not know its own
  cluster's name; name the hub after the managing cluster.
- Otherwise unchanged from [v0.11.0](v0.11.0.md#known-issues), less "nothing has run on a cluster": v0.11.0 runs on
  every cluster.
