# v0.11.1

**Released:** 2026-10-29 · **Branch:** `main` · **Previous:** [v0.11.0](v0.11.0.md) (2026-10-29).

A patch release: **a production observability hub runs on the management cluster**, and the `prod-support` cluster
purpose is removed, so no separate support cluster is needed for observability.

| Measured | Value |
|---|---|
| Resource kinds | 54 CRDs in `chart/crds` (unchanged) |
| CRD changes | `ObservabilityHub.spec.clusterRef` becomes optional (still immutable); `prod-support` leaves the `purpose` enums of `PixieCloud` and `PixieVizier`; descriptions on `ObservabilityAgent` |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

- **Production's hub on the management cluster.** A hub with no `clusterRef` runs on the managing cluster, which counts
  as production. Production agents report only to that hub, and nonprod agents only to a hub on a nonprod cluster. A
  hub on a production cluster is refused, so nothing runs beside customer workloads. The agents still reach the hub over
  their `PeerLink`, whose hub end is the managing cluster. `prod-support` is removed: its enum values, the set refusal
  `SupportCluster` and its credential tier. Listing production credentials no longer looks up a `KubernetesCluster`
  with an empty name, which would have failed every nonprod Secret copy once such a hub existed.

## What it does not include

- Creating a production hub is a later step: the image mirrors and the Pixie build, the platform releases, then the hub
  and agents (rollout steps 1, 3, 5 and 6 in [observability.md](../infrastructure/observability.md)).
- The hub has no public ingress. People reach its UIs with `kubectl port-forward` until an authenticated tunnel is
  added.
- When the hub is created, its storage is billed on the management cluster (hub Prometheus 100 Gi by default, plus
  OpenSearch, CloudNativePG and NATS volumes).

## Upgrading

- **CRDs in two steps around the roll** ([crd-rollout.md](../operations/crd-rollout.md)): widened before the operator
  starts, exact once it alone runs. Removing `prod-support` from the enums is safe only if nothing was created with it.
- **What rolls on each cluster:** the operator, and the zetta-tunnel mesh pods, which carry a container from the
  operator image. No Lake or Cloud v1 workload changes.

## Known issues

- The managing cluster counts as production because a hub without `clusterRef` names it. A cluster that manages only
  nonprod clusters has no production agent that could report to such a hub.
- The hub's own metrics carry the hub's name as their `cluster` label, because the operator does not know its own
  cluster's name; name the hub after the managing cluster.
- Otherwise unchanged from [v0.11.0](v0.11.0.md#known-issues).
