# v0.1.0

**Released:** 2026-10-12 · **Branch:** `main` · **Previous:** none. This is the first tagged release.

orama-operator is the Kubernetes operator for Orama's cloud. You describe a system as a custom
resource and the operator builds it, keeps it that way, and reports what is true. It is a Go
(kubebuilder) operator with a thin Helm chart that installs it. Kubernetes holds the desired
state, Zetta holds the observed state, and a steady system produces no writes.

Because this is the first release, **this page lists everything in it**: all 17 resource kinds,
what each one reconciles, the deployment API the manager serves, and how it is installed. The
field-by-field reference is [`docs/crd-reference.md`](../crd-reference.md); this page says what
each kind is for and links the page that holds the detail.

## 1. How the operator works

- **Infrastructure state is a custom resource**, declared, owned and reconciled. Nothing is a
  one-shot Job or a side effect of an application starting. This holds for resources outside the
  cluster too: a DNS record, a load balancer and an auth application are each a resource.
- **Status is accurate and does not flap.** Each kind reports a `Ready`, `Progressing` or
  `Degraded` phase, a count, a per-component list and standard conditions. The status
  subresource is written only on a real transition, so a steady system produces no control-plane
  traffic.
- **Least privilege.** Every service that reaches a datastore gets its own role with only the
  grants it needs.
- **Workloads are hardened the same way everywhere**; the rules applied to every component are
  in [`docs/components.md`](../components.md).
- **A dependency's own operator is used only when it is reliable.** CloudNativePG runs Postgres.
  The RabbitMQ topology is the operator's own kind because the upstream topology operator's
  images stopped being pullable.
- **External resources are never destroyed by accident.** Kinds that own something outside the
  cluster hold a finalizer, and `ClerkApplication` defaults to keeping the application when its
  resource is deleted.

## 2. Zetta clusters

**`OramaZettaCluster`** deploys a headless Orama Zetta cluster: a StatefulSet of equal-peer
nodes, a headless Service for peers and a client Service for the API (MCP, REST, the web
portal). See [`docs/zetta-datastore.md`](../zetta-datastore.md),
[`docs/zetta-cluster-mtls.md`](../zetta-cluster-mtls.md) and
[`docs/connecting.md`](../connecting.md).

- **One mTLS cluster from a shared join token.** The operator mints one token per cluster; the
  engine derives the cluster CA from it. There is no plaintext mode.
- **Authentication is always on.** The operator seeds an admin token, injects it, and the node
  denies every request without a bearer.
- **Zetta is the operator's own datastore.** A cluster can carry the operator's schema
  (`orama_control`, `orama_data`), applied by a Job over the node's SQL API.
- **Clusters that span Kubernetes clusters.** Resources sharing a `clusterName` are siblings of
  one multi-leader cluster. Each slice declares how it is reached (`wan-accessible` or
  `dial-out-only`), and peers are discovered through a topology table in Zetta itself. Peer
  addresses are validated as data, never passed as shell text.
- **Storage and sizing**: a volume per node, resource caps, and extra environment variables,
  with any that collide with the operator's own reported in status.
- **Exposure is explicit**: an Ingress and a proxied Cloudflare DNS record only when asked for.
- **Elastic capacity (opt-in, not live-tested)**: the operator can own a Karpenter `NodePool`
  for a cluster, with cost guardrails, and can own the Karpenter install itself
  ([`docs/karpenter-cloud-iam-prerequisite.md`](../karpenter-cloud-iam-prerequisite.md)).

## 3. Lake

**`Lake`** (cluster-scoped) deploys the lake service of the liquid project and everything it
needs. See [`docs/lake/README.md`](../lake/README.md).

### The service itself

- **Deployment, Service, Ingress and DNS**, with Lake's own health probes and non-root
  execution.
- **Control-plane Postgres** as a CloudNativePG cluster, with the schema applied once through a
  `PostgresSchema` from a vendored, byte-verified copy of lake's schema
  ([`schema.md`](../lake/schema.md)). Lake never migrates itself.
- **A data-plane Zetta**: an owned `OramaZettaCluster`.
- **The shared store volume**: a claim the operator creates, or an existing one it mounts
  without adopting.
- **Safe rollouts**: a single replica on a ReadWriteOnce volume is recreated, never overlapped,
  unless the store allows a hand-off.
- **Backups (opt-in)**: scheduled Postgres backups to object storage
  ([`backups.md`](../lake/backups.md)).
- **Pods resolve with `ndots:2`** and in-cluster URLs are full Service names.

### Workspaces, services and storage

- **Workspaces**: lake's `workspaces` rows become isolated namespaces, each with its own Zetta,
  network policy and quota. Volumes grow in place from lake's desired size
  ([`workspaces.md`](../lake/workspaces.md)).
- **Managed services**, read from lake's control Postgres: Zetta and Postgres, the catalogue
  kinds Kafka, ClickHouse, TiDB, Cassandra and Valkey through their upstream operators, and
  SQLite, DuckDB and Polars, which the operator runs itself
  ([`services.md`](../lake/services.md)).
- **Customer stores**: a cluster volume per store, and delivery of the credential for a
  customer's own bucket. Stores are mounted into the pods the operator builds
  ([`stores.md`](../lake/stores.md)).
- **Volume snapshots**: scheduled and requested CSI snapshots of the store and workspace
  volumes, with pruning ([`volume-snapshots.md`](../lake/volume-snapshots.md)).

### Apps, builds and environments

- **Apps**: lake's `apps` rows become **`LakeApp`** workloads from a pinned repository revision
  or a digest-pinned image, with private-by-default ingress, scoped tokens, wildcard DNS and
  live rollout events ([`apps.md`](../lake/apps.md)).
- **Image builds in the cluster**: one rootless BuildKit Job per queued row, isolated per
  space, with a registry cache, concurrency caps and progress events
  ([`builds.md`](../lake/builds.md)).
- **Environments**: a desired deployment becomes a **`LakeEnvironment`**: one restricted,
  quota-bound namespace per named or per-change environment, with preview DNS and teardown
  ([`environments.md`](../lake/environments.md)).
- **App transfer metering**: bytes in and out per app and hour, read from the ingress
  controller ([`app-transfer.md`](../lake/app-transfer.md)).

### Agents, methodologies and compute

- **Agents**: the Agent Library's deployments, launches of user-created agents as jobs or
  services, and one CronJob per schedule ([`agents.md`](../lake/agents.md)).
- **Methodology runs**: a workspace's Python methodology runs as untrusted code in its own pod,
  with no credential and no network unless granted
  ([`methodology-runs.md`](../lake/methodology-runs.md)).
- **Workload resources**: the CPU, memory and GPU each scheduled pod was given, written only on
  change, for lake to price ([`workload-resources.md`](../lake/workload-resources.md)).

### Secrets and recovery

- **`LakeSealedSecret`**: one-way delivery of a secret. Each Lake owns an X25519 sealing key and
  publishes its recipient; ciphertext bound to the cluster becomes an owned Kubernetes Secret,
  with no plaintext in the authored resource ([`sealed-secrets.md`](../lake/sealed-secrets.md)).
- **`LakeRestoreRehearsal`** (cluster-scoped): automates a Postgres restore, a scratch upgrade
  and a replicated failover, and records the evidence
  ([`data-services/postgres.md`](../lake/data-services/postgres.md)).
- **Data-service evidence in status**: `kubectl get lake` reports managed and unmanaged
  data-service counts, and never implies protection that has not been tested.

## 4. Orama Cloud v1

**`OramaCloudV1`** deploys the complete, self-contained Orama Cloud v1 stack, one resource per
cluster. See [`docs/components.md`](../components.md).

- **Components**: the engine (a GPU-capable writer, readers and Envoy), the dashboard, the
  docs site, ingestion (the index builder and the crawler), the control database, analytics,
  the cache, the broker, hosted search, the semantic cache, and the workers bundled into one
  image. Each can be turned off.
- **Data stores** run in the cluster or point at an external endpoint: Postgres through
  CloudNativePG, ClickHouse through the Altinity operator, Redis, RabbitMQ and Typesense.
- **Regions**: a cluster is a `primary` or a `read` tier, and read tiers reach the primary
  through configured peers. No service mesh.
- **Profiles**: `light`, `medium` and `heavy` preset replication and sizing.
- **Identity provider**: none, Keycloak, Firebase or Clerk.
- **Language models**: several providers at once, with a default.
- **Secrets**: the operator generates a per-component Secret with placeholder values,
  create-if-absent; real values are edited in. No plaintext in the resource.
- **Right-sizing**: each component's Kubernetes limits are also translated into the binary's
  own memory settings.
- **A demo seed** so a fresh install answers queries.

## 5. Supporting resources

| Kind | What it reconciles |
|---|---|
| `PostgresSchema` | A versioned SQL schema: an owned, idempotent migration Job that waits for the database, checks a guard, applies, and records the applied version in status. |
| `RabbitMQTopology` | The broker's vhosts, users, permissions and streams, through its management API, so each service has its own user. |
| `CloudflareDNSRecord` | One DNS record, proxied or not. Owned by the kinds that expose a host. |
| `CloudflareLoadBalancer` | A global load balancer: origin pools, health checks, geo steering and failover. Implemented, not live-tested. |
| `CloudflareKVNamespace` | A Workers KV namespace. |
| `CloudflareR2Bucket` | An R2 bucket. |
| `ClerkApplication` | A Clerk application per environment, through the Platform API, with its keys and issuer written to an owned Secret. Keeps the application on delete unless told otherwise. |

The pattern and the reasons are in [`docs/datastore-crds.md`](../datastore-crds.md).

## 6. End-to-end test kinds

These are test fixtures. Their controllers are off unless the manager runs with
`--enable-e2e-controllers`, and their definitions are in `chart/e2e-crds/`, not the install
chart.

| Kind | What it runs |
|---|---|
| `OramaCloudV1E2ETest` | The functional suite for the v1 stack, embedded in the operator: about 70 assertions over search, CRUD, replication, hooks, analytics and answers. |
| `ZettaClusterE2ETest` | The live-cluster Zetta suite, from the `oramasearch/zetta-e2e` image: the in-app test kit and black-box integration, with authorization always on. |
| `LakeE2ETest` (cluster-scoped) | A lake-owned runner: sign up, create a repository, push and pull it through liquid's sync protocol, verify the bytes. |

## 7. The deployment control plane

The manager serves an authenticated deployment API on `--control-plane-bind-address` (default
`:8090`), over REST `/v1` and MCP, from one OpenAPI contract. liquid drives it. See
[`docs/control-plane/README.md`](../control-plane/README.md).

| Operation | What it does |
|---|---|
| `createDeployment` | Record a desired deployment for an environment. |
| `listDeployments` | List deployments and their history. |
| `deploymentStatus` | Read a deployment's observed status. |
| `rollbackDeployment` | Roll an environment back to an earlier deployment. |

Desired deployments are appended to the operator's Zetta control plane and materialised as
`LakeEnvironment` resources; history and audit live in Zetta.

## 8. Install and operate

- **The Helm chart** (`chart/`, version `0.1.0`) installs the manager, its RBAC and the 14
  resource definitions. [`docs/install.md`](../install.md) covers the platform operators, the
  chart, a first resource, secrets, images, multi-region and uninstall.
- **Private images**: the manager's and the applications' pull secrets are separate settings
  ([`docs/install/credentials.md`](../install/credentials.md)).
- **On-premises**: a connected or air-gapped install of one Lake on the liquid k0s distribution
  ([`docs/install/k0s.md`](../install/k0s.md)).
- **Resource definitions and upgrades**: Helm applies definitions on install only, so an upgrade
  never adds one. `make check-crds CONTEXT=<context>` runs before any upgrade
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)).
- **Manager flags**: `--metrics-bind-address` (`:8080`), `--health-probe-bind-address`
  (`:8081`), `--control-plane-bind-address` (`:8090`), `--leader-elect`,
  `--enable-e2e-controllers`, and the default images for the services the operator runs itself
  (`--lake-sqlite-image`, `--lake-duckdb-image`, `--lake-polars-image`).
- **External dependencies**: [`docs/provisioning-runbook.md`](../provisioning-runbook.md).

## What `v0.1.0` does **not** include

- **Live proof of the Cloudflare load balancer and the Karpenter slices.** They are implemented
  and unit-tested, and have not been run against a real account.
- **Further Cloud v1 work**: storage, authentication and ownership changes for running a
  second Orama Cloud v1 stack are not in this release.
- **Creating clusters.** The operator reconciles what runs inside a Kubernetes cluster and a
  few external resources. It does not yet create a cluster.
- **A version reported by the binary.** The manager has no version flag or build stamp; the
  image tag names the commit.
- **Backups without object storage.** A `Lake` reports `BackupReady=False` until object
  storage for its backups is configured.

## Known issues

- **Three leftover test resource definitions** from before the e2e kinds were gated may remain
  on clusters that installed earlier builds, and are to be retired.
- **The chart's RBAC is maintained by hand** and can drift from the generated role. A missing
  grant, or one missing resource definition, makes the whole manager crash-loop; this is
  deliberate, and the checks are in
  [`docs/operations/crd-rollout.md`](../operations/crd-rollout.md).

```sh
  --set operator.image.tag=<tag>
```
