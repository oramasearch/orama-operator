# v0.9.5

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.4](v0.9.4.md) (2026-10-24).

A patch carrying **what lake v0.6.0 needs from the operator**: its schema through
`0099_account_balances` and the Stripe events of the prepaid account balance
([lake#1114](https://github.com/oramasearch/lake/issues/1114)).

> **Read [Before it rolls](#before-it-rolls).** It rolls before the lake v0.6.0 image.

| Measured | Value |
|---|---|
| Resource kinds | 48 CRDs in `chart/crds` (unchanged) |
| Lake schema | lake `dev` at `58356286` (v0.6.0's schema), through `0099_account_balances` |
| Tests | see [Verification](#verification) |

## Changes

| PR | Change |
|---|---|
| [#937](https://github.com/oramasearch/orama-operator/pull/937) | **Lake schema through `0099_account_balances`** (`account_balances`, `account_balance_credits`, `account_balance_charges`; guard `account_balances_guard`, which the restore rehearsal reads). Additive; the schema gate holds the lake v0.6.0 image until it has applied ([`../lake/schema.md`](../lake/schema.md)) |
| [#937](https://github.com/oramasearch/orama-operator/pull/937) | **Stripe events for the balance**: every Lake with `spec.payments` subscribes to `payment_intent.succeeded`, `payment_intent.payment_failed` and `setup_intent.succeeded` (auto top-up), beside the Checkout events top-ups use. Existing endpoints are corrected on the next pass ([`../lake/payments.md`](../lake/payments.md)) |

## Before it rolls

- **Roll it before the lake v0.6.0 image.** lake v0.5.2 keeps running on the new schema.
- **The Lake's restricted Stripe key (`appKey`) must be allowed to write PaymentIntents** for auto
  top-up; that is set in the Stripe Dashboard, not by the operator.
- Rolling needs Steve's consent: the managing cluster by its script, then every leaf's
  `operator.yaml` in one command.
