# v0.10.4

**Released:** 2026-10-26 · **Branch:** `main` · **Previous:** [v0.10.3](v0.10.3.md) (2026-10-25).

A patch with two changes: **agents default to `gpt-6.1-sol`**, and **a Lake restart replaces the App's pods**. Before
it, pressing Restart on a Lake App bumped its generation but left the pod template unchanged, so no pod was replaced.

| Measured | Value |
|---|---|
| Resource kinds | 49 CRDs in `chart/crds` (unchanged) |
| CRD changes | `LakeApp` gains `spec.sync.restartGeneration` (optional); `Lake`'s `spec.agents.model` default is `gpt-6.1-sol` |
| Lake schema | nothing vendored: lake v0.7.2's migration `0104_app_restarts` comes from its image (`lake migrate`) |
| Tests | see [Verification](#verification) |

## What it includes

- **Agents default to `gpt-6.1-sol`.** The `Lake` CRD default for `spec.agents.model` and the
  controller's `agentDefaultModel` move from `gpt-5.5` to `gpt-6.1-sol`. People choose a model per
  workspace in Lake (lake v0.7.2); this is the model when nobody has. A CRD default fills only a missing
  field, so a Lake that already stores `gpt-5.5` keeps it: name `agents.model: gpt-6.1-sol` explicitly in
  a set to move it.
- **A Lake restart replaces the App's pods.** The apps sync reads lake's `apps.restart_generation`
  (lake v0.7.2, migration `0104_app_restarts`) into the new optional field
  `LakeApp.spec.sync.restartGeneration`, and writes it on the pod template as the annotation
  `orama.cloud/lake-app-restart` only when it is above 0. Each restart is then a new template, so the
  Deployment replaces its pods; a scale or an access change leaves the annotation as it is. The query
  reads the column through `to_jsonb`, so it works with either schema: before migration `0104` every App
  reads 0.

## Upgrading

**CRD change.** `LakeApp` gains one optional field, so roll as for every release: CRDs widened first
(`hack/crdunion`), then `helm upgrade`, then CRDs exactly
([`../operations/crd-rollout.md`](../operations/crd-rollout.md)). The change only adds a field and changes a
default, so the running v0.10.3 operator is unaffected by the widened CRDs.

**Order with lake v0.7.2.** Either can roll first. Until both have, a restart is recorded but replaces nothing, as
before. Nothing needs to be vendored for lake v0.7.2: its image migrates its own schema.

**What restarts on the roll:** nothing that the restart change adds. An App never restarted has
`restartGeneration` 0 and gets no annotation, so no running App pod is replaced. Where a Lake's agents model
moves to `gpt-6.1-sol`, its agent workloads roll once with the new model; the set files decide that, not the
operator roll.

## What it does not include

- Routing the Ingress to lake's proxy listener.
- The changes held back in [v0.9.0](v0.9.0.md#what-it-does-not-include).
- Ordering each wildcard certificate once per domain: each production cluster orders every wildcard, so a
  domain served from two clusters gets duplicate certificate packs.

## Known issues

- **Neither change had run on a cluster when the release was cut.** The restart change's live proof is a
  Restart in Lake (on lake v0.7.2) replacing the App's pods.
- **A Lake that already stores `gpt-5.5` keeps it** until its set names `agents.model: gpt-6.1-sol`.
- A Cloud v1 writer image rollout can be blocked by an unhealthy old pod; not fixed here.
- Otherwise unchanged from [v0.10.3](v0.10.3.md#known-issues).
