# v0.10.4

**Released:** 2026-10-26 · **Branch:** `main` · **Previous:** [v0.10.3](v0.10.3.md) (2026-10-25).

A patch with two changes: **agents default to `gpt-6.1-sol`**, and **a Lake restart replaces the App's pods**. Before
it, pressing Restart on a Lake App bumped its generation but left the pod template unchanged, so no pod was replaced
([lake#1228](https://github.com/oramasearch/lake/issues/1228)).

| Measured | Value |
|---|---|
| Resource kinds | 49 CRDs in `chart/crds` (unchanged) |
| CRD changes | `LakeApp` gains `spec.sync.restartGeneration` (optional); `Lake`'s `spec.agents.model` default is `gpt-6.1-sol` |
| Lake schema | nothing vendored: lake v0.7.2's migration `0104_app_restarts` comes from its image (`lake migrate`) |
| Tests | see [Verification](#verification) |

## What it includes

| PR | Change |
|---|---|
| [#1030](https://github.com/oramasearch/orama-operator/pull/1030) | **Agents default to `gpt-6.1-sol`.** The `Lake` CRD default for `spec.agents.model` and the controller's `agentDefaultModel` move from `gpt-5.5` to `gpt-6.1-sol` (Steve, 2026-10-26: "default to sol"). People choose a model per workspace in Lake (lake v0.7.2); this is the model when nobody has. A CRD default fills only a missing field, so a Lake that already stores `gpt-5.5` keeps it: the sets name `agents.model: gpt-6.1-sol` explicitly to move it. |
| [#1033](https://github.com/oramasearch/orama-operator/pull/1033) | **A Lake restart replaces the App's pods.** The apps sync reads lake's `apps.restart_generation` (lake v0.7.2, migration `0104_app_restarts`, [lake#1232](https://github.com/oramasearch/lake/pull/1232)) into the new optional field `LakeApp.spec.sync.restartGeneration`, and writes it on the pod template as the annotation `orama.cloud/lake-app-restart` only when it is above 0. Each restart is then a new template, so the Deployment replaces its pods; a scale or an access change leaves the annotation as it is. The query reads the column through `to_jsonb`, so it works with either schema: before migration `0104` every App reads 0. Issue [lake#1228](https://github.com/oramasearch/lake/issues/1228) |

## Upgrading

**CRD change.** `LakeApp` gains one optional field, so roll as for every release: CRDs widened first
(`hack/crdunion`), then `helm upgrade`, then CRDs exactly
([`../operations/crd-rollout.md`](../operations/crd-rollout.md)). The change only adds a field and changes a
default, so the running v0.10.3 operator is unaffected by the widened CRDs.

**Order with lake v0.7.2.** Either can roll first. Until both have, a restart is recorded but replaces nothing, as
before. Nothing needs to be vendored for lake v0.7.2: its image migrates its own schema.

**What restarts on the roll:** nothing that #1033 adds. An App never restarted has `restartGeneration` 0 and gets no
annotation, so no running App pod is replaced. Where a Lake's agents model moves to `gpt-6.1-sol`, its agent
workloads roll once with the new model; the set files decide that, not the operator roll.

## Known issues

- **Neither change has run on a cluster yet.** The managing cluster ran v0.10.3 when this was cut; there was no
  `dev-<sha>` operator build of #1030 or #1033 on the dev environment first. #1033's live proof is a Restart in Lake
  (on lake v0.7.2 or `dev-11153627`) replacing the App's pods.
- **The set templates do not name `agents.model` yet.** Only the `lake-nonprod` `dev` and `testing` members do. Until the
  `lake-nonprod` and `lake-prod` templates name `gpt-6.1-sol`, a Lake that stores `gpt-5.5` keeps it.
- [#1036](https://github.com/oramasearch/orama-operator/issues/1036): a Cloud v1 writer image rollout blocked by an
  unhealthy old pod (nonprod's writer); not fixed here.
- Otherwise unchanged from [v0.10.3](v0.10.3.md#known-issues).
