# v0.8.0

**Released:** 2026-10-22 · **Branch:** `main` · **Previous:** [v0.7.3](v0.7.3.md) (2026-10-20).

v0.8.0 is **a security hardening release for multi-tenant clusters**, with the features reviewed
alongside it. It vendors **lake v0.4.0's schema** (`0091` to `0093`), so lake v0.4.0 can roll after
it. 78 pull requests since v0.7.3 (89 non-merge commits).

> **Read [Before upgrading](#before-upgrading).** Several changes need a Secret, an image, a decision
> or an applied file first, and several restart workloads on every cluster.

| Measured | Value |
|---|---|
| Resource kinds | 48 CRDs in `chart/crds`, four new: `BackupSchedule`, `Backup`, `EdgeHostPolicy`, `CloudflareHostPolicy` |
| Lake schema | lake tag v0.4.0 (`9115632e`), through `0093_root_recovery_participants` |
| Tests | see [Verification](#verification) |

## Security hardening

- Only the operator's namespace may install the cluster-wide Karpenter; a tenant's
  `OramaZettaCluster` no longer keeps it alive.
- An app row may name only lake secret references, never a Kubernetes Secret.
- `CloudflareTunnel` creates its CNAME only, marked, and deletes it only while marked.
- Every cluster enforces network policy with Cilium (CRD enums and a refusal of anything else).
- ingress-nginx takes only the client address from Cloudflare's ranges: `enable-real-ip` with
  `forwarded-for-header: CF-Connecting-IP` and `proxy-real-ip-cidr`, in `helmfile.yaml` and every
  `platform.yaml`; `use-forwarded-headers` is refused by the test.
- The Zetta cluster join token is mounted read-only as a file (`ZETTA_CLUSTER_TOKEN_FILE`).
- An app reaches its Lake on the API port only.
- Build namespaces deny cloud metadata with Cilium.
- App rows may not name platform hosts, wider Zetta scopes or a foreign namespace.
- A custom domain belongs to the first claim, never to a platform host, and no certificate is
  shared across owners.
- Methodology credential pods start in their own `/tmp` with `PYTHONSAFEPATH=1`, never the
  sandbox's volume.
- Sealed-secret minting never sends the operator's Kubernetes bearer to Lake.
- Tenant agent pods never get the platform's model-provider key; earlier copies are deleted.
- A workspace Kafka listener is TLS, admits only its Lake, and its user has ACLs.
- Each app pod is told its auth mode in `APP_AUTH`.
- Each node's mesh agent receives only its own workloads' private keys.
- The superuser session against a tenant's Postgres pins `search_path` and qualifies every
  catalog name.
- The zetta-tunnel gateway never serves a host that requires origin client certificates.
- Methodology runs and served models count against their workspace's quota, with a
  methodology-ceiling quota per Lake.
- A production credential is never copied into a nonprod member: the set copy refuses
  production-listed and other-purpose Secrets and migration source credentials; nonprod sets use
  their own Secrets.
- A production pull Secret is never copied to a nonprod cluster.
- A production `LakeSet`'s Stripe, model-provider and order Secrets never reach a nonprod Lake.
- No Cloud v1 reader holds the writer's master key, and harvest-master gets its own broker user.
- A production set's dashboard never runs on sandbox authentication.
- The dashboard takes a Stripe restricted key from its own Secret.
- ingress-nginx clears `Authorization` and drops `Cookie` headers carrying a Lake control session
  on app Ingresses only, with the same maps in `helmfile.yaml` and every `platform.yaml`.
- App-transfer metering reads counters only from platform ingress-nginx pods whose owner chain
  checks out by UID, for apps the Lake controls.
- Cloud v1 writable ephemeral storage is bounded.
- Cloud v1 workloads run under their own service accounts.
- Each Lake gets its own deploy bearer, and the deployment API moves to TLS (cert-manager) behind
  a NetworkPolicy, no longer accepting the admin token.
- A peer gateway is removed when its credentials go missing, change or are deleted, and a changed
  credential replaces the gateway.
- ingress-nginx admission webhooks and snippet annotations are off, in `helmfile.yaml` and every
  `platform.yaml`.
- A Lake's Zetta egress is left to its `NetworkSandbox` (`ZETTA_EGRESS_ALLOW=*`), then a Lake
  Zetta's sandbox egress is mirrored into `ZETTA_EGRESS_ALLOW`.
- Stage and collect pods reach their Lake; a failure reports the pod's own message.

## Features and other fixes

- `BackupSchedule` and `Backup` kinds, Jobs from the operator image, scoped R2 buckets;
  `CloudflareR2Bucket` gains `deletionPolicy`.
- `EdgeHostPolicy` and `CloudflareHostPolicy`: per-host Full (strict) and HTTPS redirect as
  declared Cloudflare rules.
- HTTP-01 for Lake hosts without a DNS-01 credential, chosen per host.
- The zone policy orders an Advanced Certificate for proxied hosts Universal SSL does not cover.
- `LakeSet` `spec.e2eTests` runs the Lake e2e gate on the member's cluster.
- e2e control-plane sections for the Cloud v1 dashboard and the edge workers.
- A serverless-redis-http shim so the dashboard's Upstash client uses the stack's Redis.
- Third-party keys from their own Secrets, and the dashboard's derived values.
- HPES in the stack for index-builder's embeddings, on CPU, no public host.
- The engine and the dashboard sign in as their own datastore users.
- Cloud v1's generated broker and Redis passwords rotate through `spec.credentialRotation`.
- The Cloud v1 import consumer runs in the stack, reading the S3 bucket through SQS (off by
  default).
- A Cloud v1 migration's removal deletes its finished Jobs before the run volume and never reruns a
  successful removal.
- `Lake` `spec.replicas` above one is refused; lake runs one process per store root.
- `spec.billing`, a typed switch for `LAKE_BILLING` that `spec.payments` requires.
- The Lake's default Zetta is the v0.3.0 release, pinned by digest; set files can pin
  `spec.services.zettaImage` to keep workspace Zettas on an earlier image.
- The default MCP runner image is pinned by digest.
- The manager's start-up memory is bounded: Go's limit from the container, no Helm release Secrets
  in the cache.
- The management cluster's helmfile names the CloudNativePG release `cnpg`; the platform sync test
  compares release names.
- Lake's schema vendored at v0.4.0, through `0093_root_recovery_participants`.

## Before upgrading

Each needs doing before or with the upgrade.

- **serverless-redis-http shim:** the shim's image must be pullable before the upgrade, or the
  shim pulls nothing and the stack is not Ready.
- **Third-party keys:** a Cloud v1 set's LLM key Secret must hold non-empty keys; the cluster-row
  Job re-runs once on each control DB.
- **HPES:** the HPES image must exist and be pinned in the set files before the upgrade; 7Gi and
  2 CPU per stack.
- **Datastore users:** roll to a nonprod stack first and confirm the dashboard never writes the
  four operator-owned tables.
- **Sandbox authentication refused in production:** a production member with no dashboard
  environment goes `Ready=False`, and the steps after the dashboard stop on it.
- **Stripe restricted key:** rolls only with the restricted key, its Secret and the set edit.
- **No production credential in nonprod:** the nonprod Secrets must exist and the nonprod set files
  be applied right after the upgrade, or the nonprod sets go `Degraded`; a nonprod pilot migration
  becomes `Blocked`.
- **Production pull Secret:** a nonprod pull Secret and the nonprod `operator.yaml` must be applied
  after the upgrade.
- **Default Zetta image:** apply set files that pin `spec.services.zettaImage` before the operator
  release rolls, or workspace Zettas follow the new default.
- **App rows and Kubernetes Secrets:** before the upgrade, check the Lakes for legacy
  `secret_env_refs` rows.
- **Custom domains:** before the upgrade, read the live custom-domain rows for hosts under platform
  zones.
- **Real client IP:** ingress-nginx restarts on every cluster at the upgrade.
- **Admission webhooks and snippets off:** applying the values restarts the ingress-nginx pod on
  each cluster (seconds of errors with a single replica).
- **Authorization and Cookie cleared on app Ingresses:** tenant apps no longer receive
  `Authorization`; takes effect only when the platform values are applied (the management cluster's
  helmfile, the leaves' `ClusterHelmRelease`).
- **Methodology ceiling:** every Lake gets methodology-ceiling with the defaults (64 CPU, 256Gi,
  8 GPU, 500 pods, 200 PVCs); confirm they suit your Lakes.
- **Advanced Certificate:** needs Advanced Certificate Manager on the zones and SSL and
  Certificates > Edit on the tokens; until then it only sets a condition.
- **Zetta join token as a file:** every Zetta StatefulSet rolls once at the upgrade.
- **Lake Zetta egress:** every Lake-owned Zetta restarts once, and must roll before a Zetta image
  that enforces `ZETTA_EGRESS_ALLOW`. An egress change restarts that workspace Zetta; DNS-name
  rules do not yet work for Zetta.
- **Mesh agent keys:** mesh agents on every cluster restart once.
- **`APP_AUTH`:** every `LakeApp` pod restarts once; must roll before an app-runtime image that
  reads it.
- **MCP runner pinned by digest:** every Lake restarts at the upgrade (env change, Recreate on its
  volume).
- **Deployment API on TLS:** the manager pod mounts a cert-manager Secret and restarts once; any
  client using the admin token or plain HTTP breaks.
- **Peer gateways:** every Lake-created peer gateway is replaced once at the upgrade (short drop); a
  credential read error tears the gateway down by design.
- **Lake e2e gate:** the Lake e2e image must exist before the gate is turned on.
- **Backups:** apply the CRDs before the manager; the first real backup needs a bucket with
  credentials, a token that can mint tokens, and ClickHouse egress to R2.

## What it does not include

Everything under [v0.7.1](v0.7.1.md)'s *does not include*. Also held for a planned rollout or a
decision, not in this release: installing by SHA-256, AKS access through workload identity, a
manager that writes only in labelled namespaces, split Lake database credentials, zone-level
authenticated origin pulls, the base model on workspace Zettas, and service launch tokens.

## Known issues

The management cluster's own operator and platform charts are still installed by a helmfile run by
hand.
