# v0.11.3

**Released:** 2026-10-30 · **Branch:** `main` · **Previous:** [v0.11.2](v0.11.2.md) (2026-10-30).

A patch release: **kube-prometheus-stack no longer raises `KubeCPUOvercommit` and `KubeMemoryOvercommit`** on any
cluster. Both fire when the pods' requests would not fit with the largest node gone. A cluster that autoscales its pools
instead of holding a spare node fires them all the time, so alerts were posted every few hours for a state that is
normal and intended.

## What it includes

- `defaultRules.disabled` turns off `KubeCPUOvercommit` and `KubeMemoryOvercommit`, set the same way in `helmfile.yaml`
  and every leaf's `config/clusters/*/platform.yaml`, with a comment beside it saying why.
  [observability.md](../infrastructure/observability.md) lists which default rules are off. A pod that cannot be placed
  after a node is lost still pages, as `KubePodNotReady` after 15 minutes, and the `v1` stack's own rules stay on.
  `KubeCPUQuotaOvercommit` and `KubeMemoryQuotaOvercommit` (namespace quotas) stay on.

## What it does not include

- Any change to requests, limits, node pools or autoscaler bounds. CPU requests are well above use; right-sizing them is
  a separate change.
- Pixie itself.

## Upgrading

- No CRD changes. The CRD rollout ([crd-rollout.md](../operations/crd-rollout.md)) runs as for any release and changes nothing.
- **The platform values:** the leaves take them when their `ClusterHelmRelease`s are applied from
  `config/clusters/*/platform.yaml`; the managing cluster with `helmfile sync -l name=kube-prometheus-stack`. Only the
  `PrometheusRule` holding the two rules changes; Prometheus reloads its rules without restarting.
- **What rolls on each cluster with the operator:** the operator, and the zetta-tunnel mesh pods, which carry a container
  from the operator image. No Lake or Cloud v1 workload changes.
