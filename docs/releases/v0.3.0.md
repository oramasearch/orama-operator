# v0.3.0

**Released:** 2026-10-17 · **Branch:** `main` · **Previous:** [v0.2.0](v0.2.0.md) (2026-10-14).

v0.3.0 is **secure networking** and **regions**. Every managed workload now runs inside an
owner-scoped `NetworkSandbox`, and only the operator writes network policy. Lake declares the paths
a workspace may use (`Connection`, `EgressRule`, `Tunnel`, `PeerConnection`), and zetta-tunnel
carries the ones a policy cannot: the egress gateway, developer tunnels, peer gateways, an ingress
gateway and a mesh agent on every node. A `LakeSet` can now run one Lake per region, with a region
picker at an apex host (decision 64), and the nonprod set gains a `testing` environment.

Everything in [v0.2.0](v0.2.0.md) is still here. This page lists what is new or changed, and ends
with the full list of resource kinds.

## 1. Network sandboxes and policy

- **`NetworkSandbox`**: every managed workload gets an owner-scoped sandbox, a mandatory ingress and
  egress policy that allows only what its owner declares (#478, decision 48).
- **Only the operator writes network policy.** RBAC denies tenants every policy kind, and a
  repository audit counts wildcard grants (#484, decision 49).
- **Cloud metadata endpoints are blocked** in every sandbox (#482).
- **Orama Cloud v1's engines reach only their broker, DNS and the public internet** (#480).

## 2. Declared connections and credentials

- **`Connection`**: Lake's `network_connections` rows become declared paths between a workspace's
  workloads and its services, replacing blanket workspace reachability (#485, decision 50).
- **A credential-scoped `Connection` gets its own Postgres role**, delivered as a workspace secret
  (#487, decision 51).

## 3. Egress, tunnels and peers

- **`EgressRule`**: outbound by address through policy, and by DNS name only through zetta-tunnel's
  egress gateway (#491, decision 52).
- **`Tunnel`**, with providers **`TunnelProvider`**, **`ZettaTunnel`** and a customer's own
  **`CloudflareTunnel`**: developer access into a workspace (#489, decision 53). A tunnel resolves a
  Service's named target port from its pods (#509).
- **`PeerConnection`** through zetta-tunnel peer gateways, with credentials only through a
  cluster-scoped **`PeerLink`** minted on the managing cluster (#490, decision 54).
- **zetta-tunnel runs at `v0.1.0`** (#510).

## 4. The zetta-tunnel ingress gateway and mesh

- **The ingress gateway** runs on every cluster (namespace `zetta-tunnel-ingress`). An Ingress
  moves to it by its class (`ingressClassName: zetta-tunnel` on `Lake`, `OramaCloudV1` and
  `OramaZettaCluster`); ingress-nginx stays until every cluster is cut over (#493, decision 55). No
  cluster has been cut over: every Ingress is still class `nginx`, so the gateway runs zero
  replicas, as designed.
- **The mesh agent** runs as a DaemonSet on every node (namespace `zetta-tunnel-mesh`), with the
  operator's credential-free `mesh-projector`. Nothing is enrolled by default
  (`NetworkSandbox.spec.mesh.enrolled`) (#494, decision 56).
- **Lake's schema 0084 and 0085** are vendored: the network desired-state and status tables and the
  tunnel CA fields (#495).

## 5. Regions and the apex host

Decision 64 (https://github.com/oramasearch/liquid-bridge/issues/39): production Lake runs one Lake
per region, each at its own host, with a region picker at an apex host (`lake.live` in front of
`eu.lake.live` and `us.lake.live`). One `LakeSet` manages every region (#512, #516).

- **`Lake.spec.region`** (`name`, `label`), **`spec.regions`** (the picker's list) and
  **`spec.apexHost`**, given to the Lake as `LAKE_REGION`, `LAKE_REGION_LABEL`, `LAKE_REGIONS` and
  `LAKE_APEX_HOST`.
- **`apexHost`** adds a second rule (and TLS host) to the Lake's Ingress and an owned proxied
  `<lake>-apex-dns` record; removing it removes both.
- **A `LakeSet` member** that states a region label gets its cluster's region as `region.name` (a
  different stated name is refused) and the set's region list, with each region's location from
  `cloudRegionLocations`. A labelled member with no host, a region with no known location, a list
  stated by hand or a second apex host refuses the whole set.
- **Members that state no region are unchanged**, so this release changes nothing on the running
  sets until a set file states regions.

Detail: [`docs/lake/README.md#regions`](../lake/README.md#regions). Lake's picker is
https://github.com/oramasearch/lake/issues/757; moving `lake-prod` to `lake.live` is #513.

## 6. Environments and clusters

- **`lake-nonprod` has three environments**: `dev`, `testing` and `staging`, at
  `lake-<name>.oramadev.net` on `orama-nonprod-cluster-01` (#517, #518). Nonprod stays on
  `oramadev.net`; production is `lake.live` (decision 64).
- **Every leaf runs this release**, by `OramaOperator` `version: v0.3.0` in
  `config/clusters/*/operator.yaml`.

## 7. Fixes

- The manager starts when it owns Namespaces it cannot list: every Namespace read is uncached, and a
  test holds it (#496, #497).
- A service's target is found from its primary resource, not a label its pods lack (#498).
- Lake is read with GET, and no headless Service port is opened to a connection (#499).
- A watch handler never changes the cached object it is given (#500).

## What `v0.3.0` does **not** include

- **Lake's region picker.** The operator supplies the region data; Lake shows nothing with it until
  https://github.com/oramasearch/lake/issues/757 ships.
- **`lake.live` in production.** `lake-prod` still serves `lake-eu.oramadev.net` and
  `lake-us.oramadev.net` (#513).
- **Any cluster cut over to the zetta-tunnel ingress gateway**, and any workload enrolled in the mesh.
- **Geo load balancing, connected multi-region Zetta and one sign-in across regions**
  (https://github.com/oramasearch/liquid-bridge/issues/40).
- **A self-managed management cluster**: `orama-production-cluster-01` is still rolled by a script.

## Known issues

- **Security: no Ingress has TLS to the origin** (#457), carried from v0.2.0. Required before
  go-live.
- **Security: the Cloudflare DNS controller may adopt, change or delete records it did not create**
  (#312). Relevant to the apex host and to moving `lake-prod` to `lake.live`.
- **Security: a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller**
  (#280).
- **Security: generated broker and Redis passwords** (#307) and **Prod 1's hooks deny list as fixed
  values** (#306) are open for the Orama Cloud v1 migration.
- **Regions and the apex host are not yet proven on a live Lake.** Unit tests and a server dry-run
  of the CRD pass; the live proof on `lake-nonprod` is #520 and runs against this release.
- **ingress-nginx is retired upstream**; the zetta-tunnel gateway replaces it per cluster (#437).
- A Kafka service in a workspace does not start under restricted Pod Security (#428); every service
  kind's sizing and metering is #435.
- Leftover test resources on the management cluster (#168).

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.3.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
