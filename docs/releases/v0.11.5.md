# v0.11.5

**Released:** 2026-10-31 · **Branch:** `main` · **Previous:** [v0.11.4](v0.11.4.md) (2026-10-30).

A patch release: **Pixie's release is committed**, so the observability hubs and agents can install. Until now every
`ObservabilityHub` and `ObservabilityAgent` stayed `Pending` on `ObservabilityProvider pixie does not exist`, which is why
`ObservabilityAgentNotReady` and `ObservabilityHubUnreachable` kept firing for the production clusters.

| CRD changes | none |
| Operator code | none (one new test) |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

- [`config/clusters/observability-provider.yaml`](../../config/clusters/observability-provider.yaml): the
  `ObservabilityProvider` `pixie`, built from Pixie at the vendored commit `4b445e0b7907` plus Pixie's build patches
  `0001`–`0004`: Vizier `0.14.16-pre-orama.1`, Cloud `0.1.10-pre-orama.1`, CLI `0.8.9-pre-orama.1`, and 27 images, each
  in a private registry repository pinned by digest (the 8 dependency images are mirrors with their upstream's digest).
  The build patches `0002` (every image named `pixie-*`), `0003` (143 Go licences recorded, so the build does not depend
  on pkg.go.dev) and `0004` (the UI bundle's stamp values quoted for Bazel 7), and the build recipe that made the
  release.
- `TestCommittedPixieReleaseIsInstallable` fails when the operator's Pixie commit or image keys move away from the
  committed release.
- The sample drops `cloud-plugin-load-db`, a key the operator refuses.

## What it does not include

- Any change to the operator's code, the hubs, the agents or the platform charts.
- Pixie had not run on a cluster before this release ([observability.md](../infrastructure/observability.md)).

## Upgrading

- No CRD changes. The CRD rollout ([crd-rollout.md](../operations/crd-rollout.md)) runs as for any release and changes nothing.
- **The provider is applied to the managing cluster** from `config/clusters/observability-provider.yaml`. Once it exists,
  every hub and every agent installs at once: there is no setting that holds production back while nonprod goes first.
- **What rolls on each cluster with the operator:** the operator, and the zetta-tunnel mesh pods, which carry a container
  from the operator image. No Lake or Cloud v1 workload changes.

## Known issues

- Unchanged from [v0.11.1](v0.11.1.md#known-issues).
- A production hub requests about 1.8 CPU and 7 GiB; a single-node managing cluster needs that much free.
