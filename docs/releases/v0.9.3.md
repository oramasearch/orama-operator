# v0.9.3

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.2](v0.9.2.md) (2026-10-24).

A patch so **a Cloud v1 stack can replace a volume it cannot change in place**, which `v1-eu`'s move
to premium production storage needs
([#922](https://github.com/oramasearch/orama-operator/pull/922)), plus the cluster files since v0.9.2.

> **Read [Before it rolls](#before-it-rolls).** `approveDataDeletion: true` erases a volume's data by
> design.

## Changes

| PR | Change |
|---|---|
| [#920](https://github.com/oramasearch/orama-operator/pull/920) | Every Cloud v1 component's `storage` (writer, reader, analytics, broker, cache, search, controlDB and the new `ingestion.harvestMongoStorage`) takes `approveDataDeletion`. `false` (the default) never erases data: a volume that cannot reach its declared class or size stays, and `StorageApplied` says why. `true` replaces such a volume, deleting it and the workload using it and creating them again from the spec, while the stack is held at `ReplacingStorage`. A larger declared `size` still grows a volume in place. Only declared values count. HARVEST's Mongo gets the same `storage` as every other store (#915) |

## Before it rolls

- **`approveDataDeletion: true` erases data by design.** Nothing in the committed files sets it until
  #922, which is applied separately, with Steve's consent, after this operator runs on cluster-02.
  Set it back to `false` before any customer data is copied.
- The new fields are additive; a stack that does not set them behaves as before.
- Rolling needs Steve's consent: the managing cluster by its script, then every leaf's
  `operator.yaml` in one command.
