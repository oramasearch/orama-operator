# v0.9.3

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.2](v0.9.2.md) (2026-10-24).

A patch so **a Cloud v1 stack can replace a volume it cannot change in place**, for example to move a
stack onto a different storage class.

> **Read [Before it rolls](#before-it-rolls).** `approveDataDeletion: true` erases a volume's data by
> design.

| Measured | Value |
|---|---|
| Resource kinds | 48 CRDs in `chart/crds` (unchanged); `OramaCloudV1` gains `storage.approveDataDeletion` on every component and `components.ingestion.harvestMongoStorage` |
| Lake schema | unchanged: lake v0.5.0 (`9c7c2fc7`), through `0098_authentication_attempts` |
| Tests | see [Verification](#verification) |

## Changes

- Every Cloud v1 component's `storage` (writer, reader, analytics, broker, cache, search, controlDB and
  the new `ingestion.harvestMongoStorage`) takes `approveDataDeletion`. `false` (the default) never
  erases data: a volume that cannot reach its declared class or size stays, and `StorageApplied` says
  why. `true` replaces such a volume, deleting it and the workload using it and creating them again from
  the spec, while the stack is held at `ReplacingStorage`. A larger declared `size` still grows a volume
  in place. Only declared values count. HARVEST's Mongo gets the same `storage` as every other store.

## Before it rolls

- **`approveDataDeletion: true` erases data by design.** Set it only for the replacement, and set it
  back to `false` before any data you need is written to the stack.
- The new fields are additive; a stack that does not set them behaves as before.
- Roll the managing cluster's operator first, then every leaf's `OramaOperator`.
