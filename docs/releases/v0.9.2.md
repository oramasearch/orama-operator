# v0.9.2

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.1](v0.9.1.md) (2026-10-24).

A patch so **lake can reach its Zettas again**: the lake Deployment gets its own `ZETTA_EGRESS_ALLOW`.
Everything in v0.9.1 is unchanged.

> **Read [Before it rolls](#before-it-rolls).** It pairs with the lake build carrying

## Changes

| PR | Change |
|---|---|
| PR_NUMBER | **The lake Deployment gets `ZETTA_EGRESS_ALLOW=*.svc.cluster.local`**, reserved so `spec.env` cannot replace it. lake v0.5.0 was built against zetta v0.5.0, whose client refuses every connection but loopback until a policy is installed, and lake reached no Zetta on `dev` ([lake#1097](https://github.com/oramasearch/lake/issues/1097)). With [lake#1100](https://github.com/oramasearch/lake/pull/1100), lake installs the variable as that policy. It covers what lake dials through zetta's client, all in the cluster: the bus Zetta and the workspace Zettas (4800), agent services and service wrappers (8080). Workspace namespaces are made at runtime, so they are matched by suffix; the namespace's NetworkPolicy still decides which in-cluster services lake reaches ([`../lake/README.md`](../lake/README.md)) |

## Before it rolls

- **Roll it before the lake build with lake#1100.** On lake v0.5.0 as released the variable changes
  nothing, because that build never installs a policy; on lake v0.4.0 it is ignored.
- **Each Lake restarts once** when the variable appears in its Deployment.
- Rolling needs Steve's consent: the managing cluster by its script, then every leaf's
  `operator.yaml` in one command.
