# v0.6.0

**Released:** 2026-10-17 · **Branch:** `main` · **Previous:** [v0.5.0](v0.5.0.md) (2026-10-17).

v0.6.0 is **the Cloud v1 engine reachable and kept, for the migration**: the next operator step of
the Cloud v1 migration ([orama-bridge#137](https://github.com/oramasearch/orama-bridge/issues/137)).
The writer verifies the dashboard's write tokens; the writer and readers can be published on public
hosts, with extra names on any public Ingress and `/metrics` closed to the internet; each reader is a
StatefulSet pod with its own disk; readers record search events with a dedicated analytics key, and
a scheduled import pulls them into ClickHouse, which keeps 30 days; a new control database gets the
`c1` cluster row from the operator. `engine.reader.hpa` is removed. `v1-prod.yaml` carries `v1-eu`'s
production values, not applied.

Everything in [v0.5.0](v0.5.0.md) is still here. This page lists what is new or changed.

## 1. Writer verifies write tokens

#414, issue #384, decision 71.
- **New fields** `spec.jwtIssuer` and `spec.components.engine.writer.jwt {jwksURL, audiences[]}`.
  The writer renders one `dashboard` JWT provider under `writer_side.jwt` (combined and writer-only
  configs, never reader-only). The JWKS URL defaults to the dashboard Service in the same namespace,
  so key fetches do not depend on public DNS; the network sandbox opens writer to dashboard TCP 3000
  only while that default is in use.
- `spec.jwtIssuer` is the one source of the issuer for the dashboard and the writer. It has no
  default: `engine.writer.jwt` refuses an empty issuer. A configuration that would reject every write
  fails the reconcile before the engine changes.
- The writer rolls through its config hash and the dashboard through `orama.cloud/jwt-issuer-hash`.
  A lost `<cr>-jwt-pub` is recovered from `<cr>-jwt` without rotating the pair. No Firebase field.

## 2. Public writer and reader hosts

#417, issue #385, decision 72.
- **New fields** `spec.components.engine.writer.host` (primary region only) and
  `spec.components.engine.reader.host`. Each published host gets an owned Ingress (`<cr>-writer` to
  `:8080`, `<cr>-reader` to `:80`) with origin TLS, a sandbox rule admitting only ingress-nginx to that
  stack's writer or reader pods, and, with Cloudflare DNS managed, a proxied create-only
  `CloudflareDNSRecord`.
- With `writer.jwt` set, `https://<writer.host>` must be exactly one of the audiences, or the
  reconcile fails.
- The operator never adopts or deletes an object it does not control. A host change deletes the old
  child, whose finalizer removes the old Cloudflare record, and creates a fresh one. Every host must be
  in the token Secret's zone.

## 3. Extra hosts

#418, issue #313, decision 73.
- **New field** `extraHosts` on `dashboard`, `docs`, `oramasearchApp`, `engine.writer` and
  `engine.reader`: more names on the same Ingress, routed to the same backend, each with its own
  origin certificate and `<host>-tls` Secret.
- Only `host` gets a `CloudflareDNSRecord`; an extra host never gets one. Duplicate names across the
  five components are refused.

## 4. `/metrics` closed on public hosts

#410, issue #314, decision 74.
- Envoy answers `/metrics` with 404 on the readers, by a route before its catch-all; a new Envoy
  bootstrap rolls the readers only.
- Each public engine Ingress has a deny-all companion, `<cr>-writer-metrics` / `<cr>-reader-metrics`,
  answering 403 for `/metrics` on the main host and every extra host. Inside the cluster the endpoint
  stays on each pod's `:8080`.
- No Sentry and no Prometheus scrape annotations: in-cluster monitoring is #15.

## 5. Readers on their own disks

#550, issue #382, decision 75.
- Readers are the StatefulSet `<cr>-reader` (headless Service `<cr>-reader-headless`, `Parallel`),
  with one `ReadWriteOnce` `data` claim per reader at `/app/.data`, so a replaced reader resumes from
  its own stream offset.
- **New field** `spec.components.engine.reader.storage {size, storageClassName}`: 10Gi on the
  cluster default class by default, grown by the operator as the writer's is. `v1-prod.yaml` sets
  512Gi.
- `reader.replicas` (default 3) is fixed on every reconcile; no autoscaler. Claims are kept on
  scale-down and on deletion.
- **Rolling this operator replaces each Cloud v1 reader Deployment with the reader StatefulSet**:
  the owned Deployment is deleted before the StatefulSet is created, so the readers are down during
  the switch (see [Known issues](#known-issues)).

## 6. Reader analytics key

#419, issue #386, decision 76.
- The reader-only config renders `reader_side.analytics` with Prod 1's `metadata_from_headers` and
  `api_key` from `<cr>-analytics-api-key`, generated once on every stack.
- The analytics processor gets that key, never the master key, and its ClickHouse password and
  control-database URI by `secretKeyRef`.

## 7. Scheduled analytics import and 30-day retention

#421, issue #388 (folds in #315 and #444), decision 77.
- **New field** `spec.components.analyticsProcessor.import {enabled, suspend}`. With `enabled`, the
  operator owns the CronJob `<cr>-analytics-import`: every five minutes (UTC, `Forbid`), `POST
  /import` and then `POST /aggregate2`. Its sources are exactly the reader ordinals
  `0..replicas-1` through `<cr>-reader-headless`, so each reader is pulled once. `suspend` keeps it
  off until the cutover. Its curl image takes `spec.images.overrides["analytics-import"]`.
- The operator-owned Job `<cr>-analytics-retention` sets a 30-day TTL on the processor's ClickHouse
  tables.
- The functional e2e suite no longer calls `GET /v1/analytics`, which would drain the readers.

## 8. The `c1` cluster row

#447, issue #443, decision 78.
- Once every control-DB `PostgresSchema` is current and the master key is valid, the operator owns
  the Job `<cr>-controldb-cluster-row`. In one transaction, under a table lock, it inserts the
  `oramacore_clusters` row `c1` (`https://<engine.writer.host>`, `https://<engine.reader.host>`, the
  master key) **only when the table has no row at all**. It never updates or deletes a row.
- **It waits for both public hosts**: with either `engine.writer.host` or `engine.reader.host` unset,
  no row is written.
- A failed Job is replaced five minutes after its failure. Condition `ClusterRowReady` reports it
  without changing the phase.
- The Job and the schema Jobs run `spec.images.overrides.postgres-client` (default
  `postgres:16-alpine`). **New field** `PostgresSchema.spec.imagePullSecrets`, so that image can be
  private; `OramaCloudV1` passes its `spec.images.pullSecretName`.

## 9. `engine.reader.hpa` removed

#608, issue #606.
- `spec.components.engine.reader.hpa` and `HPASpec` are gone: since #550 readers have a fixed count,
  and the field was accepted and ignored. No committed set or sample sets it, and no `OramaCloudV1`
  or `OramaCloudV1Set` on any cluster held it (read-only check, 2026-10-17).
- The operator's `horizontalpodautoscalers` RBAC is removed (kubebuilder marker and chart).
- The removal is named in `cmd/crd_field_removal_test.go`. Roll with the usual CRDs widened first,
  exactly after ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)).

#609 moved every upstream default image to an exact version tag and #610 reverted it (Steve,
2026-10-17: *"we don't need exact version tags"*). Together they change nothing.

## 10. Environments and clusters

- **Leaves on v0.5.0** (#605): `config/clusters/*/operator.yaml` pin every leaf to `v0.5.0`. They
  move to `v0.6.0` in a separate change, rolled with Steve's consent (see [Where it runs](#where-it-runs)).
- **`v1-nonprod`** (`config/clusters/sets/v1-nonprod.yaml`): `v1-dev` gets `reader-dev` and
  `writer-dev.oramadev.net`, the writer audience, `jwtIssuer: https://app-dev.oramadev.net`, the
  dashboard extra host `app-alias-dev.oramadev.net`, and the analytics import enabled and suspended.
- **`v1-prod`** (`config/clusters/sets/v1-prod.yaml`, #445): `v1-eu`'s production values (public
  hosts, the writer audience, Prod 1's LLM providers and master key, two readers, storage sizes on
  Premium SSD with the reader at 512Gi, the dashboard crons and the analytics import enabled but
  suspended) and a header classifying every Secret and listing what still blocks the first apply.
  `v1-us` keeps its sandbox values plus the master-key reference. **Not applied**: applying it needs
  Steve's consent and the items in its header.

## Known issues

Security first.

- **Security: hostnames that resolve to private IPs pass the hooks deny list.** The list matches
  host names and literal addresses, not where a name resolves; the network lockdown is #437.
- **Security: the generated broker and Redis passwords have no rotation** (#594).
- **Security: `CloudflareTunnel` still adopts and overwrites a CNAME found by name** (#585).
- **Security: Lake, LakeApp, LakeEnvironment and Zetta Ingresses have no TLS to the origin**; #578
  was closed as not planned, without a comment. Cloud v1's Ingresses have it.
- **Security: a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller**
  (#280), and **apps can reference arbitrary Secrets in the Lake namespace** through legacy
  `secret_env_refs` (#492). Both unchanged.
- **Cloud v1 readers are not Ready** until the sets run a reader image serving `GET /health/ready`
  (oramacore#340 and #341); the images are #597.
- **Rolling this operator replaces each Cloud v1 reader Deployment with the reader StatefulSet**, so
  the readers are down during the switch, and each new reader starts on an empty disk and replays the
  stream. The Kubernetes Cloud v1 environments (`v1-dev`, `v1-eu`, `v1-us`) serve no one until the
  migration.
- **`v1-dev`, `v1-eu` and `v1-us` are held at 0 engine replicas** until their sets name a master key
  (`masterAPIKeySecretRef`, from v0.5.0).
- **`config/clusters/sets/v1-nonprod.yaml` names Secrets that do not exist yet** on the managing
  cluster (#595), and **`v1-prod.yaml` names four** (`v1-prod-master-api-key`, `v1-prod-llm-keys`,
  `v1-prod-dashboard-env`, `v1-us-master-api-key`; #607). Neither file can be applied until they
  exist.
- **The `v1-dev` live proofs of the merged Cloud v1 changes are owed** (#590).
- **The managing cluster is not managed by a resource** (#593): rolling it is a script with Steve's
  consent.
- **The default Zetta image is still `main-4015ef76`** (#588).
- **Images not built yet:** the Lake end-to-end runner `oramasearch/lake-e2e` (#589) and the canary
  `oramasearch/oramacore-test-e2e` (#596).
- **Graceful shutdown and Kubernetes-practice gaps** across the operator's workloads
  ([orama-bridge#197](https://github.com/oramasearch/orama-bridge/issues/197)).
- Unchanged from v0.5.0: the temporary `Lake/prod` on `lake.oramadev.net` (#536), the zetta-tunnel
  ingress gateway never serving Cloud v1 (#575), a workspace Kafka service under restricted Pod
  Security (#428), and leftover test resources on the management cluster (#168).

- `TestControlDBSchemasAgainstPostgres` (`CONTROLDB_SCHEMA_TEST_POSTGRES_URI`): passed, 5 of 5 cases

  `CONTROLDB_TEST_POSTGRES_URI`): passed. On the vendored dashboard schema, a failed run changes
  nothing and its retry inserts the row; an empty table gets exactly the `c1` row with the writer URL
  and the key; a second run, and a table holding any other row, are left unchanged.

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.6.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
