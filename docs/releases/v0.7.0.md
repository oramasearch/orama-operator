# v0.7.0

**Released:** 2026-10-20 · **Branch:** `main` · **Previous:** [v0.6.2](v0.6.2.md) (2026-10-19).

v0.7.0 adds **two families of kinds**: the payment kinds, with which the operator keeps an app's
Stripe webhook endpoint and catalog from committed resources, and `LakeOrderSource`, with which a
management cluster provisions paid Lake orders from lake's control plane. It also lets the Cloud v1
cluster-row Job through the network sandbox, so a stack gets its `c1` row and can create projects,
and moves the vendored Lake schema to lake v0.3.0.

**Nothing in it is used on a cluster until a resource names it.** No set file, `Lake` or
`OramaCloudV1` in `config/clusters/` declares a payment kind or a `LakeOrderSource`. What changes
on every cluster when this version rolls is the cluster-row admission and the Lake schema (0089).

Everything in [v0.6.2](v0.6.2.md) is still here. This page lists what is new or changed.

## 1. Payments: Stripe from committed resources

Design and cautions: [`docs/infrastructure/payments.md`](../infrastructure/payments.md). Each family
is a provider resource, an abstract kind and a concrete Stripe kind, so another vendor is a new
concrete kind under the same abstract ones.

- **`PaymentProvider`** names a Stripe account or sandbox, its mode, and the Secret with the
  operator's restricted key. It checks the key's prefix against the mode, then that
  `GET /v1/account` returns the declared account, and reports the result in `Credentials`; it
  rechecks hourly and writes nothing to Stripe. The operator key needs *Accounts: Read*,
  *Products: Write*, *Prices: Write* and *Webhook Endpoints: Write*; with them the result is
  `Verified`. A key without *Accounts: Read* reports `ModeVerified` (the mode is proved, the account
  id is not), which means the permission should be added.
- **`PaymentWebhookEndpoint` → `StripeWebhookEndpoint`** keeps one Stripe webhook endpoint per app
  per host. It creates the endpoint and writes its one-time signing secret to a Secret it owns,
  repairs drift (URL, events, a disabled endpoint), replaces the endpoint when the Secret is lost or
  the API version changes, and deletes it in Stripe through a finalizer. It adopts only endpoints it
  tagged (`orama_managed`, `orama_owner`); one at the same URL that is not its own is `URLTaken`.
- **`PaymentCatalog` → `StripeCatalog`** keeps an app's products and prices. It reads everything
  before writing, refuses objects that are not its own (`ProductTaken`, `PriceTaken`), and a catalog
  older than the one that last wrote a product stands down (`Superseded`). Stripe prices cannot
  change, so a changed price is a new one that takes over the lookup key, and the old one is
  archived. Nothing is ever deleted, and there is no finalizer. A price is a flat amount in one
  currency, one-time, monthly or yearly. **A `cloud_v1` catalog on a live-mode key is refused**
  (`LiveModeRefused`) before any Stripe request.
- **The Stripe client** (`internal/controller/stripe_api.go`): deterministic form encoding,
  idempotency keys that name exactly one request and move on after every answered write, and
  errors with any key-shaped text redacted. Its `Stripe-Version` is `2024-06-20`, Lake's; the
  operator reads only fields whose shape is the same across the account default, Lake's version and
  the dashboard's, and the pin changes only with a test for every field it reads. A webhook endpoint
  uses its own `apiVersion`, so the payloads the apps parse are unaffected
  ([API versions](../infrastructure/payments.md#api-versions)).
- **What uses them:** nothing yet. `Lake.spec.payments` and Cloud v1's payments are not built.
  Lake's prices stay in Lake's own price list; a catalog is for product IDs and Cloud v1's sandbox
  prices.

## 2. Paid Lake orders: `LakeOrderSource`

Design, the rejected alternatives and the open questions:
[`docs/infrastructure/orders.md`](../infrastructure/orders.md).

- A cluster-scoped `LakeOrderSource` on the management cluster names the `LakeSet` whose Lakes take
  orders. On each pass it reads every member's `cloud_orders` through that member cluster's admin
  kubeconfig and a port-forward through its API server to the CNPG primary: no database is exposed
  and no credential copied.
- **A `paid` order is claimed once**, by one guarded statement that writes its event row too.
  `claimed_by` names the source, so a restart resumes the orders it holds.
- **`private_warehouse`** becomes a one-member `LakeSet` on the set's cluster in the ordered region.
  **`dedicated_cluster`** (Azure) becomes a `KubernetesCluster` with copies of the template cluster's
  `ClusterHelmRelease`s and `OramaOperator`, and the `LakeSet` on it. A Ready set makes the order
  `ready` with its host. An order that cannot be provisioned as written becomes `failed` with a
  reason.
- **Placed and copied once**: a dedicated cluster is copied from the template when it is made and
  never follows the template afterwards, and a private warehouse stays on the cluster it was placed
  on.
- Ordered resources come from the rows, not from `config/clusters/`; they carry the order id label,
  say `Retain`, and are never deleted.

## 3. Cloud v1: the cluster-row Job reaches the control DB

- **What was wrong.** The cluster-row Job (v0.6.0) inserts the stack's `c1` `oramacore_clusters`
  row, without which the dashboard cannot create a project. Its pod matched no rule of the stack's
  default-deny sandbox, so it waited for the database forever, with `ClusterRowReady=False`.
- **What changes.** The Job's pod carries `orama.cloud/controldb-client=cluster-row`. A new
  `allow-controldb-cluster-row-egress` and an added rule on `allow-controldb-ingress` let that pod,
  of this stack only, reach the CNPG pods on TCP 5432.
- **On the roll** the Job's pod template changes, so its hash changes and the stuck Job is replaced
  on the next reconcile, with no step by hand.
- The sandbox test is now `TestNetworkSandboxAdmitsEveryControlDBClient`, built from the real Job
  builders, over the three schema Jobs and the cluster-row Job.

## 4. Lake's schema at lake v0.3.0

[`docs/lake/schema.md`](../lake/schema.md).

- `internal/controller/assets/lake-schema.sql` is lake **v0.3.0**'s `db/schema.sql`
  (`18a89c14f3ce2629090e9373e673cb450ab96911`, SHA-256
  `690e75b738deebb28b71214d84654d984a747bfb9a1a5f935f4befb9cd70871f`), through `0089_cloud_orders`:
  `cloud_orders`, `cloud_order_events` and `cloud_orders_guard`. The restore rehearsal's guard query
  counts `cloud_orders_guard` too.
- **Apply before lake v0.3.0 rolls.** The schema gate holds a lake image until its migrations have
  applied, so this operator version rolls first.
- The pin is a release tag. A pull request's branch is never pinned: lake records a migration by
  name only, so one changed after it was applied would drift silently. `0090_billing_contacts`
  follows once it merges into lake `dev`.

## Known issues

- **Deleting a `StripeWebhookEndpoint` waits for a working key.** With the key revoked or wrong,
  the finalizer waits until it works or its Secret is removed.
- **Before committing a live-mode endpoint**, read
  [the cautions](../infrastructure/payments.md#before-committing-a-live-mode-endpoint): deleting an
  endpoint resource (or its Lake or namespace) deletes the live endpoint; a lost signing Secret is a
  delete then a create, so events in between are missed; the owner tag names no cluster; the write
  counter is saved at the end of a reconcile; a renamed signing Secret leaves the old one behind.
- **Two catalogs listing one product with different prices in one account would archive each
  other's prices.** Lake's catalog has no prices, so Lake cannot hit it.
- **None of the payment kinds or `LakeOrderSource` had run against real Stripe or a real leaf**
  when this release was cut. The tests use a fake Stripe that keeps Stripe's idempotency rules, and
  a real Postgres for the order SQL.
- **Nothing upgrades a dedicated cluster after it is made.**
- Unchanged from v0.6.2: a zone token may lack Zone Settings Edit; Always Use HTTPS waits for
  regional wildcard coverage; the management cluster is not managed by a resource; the default
  Zetta image; the end-to-end images; the zetta-tunnel ingress gateway and Cloud v1; a workspace
  Kafka service under restricted Pod Security; leftover test resources from earlier builds.

## Verification

Run on the release branch, macOS arm64, Go 1.26, with the Kubernetes 1.30.3 envtest binaries and a
local Postgres:

```
go build ./...                ok
go vet ./...                  ok
gofmt -l .                    nothing listed
make manifests generate       no diff
helm lint chart               1 chart linted, 0 failed
go test ./... -count=1        ok   cmd, internal/controller, internal/crdrollout, internal/meshprojection:
  (LAKE_SCHEMA_TEST_POSTGRES=1,    787 test functions, 773 passed, 14 skipped, 0 failed (789 subtests passed)
   LAKE_ORDERS_TEST_POSTGRES=1)
```

Two opt-in groups ran against Postgres this time: the Lake schema tests (`TestLakeSchemaEnvtest`
applies lake v0.3.0's schema through 0089) and `TestCloudOrdersPgxStoreAgainstPostgres` (the order
claim, eight connections, one winner). The fourteen skipped are opt-in and were **not run**: twelve
need their own Postgres switches (`TestControlDBSchemasAgainstPostgres`,
`TestControlDBClusterRowAgainstPostgres`, `TestConnectionRolesAgainstPostgres` and nine
`*PgxStoreAgainstPostgres`), `TestEgressGatewayAgainstZettaTunnel` needs a zetta-tunnel binary, and
`TestLiveChartDownloadAndPrerequisiteCheck` needs `LEAF_LIVE=1` and a live cluster. The suite ran with
the version already at 0.7.0, so `TestReleaseVersionIsDocumented` passed against this page.

Each change was also proved on its own pull request, against the code before it: the cluster-row
case of `TestNetworkSandboxAdmitsEveryControlDBClient` fails without the sandbox fix, the two order
scenarios added in review fail without the placement fix, and
`TestStripeCatalogRefusesCloudV1InLiveModeAndAllowsLake` covers the live-mode refusal.

**After the upgrade, live:** each Lake's `controldb-schema-migrate` Job ran again and completed on
schema 0089, so lake v0.3.0 may roll; and a Cloud v1 stack's stuck cluster-row Job was replaced,
logged `cluster-row: inserted the c1 oramacore_clusters row`, and the stack reports
`ClusterRowReady=True`.

The image built from the tag is published as `oramasearch/orama-operator:v0.7.0` (there is no
`latest`), and the chart as `0.7.0` in `oramasearch/orama-operator-chart`.

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)). Before the upgrade,
  `make check-crds`, then the CRDs widened, the upgrade, and the CRDs exactly
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)): this release adds six CRDs.
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.7.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
