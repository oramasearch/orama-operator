# v0.7.0

**Released:** 2026-10-20 · **Branch:** `main` · **Previous:** [v0.6.2](v0.6.2.md) (2026-10-19).

v0.7.0 adds **two families of kinds**: the payment kinds, with which the operator keeps an app's
Stripe webhook endpoint and catalog from committed resources (epic
[orama-bridge#199](https://github.com/oramasearch/orama-bridge/issues/199)), and `LakeOrderSource`,
with which a management cluster provisions paid `lake.live` orders from lake's control plane
(#634). It also lets the Cloud v1 cluster-row Job through the network sandbox, so a stack gets its
`c1` row and can create projects (#648), and moves the vendored Lake schema to lake v0.3.0 (#656).

**Nothing in it is used on a cluster until a resource names it.** No set file, `Lake` or
`OramaCloudV1` in `config/clusters/` declares a payment kind or a `LakeOrderSource`, and none is
applied. What changes on every cluster when this version rolls is the cluster-row admission and
the Lake schema (0089).

Everything in [v0.6.2](v0.6.2.md) is still here. This page lists what is new or changed.

## 1. Payments: Stripe from committed resources

#650, #651, #652; issues #637 and #638. Design and cautions:
[`docs/infrastructure/payments.md`](../infrastructure/payments.md). Each family is a provider
resource, an abstract kind and a concrete Stripe kind (principle 10), so another vendor is a new
concrete kind under the same abstract ones.

- **`PaymentProvider`** names a Stripe account or sandbox, its mode, and the Secret with the
  operator's restricted key. It checks the key's prefix against the mode, then that
  `GET /v1/account` returns the declared account, and reports the result in `Credentials`; it
  rechecks hourly and writes nothing to Stripe. A restricted key that may not read the account is
  checked by listing webhook endpoints instead (`ModeVerified`: the mode is proved, the account id is
  not).
- **`PaymentWebhookEndpoint` → `StripeWebhookEndpoint`** keeps one Stripe webhook endpoint per app
  per host. It creates the endpoint and writes its one-time signing secret to a Secret it owns,
  repairs drift (URL, events, a disabled endpoint), replaces the endpoint when the Secret is lost or
  the API version changes, and deletes it in Stripe through a finalizer. It adopts only endpoints it
  tagged (`orama_managed`, `orama_owner`); one at the same URL that is not its own is `URLTaken`.
- **`PaymentCatalog` → `StripeCatalog`** keeps an app's products and prices. It reads everything
  before writing, refuses objects that are not its own (`ProductTaken`, `PriceTaken`), and a catalog
  older than the one that last wrote a product stands down (`Superseded`). Stripe prices cannot
  change, so a changed price is a new one that takes over the lookup key, and the old one is
  archived. Nothing is ever deleted, and there is no finalizer. A price is a flat amount in one
  currency, one-time, monthly or yearly.
- **The Stripe client** (`internal/controller/stripe_api.go`): deterministic form encoding,
  idempotency keys that name exactly one request and move on after every answered write, and
  errors with any key-shaped text redacted. Its `Stripe-Version` is `2024-06-20`, Lake's.
- **What uses them:** nothing yet. `Lake.spec.payments` (#639, #655) was sent back in review, and
  Cloud v1's (#640) is not built. Lake's prices stay in Lake's own price list (decision 56); a
  catalog is for product IDs and Cloud v1's sandbox prices.

## 2. Paid lake.live orders: `LakeOrderSource`

#635, issue #634, the operator half of
[lake#831](https://github.com/oramasearch/lake/issues/831). Design, the rejected alternatives and the
open questions: [`docs/infrastructure/orders.md`](../infrastructure/orders.md). Decision 80.

- A cluster-scoped `LakeOrderSource` on the management cluster names the `LakeSet` whose Lakes take
  orders. On each pass it reads every member's `cloud_orders` through that member cluster's admin
  kubeconfig and a port-forward through its API server to the CNPG primary: no database is exposed
  and no credential copied.
- **A `paid` order is claimed once**, by one guarded statement that writes its event row too.
  `claimed_by` names the source, so a restart resumes the orders it holds.
- **`private_warehouse`** becomes a one-member `LakeSet` on the set's cluster in the ordered region.
  **`dedicated_cluster`** (Azure) becomes a `KubernetesCluster` with copies of the template cluster's
  `ClusterHelmRelease`s and `OramaOperator`, and the `LakeSet` on it. A Ready set makes the order
  `ready` with its host. An order that cannot be provisioned as written becomes `failed` with a
  reason.
- **Placed and copied once** (review fix `319d1cd`): a dedicated cluster is copied from the template
  when it is made and never follows the template afterwards, and a private warehouse stays on the
  cluster it was placed on.
- Ordered resources come from the rows, not from `config/clusters/`; they carry the order id label,
  say `Retain`, and are never deleted.

## 3. Cloud v1: the cluster-row Job reaches the control DB

#649, issue #648.

- **What was wrong.** The cluster-row Job (v0.6.0, #447) inserts the stack's `c1`
  `oramacore_clusters` row, without which the dashboard cannot create a project. Its pod matched no
  rule of the stack's default-deny sandbox, so it waited for the database forever: on `v1-dev` from
  2026-10-19 23:36Z, with `ClusterRowReady=False`. It also blocked the test copy of a team into
  `v1-dev` ([orama-bridge#149](https://github.com/oramasearch/orama-bridge/issues/149)).
- **What changes.** The Job's pod carries `orama.cloud/controldb-client=cluster-row`. A new
  `allow-controldb-cluster-row-egress` and an added rule on `allow-controldb-ingress` let that pod,
  of this stack only, reach the CNPG pods on TCP 5432.
- **On the roll** the Job's pod template changes, so its hash changes and the stuck Job is replaced
  on the next reconcile, with no step by hand.
- The sandbox test is now `TestNetworkSandboxAdmitsEveryControlDBClient`, built from the real Job
  builders, over the three schema Jobs and the cluster-row Job.

## 4. Lake's schema at lake v0.3.0

#661, issue #656. [`docs/lake/schema.md`](../lake/schema.md).

- `internal/controller/assets/lake-schema.sql` is lake **v0.3.0**'s `db/schema.sql`
  (`18a89c14f3ce2629090e9373e673cb450ab96911`, SHA-256
  `690e75b738deebb28b71214d84654d984a747bfb9a1a5f935f4befb9cd70871f`), through `0089_cloud_orders`:
  `cloud_orders`, `cloud_order_events` and `cloud_orders_guard`. The restore rehearsal's guard query
  counts `cloud_orders_guard` too.
- **Apply before lake v0.3.0 rolls.** The schema gate holds a lake image until its migrations have
  applied, so this operator version rolls first.
- The pin is a release tag. A pull request's branch is never pinned: lake records a migration by
  name only, so one changed after it was applied would drift silently. `0090_billing_contacts`
  (lake#864) follows once it merges into lake `dev`.

## Known issues

Security first.

- **Security: a `cloud_v1` `PaymentCatalog` on a live-mode provider is not refused.** The docs forbid
  it (Cloud v1's live catalog belongs to Prod 1), but nothing stops one being committed; noted on
  #640.
- **Security: deleting a `StripeWebhookEndpoint` waits for a working key** (#663). With the key
  revoked or wrong, the finalizer waits until it works or its Secret is removed.
- Unchanged from v0.6.2, all security: authenticated origin pulls use Cloudflare's global
  certificate (#633); apps and environments of a Lake without a `dnsSecretRef` stay on HTTP (#632);
  hostnames that resolve to private IPs pass the hooks deny list (#437); the generated broker and
  Redis passwords and master key have no rotation (#594); `CloudflareTunnel` adopts a CNAME found by
  name (#585); a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller
  (#280); apps can reference arbitrary Secrets in the Lake namespace through legacy
  `secret_env_refs` (#492).
- **Payments, not settled** (#664): the Stripe API version `2024-06-20`; whether the restricted-key
  fallback, which does not check the account id, is acceptable
  ([orama-bridge#200](https://github.com/oramasearch/orama-bridge/issues/200)); and the endpoint
  lifecycle cautions: deleting an endpoint resource deletes the live endpoint, and a lost signing
  Secret is a delete then a create, so events in between are missed.
- **Two catalogs listing one product with different prices in one account would archive each
  other's prices.** Lake's catalog has no prices, so Lake cannot hit it.
- **None of the payment kinds or `LakeOrderSource` has run against real Stripe or a real leaf.**
  The tests use a fake Stripe that keeps Stripe's idempotency rules, and a real Postgres for the
  order SQL.
- **Nothing upgrades a dedicated cluster after it is made** (`orders.md` open question 7).
- **The `v1-dev` live proof of the cluster row is owed**: after the roll, the Job should log
  `cluster-row: inserted the c1 oramacore_clusters row` and the stack report `ClusterRowReady=True`.
- Unchanged from v0.6.2: zone tokens may lack Zone Settings Edit; Always Use HTTPS waits for regional
  wildcard coverage (#515); old `lake-eu` and `lake-us.oramadev.net` records (#627); Cloud v1 readers
  on `v1-prod` (#597); the `v1-dev` proofs (#590); the managing cluster not managed by a resource
  (#593); the default Zetta image (#588); the e2e images (#589, #596); the temporary `Lake/prod`
  (#536); the zetta-tunnel ingress gateway and Cloud v1 (#575); a workspace Kafka service under
  restricted Pod Security (#428); leftover test resources on the management cluster (#168).

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)). Before the upgrade,
  `make check-crds`, then the CRDs widened, the upgrade, and the CRDs exactly
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)): this release adds six CRDs.
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.7.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
