# v0.5.0

**Released:** 2026-10-17 · **Branch:** `main` · **Previous:** [v0.4.0](v0.4.0.md) (2026-10-17).

v0.5.0 is **the Orama Cloud v1 stack in Prod 1's shape**, the operator side of the Cloud v1
migration ([orama-bridge#137](https://github.com/oramasearch/orama-bridge/issues/137)). The control
database is always in-cluster and gains the dashboard's migration 0008 and its reference rows; the
writer and readers can run side-only engine images; the engine's LLM providers, hooks deny list and
startup budgets match Prod 1; broker and Redis passwords are generated and the master key is one
required value; the dashboard takes its environment from Secrets and runs Prod 1's crons; every
Cloud v1 Ingress gets origin TLS; and every Cloud v1 volume has a size the operator grows. Beside
it: the Cloudflare DNS controller creates and deletes only records it owns, node pools declare
kernel settings, and `LakeE2ETest` targets a set member.

Everything in [v0.4.0](v0.4.0.md) is still here. This page lists what is new or changed.

## 1. Cloud v1 control database

**Always in-cluster** (#503, issue #377, decision 61).
- `spec.components.controlDB.mode: external` is refused at admission (a CEL rule) and by the
  reconcile for a resource stored before the rule, which leaves the existing control-DB resources
  untouched and reports `Degraded`. The network sandbox no longer opens public TCP 5432.
- The dashboard never runs `db-migrate`; an old init container is removed on update.
- The dashboard, index-builder and analytics processor read the connection from
  `<cr>-controldb-app` through one helper. The analytics processor's render escapes every value.
- Other data stores keep `mode: external`.

**Migration 0008 and the reference rows** (#398, issue #378, decision 62).
- The dashboard's migration 0008 is its own owned `PostgresSchema`, `<cr>-controldb-schema-0008`,
  applied after the 0000 to 0007 schema, so an existing control database converges on the next
  roll with no step by hand. Sign-in needs it (`subscription_plans`).
- The reference rows (Prod 1's 6 plans, 23 add-on prices and 15 LLMs, with Prod 1's IDs) are
  upserted by ID, never deleted, by `<cr>-controldb-reference-data`.
- **New field** `spec.components.controlDB.stripePrices {plans[], addons[]}`: each stack's Stripe
  price IDs.
- **New field** `PostgresSchema.spec.applyEveryVersion` (default `false`, so Lake is unchanged):
  re-apply a schema on every version even when its guard table exists.
- The stack replaces its own schema's terminally failed, current-version Job; status component
  `controldb-schema` names the first schema not yet applied.

## 2. Cloud v1 engine

- **Side-only images** (#405, issue #308, decision 64). `spec.images.overrides`
  `oramacore-writer` and `oramacore-reader`, set together or not at all. With both, the writer
  runs the writer-only image on `writer.yaml` and the readers the reader-only image on
  `reader.yaml`. Combined mode is unchanged byte for byte. Each side has its own config hash.
  Condition `EngineSidesSeparated` reports which mode runs.
- **LLM providers from `spec.llm`** (#407, issue #304, decision 65). New fields: a `google`
  provider, `spec.llm.automaticEmbeddingsSelector {provider, model}` and
  `providers[].apiKeySecretRef {name}`. Without `spec.llm` the engine gets Prod 1's four providers
  (OpenAI, Google, Groq, Anthropic), `groq` as default. Every key is a placeholder filled at pod
  start, never in the ConfigMap. `orama.cloud/llm-secret-hash` rolls the writer and readers when a
  key changes.
- **Hooks deny list** (#409, issue #306, decision 66). Prod 1's deny list entry for entry, the
  cluster's own names, the stack's `<cr>-*`, `**` forms of Prod 1's prefix entries, IPv4-mapped and
  unspecified IPv6, and Azure's WireServer `168.63.129.16`; fixed timeouts 200 ms and 1 s. No field.
  The writer and readers roll once.
- **Startup budgets** (#504, issue #309). The startup probe allows the writer 20 minutes
  (`failureThreshold` 120) and each reader 40 minutes (240), Prod 1's budgets, so a reader loading a
  production-size index is not killed. Readiness and liveness are unchanged.
- **Reader readiness on `/health/ready`** (#506, issue #458). A reader is Ready only once it has
  applied the stream head it saw at startup. A reader that refuses (`REPLICATION_HISTORY_EXPIRED`,
  `REPLICATION_STREAM_BEHIND`) is never Ready, and the `reader` component detail names the cause.
  **The reader image must serve `GET /health/ready`** (oramacore#340 and #341); see
  [Known issues](#known-issues).

## 3. Cloud v1 credentials

#411, issue #307, decision 67.
- `<cr>-broker-admin` and `<cr>-cache-auth` hold a random 48-character password each, created once
  where the store is in-cluster. The literal `dev-rabbitmq-password` is gone. Redis requires its
  password.
- **New field** `spec.masterAPIKeySecretRef {name, key (default MASTER_API_KEY)}`: the one master
  key. With no reference, a missing Secret or key, an empty, `dev-*` or multi-line value, the writer
  and readers are held and `Ready=False` names the reason.
- `orama.cloud/credentials-hash` rolls every consumer when a credential Secret changes.

## 4. Cloud v1 dashboard

- **Environment from Secrets** (#423, issue #311, decision 68). **New fields**
  `spec.components.dashboard.envFrom` and `.env`. Variables the operator owns (`DATABASE_URL`,
  `POSTGRES_*`, `JWT_*`, `MASTER_API_KEY`) are refused with a readable message, a missing
  reference fails the reconcile before the Deployment is touched, and
  `orama.cloud/dashboard-env-hash` rolls the dashboard when a source changes.
- **Crons and the e2e canary** (#424, issue #17, decision 69). **New field**
  `spec.components.dashboard.crons {enabled, suspend (default true), e2eCanary {image, secretRef}}`.
  The crawler (every minute), index GC (hourly) and consumption sync (every six hours) are CronJobs
  calling the in-cluster dashboard with its own `CRON_SECRET`; `<cr>-e2e-canary` runs Prod 1's
  canary every five minutes and the prune once a day. All are created suspended; the cutover
  unsuspends them through the `v1-prod` set file.

## 5. Cloud v1 origin TLS

#545, issue #457, decision 70.
- Each stack owns a namespaced cert-manager `Issuer` `<cr>-letsencrypt` (Let's Encrypt, DNS-01
  through `spec.cloudflare.apiTokenSecretRef`). Every Cloud v1 Ingress gets one TLS entry and one
  Secret per host (`<host>-tls`), and nginx `ssl-redirect`. A host with no Cloudflare token fails
  the reconcile. RBAC adds `cert-manager.io` `issuers`.
- The v1 set files name `docs-dev`, `docs-eu` and `docs-us.oramadev.net` instead of
  `docs.sandbox.local`.
- Lake, LakeApp, LakeEnvironment and Zetta Ingresses are not covered (#578).

## 6. Cloud v1 storage

#505, issue #383, decision 63.
- **New field** `storage {size, storageClassName}` on the writer, the four in-cluster stores
  (analytics, cache, broker, search) and the control database; omitted, 10Gi on the cluster default
  class, as before.
- The operator grows existing claims (and the CNPG `Cluster`'s `spec.storage.size`) when a size goes
  up; claim templates stay as created. Condition `StorageApplied` reports a shrink or a class change
  it cannot apply (`ShrinkNotSupported`, `StorageClassChangeNotSupported`, `StorageUpdateFailed`,
  `ClaimsPending`) and leaves the volume untouched.
- `config/clusters/sets/v1-prod.yaml` carries Prod 1-derived sizes, each with its source: writer
  512Gi, analytics 200Gi, broker 20Gi, control database 10Gi; cache and search stay 10Gi.

## 7. Cloudflare DNS: create-only

#502, issue #312.
- `CloudflareDNSRecord` creates only records it can prove it made: each new record carries the
  comment `orama-operator:<namespace>/<name>` (**new status field** `status.ownerComment`). A
  record at the name without it is refused, never adopted, changed or deleted.
- Cleanup and renames delete a record only while its comment still matches; otherwise the finalizer
  is released with a Warning `RecordNotOwned`. Records tracked by `status.recordID` before this
  change keep working without gaining a comment.
- **New field** `spec.sharedOwner`, which requires `deletionPolicy: Retain` (CEL): Lake's Clerk
  records use `clerk/<instance ID>`, so every Lake on one Clerk instance recognises them.

## 8. Node-pool sysctls

#501, issue #454; #586 (docs).
- **New field** `sysctls` on `KubernetesCluster` node pools, copied to `AksCluster`: Linux kernel
  settings (for example `vm.max_map_count: 4194304` for OramaCore readers). The 28 settings AKS
  supports are mapped to `linuxOSConfig.sysctls` at creation; others are refused with
  `InvalidSysctls` before any Azure request. `InSync` reports a pool whose live setting differs.
- AKS sets `linuxOSConfig` only when a pool is created. Existing clusters need a new pool (#579).
- **The managed-cluster Azure API version moves from `2024-09-01` to `2025-05-01`** for every read,
  create and delete.
- [`docs/infrastructure/node-pool-replacement.md`](../infrastructure/node-pool-replacement.md)
  designs the replacement.

## 9. `LakeE2ETest` aimed at a set member

#554, part of #537. The runner is the private repository
[oramasearch/lake-e2e](https://github.com/oramasearch/lake-e2e).
- **New fields** `spec.member {lakeSet, name}` (exactly one of it and `spec.targetRef`, CEL),
  `spec.env`, `spec.runID` and `spec.timeoutSeconds` (default 3h). A Lake not labelled as that
  set's member is refused.
- One Job per spec generation, `<name>-e2e-<generation>`; a finished run is never restarted.
- **New status fields** `pass`, `fail`, `skip`, `failed[]`, `skipped[]` (`{step, reason}`),
  `lakeRevision`, `target`, `runID`, `observedGeneration`, `startedAt`, `completedAt`. Print
  columns Target, Phase, Pass, Fail, Skip.

## 10. Environments and clusters

- **Leaves on v0.4.0** (#584): `config/clusters/*/operator.yaml` pin every leaf to `v0.4.0`. They

## Known issues

Security first.

- **Security: hostnames that resolve to private IPs pass the hooks deny list.** The list matches
  host names and literal addresses, not where a name resolves; the network lockdown is #437.
- **Security: the generated broker and Redis passwords have no rotation** (#594).
- **Security: `CloudflareTunnel` still adopts and overwrites a CNAME found by name** (#585); only
  `CloudflareDNSRecord` became create-only.
- **Security: Lake, LakeApp, LakeEnvironment and Zetta Ingresses have no TLS to the origin** (#578);
  Cloud v1's do from this release.
- **Security: a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller**
  (#280), and **apps can reference arbitrary Secrets in the Lake namespace** through legacy
  `secret_env_refs` (#492). Both unchanged from v0.4.0.
- **Rolling this operator makes every Cloud v1 reader not Ready** until the sets run a reader image
  with oramacore#340 and #341 (`GET /health/ready`): the readiness probe hits a path the current
  v1.2.39 image does not serve, so the reader Services empty. The images are #597. The Kubernetes
  Cloud v1 environments (`v1-dev`, `v1-eu`, `v1-us`) serve no one until the migration.
- **`config/clusters/sets/v1-nonprod.yaml` names three Secrets that do not exist on the managing
  cluster**: `v1-nonprod-llm-keys`, `v1-nonprod-master-api-key` and `v1-nonprod-dashboard-env`.
  Applying the file fails until they are created (#595).
- **The `v1-dev` live proofs of the merged Cloud v1 changes are owed** (#590).
- **`v1-prod`'s storage sizes take effect only** once this operator runs on the production leaves and
  `config/clusters/sets/v1-prod.yaml` is applied.
- **The managed-cluster Azure API version change** (`2025-05-01`, #501) must pass the drift check on
  `orama-nonprod-cluster-01` before the production leaves.
- **The managing cluster is not managed by a resource** (#593): rolling it is a script with Steve's
  consent.
- **The default Zetta image is still `main-4015ef76`**; zetta v0.3.0 is #588 and not in this release.
- **Images not built yet:** the Lake end-to-end runner image `oramasearch/lake-e2e` (#589) and the
  canary image `oramasearch/oramacore-test-e2e` (#596), so no set file carries `crons.e2eCanary`
  and no `LakeE2ETest` exists on a cluster.
- Unchanged from v0.4.0: the temporary `Lake/prod` on `lake.oramadev.net` (#536), the zetta-tunnel
  ingress gateway never serving Cloud v1 (#575), a workspace Kafka service under restricted Pod
  Security (#428), and leftover test resources on the management cluster (#168).

Nowhere yet beyond the local tests above. None of this release's code changes has run on a
cluster; each one's live proof is pending Steve's consent (#590 for the Cloud v1 ones).

The image is built from the tag (2026-10-17): `oramasearch/orama-operator:main-21fe4f3`, digest
`sha256:d0c389f0071286fe0a2b97908b5be1f6ce33e1ef46f5777c3f69c6712ec306e0`, on the cluster BuildKit.
Docker Hub `v0.5.0` names that digest, there is no `latest`, and the repository stays private. The
chart is published as `0.5.0` for leaves (`sha256:0305b32a75e0025e9d09867f8fe8b3769151223e074c25c24c15edf686e94411`)

  tag with `operator.image.tag=v0.5.0` (CRDs widened, `helm upgrade`, rollout, CRDs exactly).

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.5.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
