# v0.5.0

**Released:** 2026-10-17 · **Branch:** `main` · **Previous:** [v0.4.0](v0.4.0.md) (2026-10-17).

v0.5.0 brings **the Orama Cloud v1 stack to the shape of the original hosted service**. The control
database is always in-cluster and gains the dashboard's migration 0008 and its reference rows; the
writer and readers can run side-only engine images; the engine's LLM providers, hooks deny list and
startup budgets match the hosted service; broker and Redis passwords are generated and the master
key is one required value; the dashboard takes its environment from Secrets and runs its crons;
every Cloud v1 Ingress gets origin TLS; and every Cloud v1 volume has a size the operator grows.
Beside it: the Cloudflare DNS controller creates and deletes only records it owns, node pools
declare kernel settings, and `LakeE2ETest` targets a set member.

Everything in [v0.4.0](v0.4.0.md) is still here. This page lists what is new or changed.

## 1. Cloud v1 control database

**Always in-cluster.**
- `spec.components.controlDB.mode: external` is refused at admission (a CEL rule) and by the
  reconcile for a resource stored before the rule, which leaves the existing control-DB resources
  untouched and reports `Degraded`. The network sandbox no longer opens public TCP 5432.
- The dashboard never runs `db-migrate`; an old init container is removed on update.
- The dashboard, index-builder and analytics processor read the connection from
  `<cr>-controldb-app` through one helper. The analytics processor's render escapes every value.
- Other data stores keep `mode: external`.

**Migration 0008 and the reference rows.**
- The dashboard's migration 0008 is its own owned `PostgresSchema`, `<cr>-controldb-schema-0008`,
  applied after the 0000 to 0007 schema, so an existing control database converges on the next
  roll with no step by hand. Sign-in needs it (`subscription_plans`).
- The reference rows (6 plans, 23 add-on prices and 15 LLMs) are upserted by ID, never deleted, by
  `<cr>-controldb-reference-data`.
- **New field** `spec.components.controlDB.stripePrices {plans[], addons[]}`: each stack's Stripe
  price IDs.
- **New field** `PostgresSchema.spec.applyEveryVersion` (default `false`, so Lake is unchanged):
  re-apply a schema on every version even when its guard table exists.
- The stack replaces its own schema's terminally failed, current-version Job; status component
  `controldb-schema` names the first schema not yet applied.

## 2. Cloud v1 engine

- **Side-only images.** `spec.images.overrides` `oramacore-writer` and `oramacore-reader`, set
  together or not at all. With both, the writer runs the writer-only image on `writer.yaml` and the
  readers the reader-only image on `reader.yaml`. Combined mode is unchanged byte for byte. Each
  side has its own config hash. Condition `EngineSidesSeparated` reports which mode runs.
- **LLM providers from `spec.llm`.** New fields: a `google` provider,
  `spec.llm.automaticEmbeddingsSelector {provider, model}` and `providers[].apiKeySecretRef {name}`.
  Without `spec.llm` the engine gets four providers (OpenAI, Google, Groq, Anthropic), `groq` as
  default. Every key is a placeholder filled at pod start, never in the ConfigMap.
  `orama.cloud/llm-secret-hash` rolls the writer and readers when a key changes.
- **Hooks deny list.** The hosted service's deny list entry for entry, the cluster's own names, the
  stack's `<cr>-*`, `**` forms of the prefix entries, IPv4-mapped and unspecified IPv6, and Azure's
  WireServer `168.63.129.16`; fixed timeouts 200 ms and 1 s. No field. The writer and readers roll
  once.
- **Startup budgets.** The startup probe allows the writer 20 minutes (`failureThreshold` 120) and
  each reader 40 minutes (240), so a reader loading a production-size index is not killed.
  Readiness and liveness are unchanged.
- **Reader readiness on `/health/ready`.** A reader is Ready only once it has applied the stream
  head it saw at startup. A reader that refuses (`REPLICATION_HISTORY_EXPIRED`,
  `REPLICATION_STREAM_BEHIND`) is never Ready, and the `reader` component detail names the cause.
  **The reader image must serve `GET /health/ready`**; see [Known issues](#known-issues).

## 3. Cloud v1 credentials

- `<cr>-broker-admin` and `<cr>-cache-auth` hold a random 48-character password each, created once
  where the store is in-cluster. The literal `dev-rabbitmq-password` is gone. Redis requires its
  password.
- **New field** `spec.masterAPIKeySecretRef {name, key (default MASTER_API_KEY)}`: the one master
  key. With no reference, a missing Secret or key, an empty, `dev-*` or multi-line value, the writer
  and readers are held and `Ready=False` names the reason.
- `orama.cloud/credentials-hash` rolls every consumer when a credential Secret changes.

## 4. Cloud v1 dashboard

- **Environment from Secrets.** **New fields** `spec.components.dashboard.envFrom` and `.env`.
  Variables the operator owns (`DATABASE_URL`, `POSTGRES_*`, `JWT_*`, `MASTER_API_KEY`) are refused
  with a readable message, a missing reference fails the reconcile before the Deployment is
  touched, and `orama.cloud/dashboard-env-hash` rolls the dashboard when a source changes.
- **Crons and the e2e canary.** **New field**
  `spec.components.dashboard.crons {enabled, suspend (default true), e2eCanary {image, secretRef}}`.
  The crawler (every minute), index GC (hourly) and consumption sync (every six hours) are CronJobs
  calling the in-cluster dashboard with its own `CRON_SECRET`; `<cr>-e2e-canary` runs the canary
  every five minutes and the prune once a day. All are created suspended; a set file unsuspends
  them when the stack goes live.

## 5. Cloud v1 origin TLS

- Each stack owns a namespaced cert-manager `Issuer` `<cr>-letsencrypt` (Let's Encrypt, DNS-01
  through `spec.cloudflare.apiTokenSecretRef`). Every Cloud v1 Ingress gets one TLS entry and one
  Secret per host (`<host>-tls`), and nginx `ssl-redirect`. A host with no Cloudflare token fails
  the reconcile. RBAC adds `cert-manager.io` `issuers`.
- The docs host in the v1 set files is a real DNS name instead of `docs.sandbox.local`.
- Lake, LakeApp, LakeEnvironment and Zetta Ingresses are not covered.

## 6. Cloud v1 storage

- **New field** `storage {size, storageClassName}` on the writer, the four in-cluster stores
  (analytics, cache, broker, search) and the control database; omitted, 10Gi on the cluster default
  class, as before.
- The operator grows existing claims (and the CNPG `Cluster`'s `spec.storage.size`) when a size goes
  up; claim templates stay as created. Condition `StorageApplied` reports a shrink or a class change
  it cannot apply (`ShrinkNotSupported`, `StorageClassChangeNotSupported`, `StorageUpdateFailed`,
  `ClaimsPending`) and leaves the volume untouched.

## 7. Cloudflare DNS: create-only

- `CloudflareDNSRecord` creates only records it can prove it made: each new record carries the
  comment `orama-operator:<namespace>/<name>` (**new status field** `status.ownerComment`). A
  record at the name without it is refused, never adopted, changed or deleted.
- Cleanup and renames delete a record only while its comment still matches; otherwise the finalizer
  is released with a Warning `RecordNotOwned`. Records tracked by `status.recordID` before this
  change keep working without gaining a comment.
- **New field** `spec.sharedOwner`, which requires `deletionPolicy: Retain` (CEL): Lake's Clerk
  records use `clerk/<instance ID>`, so every Lake on one Clerk instance recognises them.

## 8. Node-pool sysctls

- **New field** `sysctls` on `KubernetesCluster` node pools, copied to `AksCluster`: Linux kernel
  settings (for example `vm.max_map_count: 4194304` for OramaCore readers). The 28 settings AKS
  supports are mapped to `linuxOSConfig.sysctls` at creation; others are refused with
  `InvalidSysctls` before any Azure request. `InSync` reports a pool whose live setting differs.
- AKS sets `linuxOSConfig` only when a pool is created. Existing clusters need a new pool.
- **The managed-cluster Azure API version moves from `2024-09-01` to `2025-05-01`** for every read,
  create and delete.
- [`docs/infrastructure/node-pool-replacement.md`](../infrastructure/node-pool-replacement.md)
  designs the replacement.

## 9. `LakeE2ETest` aimed at a set member

The runner is a separate end-to-end test image.
- **New fields** `spec.member {lakeSet, name}` (exactly one of it and `spec.targetRef`, CEL),
  `spec.env`, `spec.runID` and `spec.timeoutSeconds` (default 3h). A Lake not labelled as that
  set's member is refused.
- One Job per spec generation, `<name>-e2e-<generation>`; a finished run is never restarted.
- **New status fields** `pass`, `fail`, `skip`, `failed[]`, `skipped[]` (`{step, reason}`),
  `lakeRevision`, `target`, `runID`, `observedGeneration`, `startedAt`, `completedAt`. Print
  columns Target, Phase, Pass, Fail, Skip.

## 10. Leaf versions

- **Leaves on v0.4.0**: `config/clusters/*/operator.yaml` pin every leaf to `v0.4.0`. They move to
  `v0.5.0` in a separate change.

## What `v0.5.0` does **not** include

- **Zetta `v0.3.0` as the default Zetta image.** The default stays
  `oramasearch/zetta:main-4015ef76`.
- **Reader seeding** from another reader, and readers on persistent disks.
- **The public reader and writer hosts and the extra hosts**, each stack's own ingress-nginx, and
  the declared Cloudflare edge.
- **Generated stack-internal credentials beyond the broker and Redis**, per-key Secret references
  and helper image overrides.
- **Origin TLS for Lake, LakeApp, LakeEnvironment and Zetta Ingresses**; Cloud v1's have it from
  this release.
- **A self-managed management cluster.**

## Known issues

- **Upgrading makes every Cloud v1 reader not Ready** until the stack runs a reader image that
  serves `GET /health/ready`: with an older reader image the readiness probe hits a path the image
  does not serve, so the reader Services empty. Move the reader image before or with this release.
- **A set file that names Secrets** (LLM keys, the master key, the dashboard environment) fails to
  apply until those Secrets exist on the management cluster.
- **New storage sizes take effect only** once this operator runs on the cluster and the set file
  that states them is applied.
- **The managed-cluster Azure API version change** (`2025-05-01`) should pass the drift check on a
  nonprod cluster before production clusters.
- **The management cluster is not managed by a resource**: rolling it is a `helm upgrade`.
- **The default Zetta image is still `main-4015ef76`.**
- **The Lake end-to-end runner and the Cloud v1 canary images** are not part of this release, so a
  set file cannot yet carry `crons.e2eCanary` or a `LakeE2ETest`.
- Unchanged from v0.4.0: the zetta-tunnel ingress gateway never serves Cloud v1, a workspace Kafka
  service does not start under restricted Pod Security, and leftover test resources from earlier
  builds may remain.

## Verification

Run on the release branch, macOS arm64, Go 1.26, with the Kubernetes 1.30.3 envtest binaries:

```
go build ./...                ok
go vet ./...                  ok
gofmt -l .                    nothing listed
make manifests generate       no diff
helm lint chart               1 chart linted, 0 failed
go test ./... -count=1        ok   cmd, internal/controller, internal/crdrollout, internal/meshprojection:
                                   642 test functions, 628 passed, 14 skipped, 0 failed (614 subtests passed)
```

The fourteen skipped are opt-in and were not enabled in that run: twelve need a local Postgres
(`TestControlDBSchemasAgainstPostgres`, `TestConnectionRolesAgainstPostgres`, the nine
`*PgxStoreAgainstPostgres` and `TestLakeSchemaEnvtest`), `TestEgressGatewayAgainstZettaTunnel`
needs a zetta-tunnel binary, and `TestLiveChartDownloadAndPrerequisiteCheck` needs `LEAF_LIVE=1`
and a live cluster.

**The control database schemas against a real Postgres** (PostgreSQL 17.7, local), run separately
with `CONTROLDB_SCHEMA_TEST_POSTGRES_URI`: `TestControlDBSchemasAgainstPostgres` passed, 5 of 5
cases (an empty database; 0000 to 0007 with a team; missing reference rows fail, then recover; a
compatible partial 0008 without its guard; the stack's Stripe prices). The test creates and drops
only its own databases.

None of this release's code changes had run on a cluster when it was cut.

The image built from the tag is published as `oramasearch/orama-operator:v0.5.0` (there is no
`latest`), and the chart as `0.5.0` in `oramasearch/orama-operator-chart`.

## Upgrading

- **Leaves:** set `version: v0.5.0` in every `config/clusters/*/operator.yaml`, then apply those
  files, nonprod first.
- **The management cluster:** a roll from the tag with `operator.image.tag=v0.5.0` (CRDs widened,
  `helm upgrade`, rollout, CRDs exactly; see
  [`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)).

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.5.0`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
