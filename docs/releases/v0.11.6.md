# v0.11.6

**Released:** 2026-10-31 · **Branch:** `main` · **Previous:** [v0.11.5](v0.11.5.md) (2026-10-31).

A patch release: **the faults that stopped the observability hubs after Pixie's release was applied.** With v0.11.5 and the
provider applied, each hub's Prometheus crash-looped and Pixie Cloud never started. Three operator faults are fixed here; the
fourth, the Postgres image's missing tag, is fixed in the committed provider file.

| Measured | Value |
|---|---|
| Resource kinds | 54 CRDs in `chart/crds` (unchanged) |
| CRD changes | none |
| Operator code | the hub Prometheus, the Pixie release check, the Pixie prune, Pixie Cloud's dependency ConfigMaps |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

- **The hub Prometheus owns its volume.** It set no pod `securityContext`, so its Azure disk stayed root's and Prometheus
  (non-root) failed with `permission denied` on `/prometheus`. It now runs as uid 1000 with `fsGroup` 2000, like the
  platform's kube-prometheus-stack.
- **A Pixie Postgres image must carry its tag.** CloudNativePG reads the PostgreSQL version from the tag and refuses an
  image given by digest alone, so the provider is not Ready until `postgres` is `repo:<version>@sha256:…`.
  `config/clusters/observability-provider.yaml` names `pixie-postgres:16.15@sha256:34cd4159…`.
- **The Pixie prune spares objects another controller owns.** CloudNativePG copies the `pixie-db` Cluster's inherited
  labels, `orama.cloud/pixie: cloud` included, onto the ServiceAccount, Services and budget it creates; the prune listed
  them by that label and deleted them on every pass, so the database pod's token stopped working (`Unauthorized`). It
  also tried to delete CNPG's Role and RoleBinding (refused). It now skips an object whose controller is not an
  `orama.cloud` kind.
- **`pl-sentry-dsn-config` is rendered**, its three keys empty (Sentry off), as upstream ships it in `cloud_deps`;
  without it `config-manager` stopped at `CreateContainerConfigError`.
- Two tests: every ConfigMap key a rendered Cloud pod needs is rendered, and the prune leaves a CNPG-owned object alone.

## What it does not include

- Any change to the platform charts, Lake or Cloud v1.
- Pixie Cloud had not yet started on a cluster: past the database, Kratos and Hydra, the bootstrap, the deploy keys and the
  Viziers are still unproven ([observability.md](../infrastructure/observability.md)).

## Upgrading

- No CRD changes. The CRD rollout ([crd-rollout.md](../operations/crd-rollout.md)) runs as for any release and changes nothing.
- **What rolls on each cluster with the operator:** the operator, and the zetta-tunnel mesh pods, which carry a container from
  the operator image. On each cluster that runs a hub, the hub Prometheus is re-created with its new `securityContext`. No
  Lake or Cloud v1 workload changes.
- A `pixie-db-1` pod started before the upgrade may still hold a token for a ServiceAccount the old prune deleted. If it keeps
  failing with `Unauthorized` once CNPG has recreated the account, the pod must be replaced.
