# v0.10.2

**Released:** 2026-10-25 · **Branch:** `main` · **Previous:** [v0.10.1](v0.10.1.md) (2026-10-25).

A patch with two fixes: an app's **Zetta binding is the JSON document app-runtime reads**, so apps with workspace
data start again (lake#1205), and Cloud v1 stacks **generate their DISCO and pgAdmin credentials** and replace the
placeholder RabbitMQ admin password (#570).

## What it includes

| PR | Change |
|---|---|
| [#1001](https://github.com/oramasearch/orama-operator/pull/1001) | **An app's Zetta binding is a JSON document.** The binding Secret's `zetta` key held the bare token; app-runtime reads the file with `json.loads` and needs `{"lake_url":…,"customer_id":…,"token":…}`, so every app with workspace data crash-looped at startup (`segmentation-dashboard` on lake-dev). The operator now writes that document, on the synchronized and the standalone path; `lake_url` is the pod's `LAKE_URL`. A byte-for-byte fixture (`internal/controller/testdata/app-binding-zetta.json`) is shared with app-runtime ([app-runtime#15](https://github.com/oramasearch/app-runtime/pull/15)); lake's side is [lake#1217](https://github.com/oramasearch/lake/pull/1217). The token and the hashes Lake registers are unchanged. Issue [lake#1205](https://github.com/oramasearch/lake/issues/1205), epic [lake#1158](https://github.com/oramasearch/lake/issues/1158) |
| [#1017](https://github.com/oramasearch/orama-operator/pull/1017) | **Cloud v1: the remaining generated credentials.** Bootstrap creates `<cr>-disco-auth` (`DISCO_SECRET`, read by DISCO and workers, and by index-builder as `DISCO_SECRET_KEY`) and `<cr>-pgadmin-auth` (`PGADMIN_DEFAULT_PASSWORD`), 48-character hex, generated once and kept across disable and re-enable. Real values already in the old component Secrets are adopted (conflicting real DISCO copies stop bootstrap, naming where they are, without values); only the exact former placeholders are replaced and pruned. The exact legacy RabbitMQ admin placeholder password is replaced once; real broker passwords are kept. The same on every cluster, with no chart value or flag. Issue [#570](https://github.com/oramasearch/orama-operator/issues/570) (stays open for its live proof) |

- **Leaf operator pins:** every leaf on v0.10.1 (`02f9a10`), and the v0.10.1 back-merge (#991).

## Upgrading

**No CRD changes.** Roll as for every release: CRDs widened, then `helm upgrade`, then CRDs exactly
([`../operations/crd-rollout.md`](../operations/crd-rollout.md)).

**What restarts, once, on the first reconcile after the roll:**

- **Every Lake app with a Zetta binding** (#1001): the binding's bytes change, so its credential digest does, and
  the app's pod rolls once. After it, `segmentation-dashboard` on lake-dev should start.
- **Cloud v1 stacks, `v1-prod` included** (#1017): DISCO, workers and index-builder (the new `<cr>-disco-auth`
  hash), pgAdmin (`<cr>-pgadmin-auth`), and the broker StatefulSet where its admin password was the legacy
  placeholder. Later reconciles change no credential. On `v1-prod`, applying the roll there is a production
  change: confirm the set and its members are `Ready` afterwards.

Nothing else changes in what the operator renders.

## Known issues

- **Neither fix has run on a cluster yet.** The release was cut without a `dev-<sha>` operator build on the dev
  environment first (Steve, 2026-10-25: *"yes, let's skip and cut"*); the managing cluster ran v0.10.1 when it was
  cut. #570's live proof and lake#1205's (the app starting on lake-dev) follow the roll.
- [lake#1212](https://github.com/oramasearch/lake/issues/1212): app-runtime's `workspace.sql()` calls
  `/zetta/v1/sql`, which Lake does not serve on the workspace route. An app that queries with SQL starts after
  #1001, then fails on its first query. A lake change, not an operator one.
- Otherwise unchanged from [v0.10.0](v0.10.0.md#known-issues).
