# v0.10.0

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.5](v0.9.5.md) (2026-10-24).

The operator side of **lake v0.7.0** ([lake#1158](https://github.com/oramasearch/lake/issues/1158)):
**a lake version is now only its image.** The operator reads `lake manifest` from each lake image and
migrates the control database with that image's own `lake migrate`, so lake's migrations no longer need
an operator release first. Also a Lake on a **customer-owned domain**, an external **status page** for
lake.live, **store restore rehearsals**, a Stripe permission check for auto top-up, and generated Cloud
v1 stack-internal credentials.

> **Read [Before it rolls](#before-it-rolls).** It rolls **before** the lake v0.7.0 image, and its Cloud
> v1 change restarts stack components when it reaches a Cloud v1 stack.

## Lake

| PR | Change |
|---|---|
| [#965](https://github.com/oramasearch/orama-operator/pull/965) | **A lake version is only its image.** A Job runs `lake manifest` from `spec.image` once per image (no network, no environment, no token); every value is pattern-checked and kept in `Lake.status.imageManifest`. For an image that supports it, the Lake's `PostgresSchema` runs `lake migrate --wait-seconds 600` from the image by digest (new `spec.migrate`), and the schema gate holds the Deployment until it has applied. Stripe webhook events and products come from the manifest. Images up to lake v0.6.1 answer exit 2 and keep the vendored path. An unreadable or untrusted manifest makes the Lake Degraded and holds the image ([`../lake/schema.md`](../lake/schema.md), #936) |
| [#953](https://github.com/oramasearch/orama-operator/pull/953) | The vendored schema Job sees `schema_migrations(version)` written without a space, such as lake's `0098` (#948) |
| [#963](https://github.com/oramasearch/orama-operator/pull/963) | **A Lake on a customer-owned domain** (`spec.customDomain.host`): the CNAME and ownership TXT the customer creates are published in status and checked by DNS; once verified, its own Ingress and a Let's Encrypt certificate (HTTP-01); once issued, lake gets `LAKE_PUBLIC_HOST` = the customer host with `LAKE_HOST_ALIASES` and `LAKE_CONTROL_HOST` = the Orama host. Clerk's allowed origins follow. Inert until a member sets it ([`../lake/custom-domains.md`](../lake/custom-domains.md), #947) |
| [#943](https://github.com/oramasearch/orama-operator/pull/943) | `PaymentsReady` also checks the Lake's restricted Stripe key can create the PaymentIntent auto top-up uses, with a request that cannot create one; `AppKeyPermissionsMissing` otherwise, rechecked every minute (lake#1124) |
| [#964](https://github.com/oramasearch/orama-operator/pull/964) | **Store restore rehearsals** (`LakeRestoreRehearsal` `service: store`: the newest store snapshot restored into a throwaway namespace and read read-only, never touching the live disk or the snapshots); **`LakeSet.spec.restoreRehearsals`**, applied on each member's cluster; and `allow-rehearsal-ingress-to-controldb`, without which no Postgres rehearsal's checker could reach the control database. The lake-prod rehearsals are committed commented out ([`../lake/restore-rehearsals.md`](../lake/restore-rehearsals.md), #127) |

## Before it rolls

- **Roll it before lake v0.7.0**, through dev → testing → staging → prod with the gates. On the v0.6.1
  images running today nothing changes for the schema (they keep the vendored path); the first v0.7.0
  pin then migrates through `lake migrate`.
- **Cloud v1: #949 changes stack-internal credentials and restarts the components that use them**
  wherever a stack still runs the `dev-*` placeholders. Rehearse on `v1-dev` (`v1-nonprod`) and check
  writes, queries, crawls, cron and the decrypter there before this version reaches
  `orama-production-cluster-02` (`v1-eu`, production) (#570).
- **New CRD and RBAC:** `StatusPage`, new fields on `Lake`, `LakeSet`, `PostgresSchema`,
  `LakeRestoreRehearsal` and `CloudflareR2Bucket`, and `volumesnapshotcontents` create/delete. Apply the
  CRDs widened, roll, then exactly (`docs/operations/crd-rollout.md`).
- Rolling needs Steve's consent: the managing cluster by its script, then every leaf's `operator.yaml`
  in one command. Steve, 2026-10-24: no deploy until every project's release is cut.
