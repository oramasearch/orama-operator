# v0.10.0

**Released:** 2026-10-24 · **Branch:** `main` · **Previous:** [v0.9.5](v0.9.5.md) (2026-10-24).

The operator side of **lake v0.7.0**: **a lake version is now only its image.** The operator reads
`lake manifest` from each lake image and migrates the control database with that image's own
`lake migrate`, so lake's migrations no longer need an operator release first. Also a Lake on a
**customer-owned domain**, external **status pages**, **store restore rehearsals**, a Stripe permission
check for auto top-up, and generated Cloud v1 stack-internal credentials.

> **Read [Before it rolls](#before-it-rolls).** It rolls **before** the lake v0.7.0 image, and its Cloud
> v1 change restarts stack components when it reaches a Cloud v1 stack.

## Lake

- **A lake version is only its image.** A Job runs `lake manifest` from `spec.image` once per image (no
  network, no environment, no token); every value is pattern-checked and kept in
  `Lake.status.imageManifest`. For an image that supports it, the Lake's `PostgresSchema` runs
  `lake migrate --wait-seconds 600` from the image by digest (new `spec.migrate`), and the schema gate
  holds the Deployment until it has applied. Stripe webhook events and products come from the manifest.
  Images up to lake v0.6.1 answer exit 2 and keep the vendored path. An unreadable or untrusted manifest
  makes the Lake Degraded and holds the image ([`../lake/schema.md`](../lake/schema.md)).
- The vendored schema Job sees `schema_migrations(version)` written without a space, such as lake's
  `0098`.
- **A Lake on a customer-owned domain** (`spec.customDomain.host`): the CNAME and ownership TXT the
  customer creates are published in status and checked by DNS; once verified, its own Ingress and a
  Let's Encrypt certificate (HTTP-01); once issued, lake gets `LAKE_PUBLIC_HOST` = the customer host with
  `LAKE_HOST_ALIASES` and `LAKE_CONTROL_HOST` = the Lake's own host. Clerk's allowed origins follow.
  Inert until a member sets it ([`../lake/custom-domains.md`](../lake/custom-domains.md)).
- `PaymentsReady` also checks the Lake's restricted Stripe key can create the PaymentIntent auto top-up
  uses, with a request that cannot create one; `AppKeyPermissionsMissing` otherwise, rechecked every
  minute.
- **Store restore rehearsals** (`LakeRestoreRehearsal` `service: store`: the newest store snapshot
  restored into a throwaway namespace and read read-only, never touching the live disk or the
  snapshots); **`LakeSet.spec.restoreRehearsals`**, applied on each member's cluster; and
  `allow-rehearsal-ingress-to-controldb`, without which no Postgres rehearsal's checker could reach the
  control database ([`../lake/restore-rehearsals.md`](../lake/restore-rehearsals.md)).

## Platform

- **`StatusPage`**: external HTTP checks once a minute through Cloudflare, alerts on each change of
  state by webhook or SMTP, and a public `index.html` and `status.json` written to an S3 bucket.
  **`CloudflareR2Bucket.spec.customDomain`** serves a bucket on a custom domain. No platform chart is
  added ([`../infrastructure/status-pages.md`](../infrastructure/status-pages.md)).

## Cloud v1

- **Generated stack-internal credentials** (ClickHouse, Typesense, dashboard cron, decrypter,
  index-builder) in scoped Secrets, created once; consumers reference the shared value, and a changed
  credential rolls the components that use it. Supplied Secrets are preserved; the `dev-*` placeholders
  are pruned.

## Not in this release

- Routing the Ingress to lake's proxy port: it may roll only once every Lake runs lake v0.7.0, so it
  goes in a later release.
- Rendering lake v0.7.0's `LAKE_BRAND_*` for a white-labelled Lake, and apps and preview wildcards on a
  customer domain.
- Deleting the vendored lake schema and lists: once every Lake reports `imageManifest.supported` and no
  set pins lake v0.6.1 or older.

## Before it rolls

- **Roll it before lake v0.7.0**, one environment at a time. On v0.6.1 images nothing changes for the
  schema (they keep the vendored path); the first v0.7.0 pin then migrates through `lake migrate`.
- **Cloud v1: the generated credentials restart the components that use them** wherever a stack still
  runs the `dev-*` placeholders. Rehearse on a nonprod stack and check writes, queries, crawls, cron and
  the decrypter there before this version reaches a production stack.
- **New CRD and RBAC:** `StatusPage`, new fields on `Lake`, `LakeSet`, `PostgresSchema`,
  `LakeRestoreRehearsal` and `CloudflareR2Bucket`, and `volumesnapshotcontents` create/delete. Apply the
  CRDs widened, roll, then exactly ([`../operations/crd-rollout.md`](../operations/crd-rollout.md)).
- Roll the managing cluster's operator first, then every leaf's `OramaOperator`.

## Known issues

- A Lake's control Postgres is not backed up by the operator yet; store snapshots exist, and restore
  rehearsals are available but must be enabled per set.
- The control databases run CloudNativePG's default image by tag, which the Postgres rehearsal refuses.
- No live Let's Encrypt issuance or real DNS lookup has run for a customer domain, and no `StatusPage`
  has run against a live host.
- Those of [v0.9.5](v0.9.5.md#known-issues).
