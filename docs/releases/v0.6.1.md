# v0.6.1

**Released:** 2026-10-18 · **Branch:** `main` · **Previous:** [v0.6.0](v0.6.0.md) (2026-10-17).

v0.6.1 is **a patch for the Cloud v1 network sandbox**. v0.6.0 added the analytics retention Job,
the analytics import CronJob and the processor's pulls from the readers, but the network sandbox
did not allow them. After upgrading to v0.6.0, the analytics retention Job timed out connecting to
ClickHouse on every run, and the stack stayed not Ready. This release opens exactly those three
paths. It also has a stack that names no master key get a generated one.

Everything in [v0.6.0](v0.6.0.md) is still here. This page lists what is new or changed.

Changes in this release:

- The network sandbox allows the analytics retention Job, the import CronJob and the processor's
  reader pulls.
- A stack naming no `spec.masterAPIKeySecretRef` gets a generated `<cr>-master-api-key`; the
  nonprod Cloud v1 set file names none.
- A production Cloud v1 set member may also take a generated master key.
- The leaves pinned to `v0.6.0`.
- `main` merged back into `dev` after v0.6.0.

## 1. Network sandbox: the analytics paths

The fix this patch exists for.

| Path | In v0.6.0 | In v0.6.1 |
|---|---|---|
| Analytics retention Job → ClickHouse `:9000` (`clickhouse-client`) | No egress; ClickHouse admitted only `:8123`, from a fixed list | Egress `allow-analytics-retention-egress`; `allow-analytics-ingress` admits the Job on `:9000` |
| Analytics import CronJob → analytics processor `:8080` | No egress, and no ingress on the processor | Egress `allow-analytics-import-egress`; new ingress `allow-analytics-processor-ingress` |
| Analytics processor → readers `:8080` (it pulls every reader's search events) | Egress to the writer only; the readers did not admit it | `allow-analytics-processor-egress` reaches every reader; `allow-reader-ingress` admits it |

- Nothing else in the sandbox changes. Each allowance names only the component pods that need it.
- New test `TestOramaCloudAnalyticsJobsReachTheirTargets` checks that each path has both its egress
  and its ingress allowance. Without the fix it reports all six missing.
- [`docs/infrastructure/network-sandbox.md`](../infrastructure/network-sandbox.md) lists the paths.

## 2. A generated master API key

- **Generated by default.** With `spec.masterAPIKeySecretRef` unset, the operator creates
  `<cr>-master-api-key` (key `MASTER_API_KEY`, 48 random hex characters) once, alongside the broker,
  Redis and analytics keys. The engine, index-builder, workers, dashboard, analytics processor and
  e2e runner all read it.
- **Never replaced.** The Secret is created once and not rewritten, and the `c1` cluster row keeps
  the key it was inserted with.
- **A named Secret still wins**, for a stack that must keep an existing key.
- Before v0.6.1 a stack naming no key was held at 0 engine replicas. A named Secret that does not
  exist still holds it.
- New test `TestGeneratedMasterAPIKey`. Docs: `components.md`, `crd-reference.md`, `install.md`,
  `provisioning-runbook.md`, `config/clusters/README.md` and the samples.

## 3. Leaf versions

- **Leaves on v0.6.0**: `config/clusters/*/operator.yaml` pin every leaf to `v0.6.0`. They move to
  `v0.6.1` in a separate change.
- **The Cloud v1 set files**: a member that names no master key runs on its generated
  `<member>-master-api-key`, and the set no longer copies a master-key Secret for it.

## What `v0.6.1` does **not** include

Everything listed under v0.6.0's [*does not include*](v0.6.0.md#what-v060-does-not-include) is
still not included: Zetta `v0.3.0` as the default Zetta image, reader seeding, each stack's own
ingress-nginx, the declared Cloudflare edge, further generated credentials and per-key references,
and a self-managed management cluster.

## Known issues

- **A Cloud v1 stack's engines start only once its set is applied**, with either a generated key or
  a named Secret that exists. Until then they stay held at 0 engine replicas.
- **Cloud v1 readers are not Ready** until the stack runs a reader image serving
  `GET /health/ready`.
- **Upgrading from v0.5.0 or earlier replaces each Cloud v1 reader Deployment with the reader
  StatefulSet** (v0.6.0), so the readers are down during the switch and each starts on an empty disk.
- **The management cluster is not managed by a resource**: rolling it is a `helm upgrade`.
- **The default Zetta image is still `main-4015ef76`.**
- **The Lake end-to-end runner and the Cloud v1 canary images** are not part of this release.
- **Graceful shutdown and Kubernetes-practice gaps** across the operator's workloads are still to
  be closed.
- Unchanged from v0.6.0: the zetta-tunnel ingress gateway never serves Cloud v1, a workspace Kafka
  service does not start under restricted Pod Security, and leftover test resources from earlier
  builds may remain.

## Upgrading

- **Leaves:** set `version: v0.6.1` in every `config/clusters/*/operator.yaml`, then apply those
  files, nonprod first.
- **The management cluster:** a roll from the tag with `operator.image.tag=v0.6.1` (CRDs widened,
  `helm upgrade`, rollout, CRDs exactly; see
  [`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)). After it, a Cloud v1 stack's
  analytics retention Job should complete.

---

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.6.1`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
