# v0.6.1

**Released:** 2026-10-18 · **Branch:** `main` · **Previous:** [v0.6.0](v0.6.0.md) (2026-10-17).

v0.6.1 is **a patch for the Cloud v1 network sandbox**. v0.6.0 added the analytics retention Job,
the analytics import CronJob and the processor's pulls from the readers, but the network sandbox
did not allow them. After the v0.6.0 roll, `v1-analytics-retention` on `orama-system/v1` (managing
cluster) timed out connecting to ClickHouse on every run, and the stack stayed not Ready (#616).
This release opens exactly those three paths. It also has a stack that names no master key get a
generated one (#615), and moves `v1-dev` and `v1-us` onto that generated key.

Everything in [v0.6.0](v0.6.0.md) is still here. This page lists what is new or changed.

## 1. Network sandbox: the analytics paths

#618, issue #616. The fix this patch exists for.

| Path | In v0.6.0 | In v0.6.1 |
|---|---|---|
| Analytics retention Job → ClickHouse `:9000` (`clickhouse-client`) | No egress; ClickHouse admitted only `:8123`, from a fixed list | Egress `allow-analytics-retention-egress`; `allow-analytics-ingress` admits the Job on `:9000` |
| Analytics import CronJob → analytics processor `:8080` | No egress, and no ingress on the processor | Egress `allow-analytics-import-egress`; new ingress `allow-analytics-processor-ingress` |
| Analytics processor → readers `:8080` (it pulls every reader's search events) | Egress to the writer only; the readers did not admit it | `allow-analytics-processor-egress` reaches every reader; `allow-reader-ingress` admits it |

- Nothing else in the sandbox changes. Each allowance names only the component pods that need it.
- New test `TestOramaCloudAnalyticsJobsReachTheirTargets` checks that each path has both its egress
  and its ingress allowance. Without the fix it reports all six missing.
- [`docs/infrastructure/network-sandbox.md`](../infrastructure/network-sandbox.md) lists the paths.

## 2. A generated master API key

#617 and #619, issue #615.
- **Generated by default.** With `spec.masterAPIKeySecretRef` unset, the operator creates
  `<cr>-master-api-key` (key `MASTER_API_KEY`, 48 random hex characters) once, alongside the broker,
  Redis and analytics keys. The engine, index-builder, workers, dashboard, analytics processor and
  e2e runner all read it.
- **Never replaced.** The Secret is created once and not rewritten, and the `c1` cluster row keeps
  the key it was inserted with.
- **A named Secret still wins.** Production's `v1-eu` names Prod 1's key (`v1-prod.yaml`).
- Before v0.6.1 a stack naming no key was held at 0 engine replicas. A named Secret that does not
  exist still holds it.
- New test `TestGeneratedMasterAPIKey`. Docs: `components.md`, `crd-reference.md`, `install.md`,
  `provisioning-runbook.md`, `config/clusters/README.md` and the samples.

## 3. Environments and clusters

- **Leaves on v0.6.0** (#614): `config/clusters/*/operator.yaml` pin every leaf to `v0.6.0`. They
  move to `v0.6.1` in a separate change, rolled with Steve's consent (see [Where it runs](#where-it-runs)).
- **`v1-nonprod`** (`config/clusters/sets/v1-nonprod.yaml`): names no master key, so `v1-dev` runs
  on the generated `v1-dev-master-api-key`. `v1-nonprod-master-api-key` is no longer copied.
- **`v1-prod`** (`config/clusters/sets/v1-prod.yaml`, #619): `v1-us` names no master key and copies
  no Secret; it runs on the generated `v1-us-master-api-key` until the US migration names Prod 1's.
  `v1-eu` still names `v1-prod-master-api-key`. **Not applied.**

## Known issues

Security first.

- **Security: hostnames that resolve to private IPs pass the hooks deny list.** The list matches
  host names and literal addresses, not where a name resolves; the network lockdown is #437.
- **Security: the generated broker and Redis passwords have no rotation** (#594). The generated
  master key added in this release has none either.
- **Security: `CloudflareTunnel` still adopts and overwrites a CNAME found by name** (#585).
- **Security: Lake, LakeApp, LakeEnvironment and Zetta Ingresses have no TLS to the origin**; #578
  was closed as not planned, without a comment. Cloud v1's Ingresses have it.
- **Security: a tenant `OramaZettaCluster` can reconfigure the cluster-wide Karpenter controller**
  (#280), and **apps can reference arbitrary Secrets in the Lake namespace** through legacy
  `secret_env_refs` (#492). Both unchanged.
- **`v1-prod.yaml` still needs `v1-prod-master-api-key` holding Prod 1's real key** (#607). Its
  other source Secrets, `v1-prod-llm-keys` and `v1-prod-dashboard-env`, hold `xxx` placeholders.
  `v1-us-master-api-key` is no longer needed on the managing cluster (#619).
- **`v1-nonprod`'s Secrets exist** (#595): `v1-nonprod-llm-keys` and `v1-nonprod-dashboard-env`
  were created on 2026-10-18 with `xxx` placeholders where no real value exists yet (the OpenAI key
  is real). `v1-nonprod-master-api-key` is no longer needed.
- **The `v1-dev`, `v1-eu` and `v1-us` engines start only once their sets are applied.**
  `v1-nonprod.yaml` now generates `v1-dev`'s key and `v1-prod.yaml` generates `v1-us`'s, but neither
  file is applied yet; `v1-eu` also needs `v1-prod-master-api-key` (#607). Until then they stay
  held at 0 engine replicas.
- **Cloud v1 readers are not Ready** until the sets run a reader image serving `GET /health/ready`
  (oramacore#340 and #341); the images are #597.
- **Rolling from v0.5.0 or earlier replaces each Cloud v1 reader Deployment with the reader
  StatefulSet** (v0.6.0), so the readers are down during the switch and each starts on an empty disk.
- **The `v1-dev` live proofs of the merged Cloud v1 changes are owed** (#590), including the
  analytics retention Job completing on `orama-system/v1` with this fix.
- **The managing cluster is not managed by a resource** (#593): rolling it is a script with Steve's
  consent.
- **The default Zetta image is still `main-4015ef76`** (#588).
- **Images not built yet:** the Lake end-to-end runner `oramasearch/lake-e2e` (#589) and the canary
  `oramasearch/oramacore-test-e2e` (#596).
- **Graceful shutdown and Kubernetes-practice gaps** across the operator's workloads
  ([orama-bridge#197](https://github.com/oramasearch/orama-bridge/issues/197)).
- Unchanged from v0.6.0: the temporary `Lake/prod` on `lake.oramadev.net` (#536), the zetta-tunnel
  ingress gateway never serving Cloud v1 (#575), a workspace Kafka service under restricted Pod
  Security (#428), and leftover test resources on the management cluster (#168).

## Where it runs

Nowhere yet beyond the local tests above. None of this release's changes has run on a cluster.

The image is built from the tag on the cluster BuildKit; its digest is recorded here after the
build, in the back-merge of `main` into `dev`.

Rolling it is a separate step that needs Steve's consent.

- **Leaves:** set `version: v0.6.1` in every `config/clusters/*/operator.yaml` by pull request,
  then apply those files from the merged commit, nonprod first.
- **The managing cluster** (`orama-production-cluster-01`): the `build-operator.sh` roll from the
  tag with `operator.image.tag=v0.6.1` (CRDs widened, `helm upgrade`, rollout, CRDs exactly). This
  is where #616 was seen; after the roll, `v1-analytics-retention` should complete on
  `orama-system/v1`.

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)).
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.6.1`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
