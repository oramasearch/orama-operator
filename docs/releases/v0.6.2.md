# v0.6.2

**Released:** 2026-10-19 · **Branch:** `main` · **Previous:** [v0.6.1](v0.6.1.md) (2026-10-18).

v0.6.2 is **a patch for the Cloud v1 control database migrations**. On v0.6.1 the stack's network
sandbox admitted only the first of the three control DB migration Jobs, so `controldb-schema-0008`
waited for the database forever, `reference-data` never started, and each stack stayed at 22/24
components. This release admits every migration Job of the stack.

A release is `dev` promoted, so it also carries what merged into `dev` since v0.6.1: origin TLS on
every Lake Ingress with the operator securing the Lake's Cloudflare zone (three new kinds), a new
Cloud v1 engine image in the set files, and Lake `v0.2.0` with Clerk in the Lake set files.

Everything in [v0.6.1](v0.6.1.md) is still here. This page lists what is new or changed.

## 1. Cloud v1: every control DB migration Job reaches the database

The fix this patch exists for.

- **What was wrong.** The control DB schema is applied in three steps, each a `PostgresSchema` with
  its own migration Job: `<cr>-controldb-schema`, `<cr>-controldb-schema-0008` and
  `<cr>-controldb-reference-data`. The sandbox's `allow-postgres-schema-egress` and
  `allow-controldb-ingress` matched only the first. The other two were added without admitting
  them.
- **What changes.** `controlDBSchemaSuffixes` names all three steps. `controlDBSchemas` builds the
  `PostgresSchema`s from it, and both NetworkPolicies select
  `orama.cloud/postgresschema In [...]` from the same list, so a future schema is admitted from its
  first run. The values carry the stack's name, so another stack's Jobs are not admitted.
- **On the roll** the NetworkPolicies are updated in place. The waiting `schema-0008` pod connects on
  its next retry, then `reference-data` runs and `controldb-schema` turns Ready. No Job is deleted.
- New test `TestNetworkSandboxAdmitsEveryControlDBSchema`: without the fix it reports four missing
  admissions.

## 2. Lake: origin TLS and the Lake's zone

Contract and rollout order: [`docs/lake/origin-tls.md`](../lake/origin-tls.md).

- **Certificates.** Each Lake with a `dnsSecretRef` owns an `Issuer` `lake-<name>-letsencrypt`
  (Let's Encrypt, DNS-01 through that Secret's token). The Lake's Ingress has TLS for `host` and
  `apexHost`. New `lake-<name>-apps-wildcard` and `-preview-wildcard` Ingresses hold the wildcard
  certificates and redirect unknown names to the Lake. `LakeApp` and `LakeEnvironment` Ingresses use
  the wildcard certificate (copied into the workspace namespace) or their own `Certificate`. A public
  `OramaZettaCluster` Ingress gets its own `Issuer`.
- **No HTTP-only fallback.** A Lake Ingress with neither `dnsSecretRef` nor `tls.secretName` fails
  its reconcile and says why.
- **The zone, by new kinds.** Each such Lake owns an `EdgeProvider` and an `EdgeZonePolicy`
  `lake-<name>-edge`; the `CloudflareZonePolicy` controller is the only code that changes zone
  settings. Every ten minutes it probes each proxied host's origin and edge, and turns settings on in
  order, each only when its check passes, never off: `ssl` `full`, then `strict`, then
  `tls_client_auth` (authenticated origin pulls), then `always_use_https`.
  `kubectl get edgezp -A` shows where each zone stands, and `status.hosts` the failing hosts.
- **What each Lake Ingress takes from the zone.** `ssl-redirect` only once the zone is `full` or
  `strict` and the edge covers every host; the client-certificate requirement (Cloudflare's
  origin-pull CA, embedded in the operator) only once the zone reports `tls_client_auth` on.
- **Scope.** Lake's Ingresses only. Cloud v1's Ingresses and zones, the platform values,
  `helmfile.yaml` and `platform.yaml` are unchanged.
- **Token permission.** Each zone's token now also needs **Zone > Zone Settings > Edit**. A token
  without it is reported by name on the `EdgeZonePolicy`, and the zone is left as it is.

## 3. Set files and leaf versions

- **Lake set files:** the template runs `oramasearch/lake:v0.2.0`, and every member has Clerk. A
  production set can put each region on its own host with the picker at the apex host.
- **Cloud v1 set files:** the template's `images.overrides.oramacore` is
  `oramasearch/oramacore-cloud-v1:v1.2.39-ready-9d8ed373`.
- **Leaves on `v0.6.2`:** `config/clusters/*/operator.yaml` move to `v0.6.2` in a separate change.

## What `v0.6.2` does **not** include

Everything listed under v0.6.1's [*does not include*](v0.6.1.md#what-v061-does-not-include) is
still not included, except origin TLS for Lake, which is now in. Also not included: provisioning
paid orders from lake's control plane, geo load balancing across regions, certificates for regional
wildcards, zone-level authenticated origin pulls with an operator-owned certificate, HTTP-01 for
hosts without a DNS-01 credential, and the Stripe resources.

## Known issues

- **A zone token may not yet have Zone > Zone Settings > Edit.** Until it does, the
  `EdgeZonePolicy` reports the missing permission and its zone's settings stay as they are; the
  Lakes keep `ssl-redirect: "false"` and no client-certificate requirement.
- **Always Use HTTPS waits for edge coverage** of app hosts two labels below the apex
  (`<app>.eu.<apex>`), which Universal SSL does not cover.
- **Cloud v1 readers are not Ready** until a set runs an engine image that serves
  `/health/ready`.
- **The management cluster is not managed by a resource**: rolling it is a `helm upgrade`.
- **The default Zetta image is still `main-4015ef76`.**
- **The Lake end-to-end runner and the Cloud v1 canary images** are not part of this release.
- Unchanged from v0.6.1: the zetta-tunnel ingress gateway never serves Cloud v1, a workspace Kafka
  service does not start under restricted Pod Security, leftover test resources from earlier builds
  may remain, and graceful shutdown gaps.

## Verification

Run on the release branch, macOS arm64, Go 1.26, with the Kubernetes 1.30.3 envtest binaries:

```
go build ./...                ok
go vet ./...                  ok
gofmt -l .                    nothing listed
make manifests generate       no diff
helm lint chart               1 chart linted, 0 failed
go test ./... -count=1        ok   cmd, internal/controller, internal/crdrollout, internal/meshprojection:
                                   737 test functions, 722 passed, 15 skipped, 0 failed (747 subtests passed)
```

The fifteen skipped are opt-in and were **not run** for this release: thirteen need a local
Postgres (`TestControlDBSchemasAgainstPostgres`, `TestControlDBClusterRowAgainstPostgres`,
`TestConnectionRolesAgainstPostgres`, `TestLakeSchemaEnvtest` and the nine
`*PgxStoreAgainstPostgres`), `TestEgressGatewayAgainstZettaTunnel` needs a zetta-tunnel binary, and
`TestLiveChartDownloadAndPrerequisiteCheck` needs `LEAF_LIVE=1` and a live cluster. The suite ran
with the version already at 0.6.2, so `TestReleaseVersionIsDocumented` passed against this page.
The fix itself is proved by the new `TestNetworkSandboxAdmitsEveryControlDBSchema`.

**The fix, live:** after the upgrade, a Cloud v1 stack's sandbox selects all three schema names,
its `controldb-reference-data` migration Job completes, and `controldb-schema` is no longer
waiting.

The image built from the tag is published as `oramasearch/orama-operator:v0.6.2` (there is no
`latest`), and the chart as `0.6.2` in `oramasearch/orama-operator-chart`.

## Installing it

- **A management cluster** is installed from `helmfile.yaml`: the platform releases first, then the
  operator chart, with its registry Secret ([`docs/install.md`](../install.md)). Before the upgrade,
  `make check-crds`, then the CRDs widened, the upgrade, and the CRDs exactly
  ([`docs/operations/crd-rollout.md`](../operations/crd-rollout.md)): this release adds three CRDs.
- **A managed cluster** is installed by its management cluster: its `KubernetesCluster`, its
  `platform.yaml` and an `OramaOperator` at `version: v0.6.2`, applied from `config/clusters/`
  ([`docs/infrastructure/operations.md`](../infrastructure/operations.md)).
