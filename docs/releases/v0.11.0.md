# v0.11.0

**Released:** 2026-10-29 · **Branch:** `main` · **Previous:** [v0.10.6](v0.10.6.md) (2026-10-27).

A minor release: **five new kinds for observability**, **zone-level authenticated origin pulls** for Lake's Cloudflare
zones, and four Cloud v1 fixes for problems found after a stack moved onto the operator.

| Measured | Value |
|---|---|
| Resource kinds | 54 CRDs in `chart/crds` (49 in v0.10.6) |
| CRD changes | 5 new kinds; new optional fields on `ClusterHelmRelease`, `EdgeZonePolicy`, `CloudflareZonePolicy` and `EdgeProvider`; nothing removed |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

- **Observability.** New kinds `ObservabilityProvider`, `ObservabilityHub`, `ObservabilityAgent`, `PixieCloud` and
  `PixieVizier`; a self-hosted Pixie rendered from a vendored, pinned bundle; per-stack PodMonitors, alert rules and
  Perses dashboards for Cloud v1, written only once the monitoring CRDs exist. `ClusterHelmRelease` gains
  `imagePullSecretRef` / `imagePullSecretAs`. Two platform releases (kube-prometheus-stack, Perses) are in
  `helmfile.yaml` and every `config/clusters/*/platform.yaml` but are **not applied by this release**.
- **Zone-level authenticated origin pulls.** The managing cluster makes one origin-pull CA per Cloudflare zone, and the
  `LakeSet` copies it (never its key) to each member serving the zone. The zone switches from Cloudflare's shared
  certificate to ours only after a probe shows every origin trusts our CA. `EdgeZonePolicy` and `CloudflareZonePolicy`
  gain `spec.originPullSecretRef` and `status.zoneOriginPulls`.
- A Cloud v1 writer crash-looping on its previous image is deleted (graceful, UID and resource-version preconditions) so
  the StatefulSet rolls the requested image onto the same claim.
- A stack's dashboard crons reach its dashboard on TCP 3000; before this, the crawler and index-gc crons failed every
  run.
- Combined-image Cloud v1 readers record search analytics; before this, they recorded none.
- Cloud v1 engine Ingresses admit the engine's body limits: writer `400m`, reader `16m`. nginx answered 413 above 1 MiB.
- A doc comment moved; no behaviour change.

## What it does not include

- The observability platform releases are committed, not applied. Their image mirrors and the Pixie build don't exist
  yet.
- A production observability hub on the management cluster, without a separate `prod-support` cluster. This release
  still has the `prod-support` purpose.

## Upgrading

- **CRDs in two steps around the roll** ([crd-rollout.md](../operations/crd-rollout.md)): widened before the operator
  starts, exact once it alone runs. All changes are additive.
- **What rolls on each cluster:** every Cloud v1 stack on the combined image restarts its readers once, one pod at a
  time (the analytics fix). The writers don't restart, except a writer crash-looping on an old image, which is
  replaced. The engine Ingresses and the dashboard network policies change in place.
- **Zone origin pulls wait for a permission.** The Cloudflare token needs Zone > SSL and Certificates > Edit on the zone.
  Until it has it, `ZoneOriginPulls` names the missing permission and the zone stays on global pulls. The `LakeSet` on
  the managing cluster makes and copies the zone CA Secrets once the managing cluster runs this release.

## Known issues

- The release had not run on a cluster when it was cut: no development build of these changes was tested on a cluster
  first.
- The zone switch probes a wildcard record under one name, not through each App's own Ingress. An App whose reconcile is
  stuck before its edge step could refuse Cloudflare after the switch.
- With `400m`, ingress-nginx buffers large writer bodies to its pod's disk; the Cloudflare plan's upload cap applies
  before nginx.
- `kubectl diff -R -f config/clusters/` shows the two observability platform releases until they are applied.
- Otherwise unchanged from [v0.10.4](v0.10.4.md#known-issues), less the crash-looping writer, which this release fixes.
