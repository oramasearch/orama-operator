# v0.11.7

**Released:** 2026-10-31 · **Branch:** `main` · **Previous:** [v0.11.6](v0.11.6.md) (2026-10-31).

A patch release: **Pixie's metadata index is created as soon as OpenSearch is ready**, so the indexer starts and the
observability hubs can become Ready. After v0.11.6 the hubs were stuck at 19/20: the indexer exits when its index
`md_entities_9` is missing, the hub is not Ready without the indexer, and the operator created the index only once the hub was
Ready.

| Measured | Value |
|---|---|
| Resource kinds | 54 CRDs in `chart/crds` (unchanged) |
| CRD changes | none |
| Operator code | the PixieCloud bootstrap's order |
| Lake schema | nothing vendored |
| Tests | see [Verification](#verification) |

## What it includes

- The bootstrap takes OpenSearch's readiness apart from the hub's: it creates the metadata index once `pixie-search` is
  Ready, and does the rest (the administrator, the organisation, the deploy keys) once the hub is Ready, as before.
  `TestPixieCloudBootstrapIssuesAndRevokesPerClusterKeys` now expects the index and no keys with only OpenSearch ready.
- Docs: how people reach Perses, Prometheus, Alertmanager and the Pixie UI (`kubectl port-forward`, nothing public), and
  *Verify* records how to check that the platform charts run on every cluster.

## What it does not include

- Any change to the platform charts, Lake or Cloud v1.
- The Viziers connecting to their hub and live traces are still unproven
  ([observability.md](../infrastructure/observability.md)).

## Upgrading

- No CRD changes. The CRD rollout ([crd-rollout.md](../operations/crd-rollout.md)) runs as for any release and changes nothing.
- **What rolls on each cluster with the operator:** the operator, and the zetta-tunnel mesh pods, which carry a container from
  the operator image. No Lake or Cloud v1 workload changes. On the hubs, the operator then creates the index and the indexer
  starts.

## Known issues

- Unchanged from [v0.11.6](v0.11.6.md#known-issues).
- A `CloudflareR2Bucket` that is already gone keeps its finalizer, and its deletion can get 403 on permission groups.
