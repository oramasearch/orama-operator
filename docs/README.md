# orama-operator — docs

Deep docs for the operator. Kept in lockstep with the source (see the repo
[`CLAUDE.md`](../CLAUDE.md) → *Docs discipline*).

- [`../README.md`](../README.md) — the front door: what the operator is, status, build and test, and pointers into these docs.
- [`../DESIGN.md`](../DESIGN.md) — architecture + the decision log from the design grill.
- [`install.md`](install.md) — **install the operator + deploy a v1 stack** (prereqs, helm/helmfile, the CR, multi-region, uninstall).
- [`install/credentials.md`](install/credentials.md) — **private-image bootstrap**: manager versus application pull-secret settings, render proof, and startup diagnosis.
- [`install/k0s.md`](install/k0s.md) — **install a private Lake on the liquid k0s distribution**, including the fresh-machine, single-node storage, pull-secret, Ready, and air-gapped paths.
- [`research/secure-runtimes/`](research/secure-runtimes/README.md) — **research on secure runtimes** for apps, agents and builds ([lake#725](https://github.com/oramasearch/lake/issues/725)): gVisor, Kata Containers, Firecracker, AKS Pod Sandboxing, Confidential Containers and WebAssembly, what could not be established, and licences. Research, not a design.
- [`research/secure-networking/`](research/secure-networking/README.md) — **research for secure networking in Lake** ([#437](https://github.com/oramasearch/orama-operator/issues/437)): the deep-research report on Istio, workspace lockdown, credential-carrying connections, Cloudflare Tunnel and peering, the prompt that produced it, and the licensing check. Research, not a design: the stated direction is to build our own C++ components.
- [`infrastructure/operations.md`](infrastructure/operations.md) — **the runbook for the clusters**: create a cluster, upgrade the operator everywhere, add or change a Lake or Orama Cloud v1 instance in a set, check status, and what has gone wrong before. What is deployed is in [`../config/clusters/`](../config/clusters/README.md).
- [`infrastructure/network-sandbox.md`](infrastructure/network-sandbox.md) — **owner-scoped default-deny networking**: the `NetworkSandbox` renderer, mandatory Cilium cloud-metadata deny and live AKS finding, shared-namespace safety, operator-only policy RBAC, recovery behavior, every allowed path for Lake instances, Lake workspaces and Orama Cloud v1 stacks, and Cloud v1 engine public-address lockdown ([#465](https://github.com/oramasearch/orama-operator/issues/465), [#466](https://github.com/oramasearch/orama-operator/issues/466), [#467](https://github.com/oramasearch/orama-operator/issues/467)).
- [`infrastructure/connections.md`](infrastructure/connections.md) — **declared workspace paths**: Lake's guarded Postgres intake, one `Connection` CR per row, paired sandbox-owned ingress and egress, target-port resolution, safe retirement of `allow-workspace-internal`, deletion and status recovery ([#468](https://github.com/oramasearch/orama-operator/issues/468)); credential-scoped connections with a Postgres role each, delivered as a workspace secret, rotated and revoked ([#469](https://github.com/oramasearch/orama-operator/issues/469)).
- [`infrastructure/README.md`](infrastructure/README.md) — **management and leaf clusters**: every cluster runs the operator; the management cluster provisions leaf clusters and owns their cluster resources, a leaf owns its workloads and autoscaling; ephemeral clusters, bridges between clusters, the `KubernetesCluster`, `KubernetesClusterProvider` and `AksCluster` kinds, `ClusterHelmRelease` and `OramaOperator` (what the management cluster installs on a leaf, prerequisites first), `LakeSet` and `OramaCloudV1Set` (instances on managed clusters from one template), how the management role is turned on, and the path from the existing cluster ([#351](https://github.com/oramasearch/orama-operator/issues/351)). `orama-nonprod-cluster-01` was created with them on 2026-10-12.
- [`development.md`](development.md) — build, codegen, run, and the AKS smoke test.
- [`releases/README.md`](releases/README.md) — **releases**: one page per tagged release and the conventions for cutting one; [`releases/v0.2.0.md`](releases/v0.2.0.md) is the current release; [`releases/v0.1.0.md`](releases/v0.1.0.md) is the first and lists every resource kind.
- [`crd-reference.md`](crd-reference.md) — the field reference for every resource kind.
- [`components.md`](components.md) — what each component reconciler creates, and its status.
- [`datastore-crds.md`](datastore-crds.md) — **datastore state as declarative, owned CRDs** ([#40](https://github.com/oramasearch/orama-operator/issues/40)): the reconciled-CRD pattern and the `RabbitMQTopology` broker topology (vhosts/users/permissions/streams via the management API).
- [`zetta-datastore.md`](zetta-datastore.md) — **Zetta as the operator's datastore** (One Orama symbiosis v0): the `orama_control` / `orama_data` schema, how it's provisioned over `/v1/sql`, and the desired-vs-observed source-of-truth boundary, and the cross-cluster topology table, whose peer rows are validated as untrusted input ([operator#279](https://github.com/oramasearch/orama-operator/issues/279)).
- [`zetta-cluster-mtls.md`](zetta-cluster-mtls.md) — **the shared cluster join token**: how the operator mints one token per `OramaZettaCluster` so every node forms **one** mTLS cluster (the CA is derived from the token), why peer traffic is mTLS-only (no plaintext mode), and the engine dependencies for multi-node convergence ([operator#92](https://github.com/oramasearch/orama-operator/issues/92)).
- [`control-plane/README.md`](control-plane/README.md) — **liquid deployment control plane**: authenticated REST `/v1` and MCP operations, Zetta history/audit storage, `LakeEnvironment` materialization, rollback, and OpenAPI drift verification.
- [`lake/README.md`](lake/README.md) — **the `Lake` CR**: what it reconciles (namespace, credentials, Deployment, Service, CNPG control-plane Postgres, the schema via `PostgresSchema`, Ingress + DNS), pod DNS (`ndots:2` on lake, agent and app pods), status, RBAC, how to deploy the operator with Lake support, how to run a Lake, the current production instance.
- [`lake/schema.md`](lake/schema.md) — **Lake schema provenance and rollout ordering**: pinned byte verification, migration `0021`, when the Job skips the file (guard plus every recorded `schema_migrations` row, #271), automatic Job replacement, re-vendoring, and native envtest/Postgres proof.
- [`lake/backups.md`](lake/backups.md) — **Lake control-plane backups**: R2 credentials, scheduled CNPG Barman backups, verification, configuration changes, and recovery into a new Cluster.
- [`lake/environments.md`](lake/environments.md) — **named and per-change Lake environments**: Zetta deployment events, `LakeEnvironment` materialization, the k0s namespace profile, ingress/DNS, anti-flap status and teardown.
- [`lake/apps.md`](lake/apps.md) — **deployed Lake apps**: the Postgres desired-row contract, `lake_apps` notifications, generated scoped tokens and hash registration, merged per-app registry pull credentials, status/deletion/orphan sync, wildcard DNS, isolated workloads, bindings and live events.
- [`lake/builds.md`](lake/builds.md) — **Lake in-cluster image builds**: one rootless BuildKit Job per queued row, per-space isolation and registry cache, scoped credentials, concurrency, progress events, and status recovery.
- [`lake/lake-sqlite.md`](lake/lake-sqlite.md) — **lake-sqlite**: the web service behind the `sqlite` service kind (one SQLite database, `modernc.org/sqlite`, BSD-3-Clause): its API, configuration, build and local run.
- [`lake/lake-duckdb.md`](lake/lake-duckdb.md) — **lake-duckdb**, powered by DuckDB: where the web service behind the `duckdb` service kind lives (its own private repository and image) and how this operator runs it.
- [`lake/lake-polars.md`](lake/lake-polars.md) — **lake-polars**, powered by Polars: where the web service behind the `polars` service kind lives (its own private repository and image) and how this operator runs it.
- [`lake/services.md`](lake/services.md) — **Lake managed services**: the `services` / `service_status` contract in lake's control Postgres, workspace placement of Zetta, Postgres and catalog resources, exclusion of the workspace-owned Zetta, the trusted `lake-<lake>-services` connection projection, deletion and quota.
- [`lake/stores.md`](lake/stores.md) — **Lake customer stores** (lake#196): the `stores` / `store_status` contract on the services poll; phase 1's cluster volume (one Lake-owned PersistentVolumeClaim per store, its connection in `lake-<lake>-services`), the other pairs `Failed`, deletion.
- [`lake/volume-snapshots.md`](lake/volume-snapshots.md) — **Lake volume snapshots** (operator#260): `volume_snapshot_policies` / `volume_snapshot_status`, the `Retain` snapshot class, scheduled and requested `VolumeSnapshot`s of the store and workspace volumes, pruning, snapshots outliving their workspace, and the manual restore runbook.
- [`lake/methodology-runs.md`](lake/methodology-runs.md) — **Lake methodology runs** (lake#655): a workspace methodology's Python code run as untrusted code: stage, sandbox and collect pods in the Lake's methodology-runs namespace, no credential or network in the sandbox unless granted, phases, the per-workspace queue and GPU placement (#293), metering, and serving a trained model as a sandboxed Deployment only lake reaches (lake#690).
- [`lake/app-transfer.md`](lake/app-transfer.md) — **Lake app transfer** (lake#661): the bytes each app receives and sends through ingress-nginx, read from its per-Ingress counters (its metrics must be on) and added to `app_transfer` by app and hour for lake to bill as `transfer`.
- [`lake/workload-resources.md`](lake/workload-resources.md) — **Lake workload resources** (lake#643, lake#658): one `workload_resources` row per workspace engine, managed service, app, build, agent launch and agent cron run with the CPU, memory, GPUs, GPU class and VRAM its scheduled pods were given, a job's row from its Job as soon as it exists, and finished runs backfilled from the scheduled pod spec; the mapping, the arithmetic, and the row lifecycle lake prices from.
- [`lake/workspaces.md`](lake/workspaces.md) — **isolated workspace namespaces**: the control-Postgres contract, exclusive workspace-Zetta ownership and service status, volumes grown in place from lake's `storage_gi` (operator#259), namespace naming and lifecycle, allowed network flows (including the datastore operator and Kubernetes API flows, operator#268), PSA, quotas, local credentials, legacy replacement and live verification Job.
- [`lake/admission-fixtures.md`](lake/admission-fixtures.md) — pinned k0s admission policies and tenant RBAC used by the native environment delivery proof.
- [`lake/data-services/README.md`](lake/data-services/README.md) — **Lake data-service labels**: per-operation evidence, the managed threshold, and the customer responsibility for explicitly unmanaged services.
- [`lake/data-services/postgres.md`](lake/data-services/postgres.md) — **Lake Postgres rehearsals**: automated backup recovery, scratch upgrade, replicated failover, verification, cleanup, and status recording.
- [`lake/sealed-secrets.md`](lake/sealed-secrets.md) — **one-way secret delivery**: the cluster sealing key, canonical CBOR envelope, AAD binding, rotation, source types, and verification.
- [`connecting.md`](connecting.md) — **connect to a deployed `OramaZettaCluster`** across every surface: REST/SQL (`/v1/*`), MCP (`POST /mcp`, for Claude/agents), the self-describing `mcp.md` / `llms.txt` pages, and the web portal (`/`); addressing (port-forward / Ingress `spec.host`), and MCP/admin-token auth.
- [`operations/crd-rollout.md`](operations/crd-rollout.md) — **CRDs and rollout**: the three

- [`karpenter-cloud-iam-prerequisite.md`](karpenter-cloud-iam-prerequisite.md) — **operator-owned Karpenter install** ([#75](https://github.com/oramasearch/orama-operator/issues/75)): the cloud IAM identity the operator can't mint (controller IRSA role / node instance profile / Azure role assignment), how it's cloud-gated (EKS self-install, no-op on AKS-NAP / bare-metal), the input validation that keeps the cluster name and role ARN from injecting manifests ([#79](https://github.com/oramasearch/orama-operator/issues/79)), and the `.status` conditions.
