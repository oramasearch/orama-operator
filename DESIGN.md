# orama-operator — design

A Kubernetes **operator** (kubebuilder / Go) plus a thin **install Helm chart** that
stands up an **entire, self-contained Orama Cloud v1 stack in-cluster** — the whole
product surface, not just the engine — driven by a single `OramaCloudV1` custom
resource.

Prod v1 is documented in
[`techops-docs/docs/orama-cloud-v1/`](https://github.com/oramasearch/techops-docs/tree/main/docs/orama-cloud-v1);
this repo is the **k8s-native re-packaging** of that system.

## Deliverable shape

- **Operator** (`orama-operator`) — reconciles one umbrella CRD,
  `OramaCloudV1`, into every child workload (Deployments / StatefulSets / Knative
  Services / Secrets / subchart releases).
- **Install chart** (`chart/`) — self-contained; its *only* job is to install the
  **operator + CRDs + RBAC**. It does **not** deploy the app; the operator does.
- **`helmfile.yaml`** (repo root) — the **composition layer**: installs the upstream
  **platform operators** (CloudNativePG, RabbitMQ operator, …) +
  this operator chart, each toggleable (`installed:`) so a cluster that already has
  them skips them. This is the "reuse OSS charts / helmfile" decision.

```
helmfile apply  ─▶  platform operators (CNPG, RabbitMQ, …) + the v1 operator chart
                       │
helm install ./chart ─▶  operator + CRDs + RBAC   (if you skip helmfile)
                       │
kubectl apply OramaCloudV1 (one per cluster)  ─▶  operator reconciles the whole stack
```

## Decisions (from the 2026-07-07 design grill)

| # | Decision | Choice |
|---|---|---|
| 1 | **Scope** | The **entire** v1 surface, everything in-cluster (engine, dashboard, control-plane DB, analytics, cache, broker, ingestion, the cloud functions, workers). |
| 2 | **Deliverable** | A **kubebuilder operator** (Go) + a thin **install Helm chart** that launches it. |
| 3 | **CRD granularity** | **One umbrella CRD** `OramaCloudV1` (finer per-component CRDs may come later). |
| 4 | **Region model** | **Configurable** per cluster via `spec.region.role: primary \| read`. Multiple releases across `us-east / eu / ap` that talk to each other. |
| 5 | **Cloud functions** | **Plain Deployments** (no Knative for now). The ported Cloudflare Workers are **bundled into ONE image** run as a single Deployment; `index-builder` (was GCP Cloud Run) is its own Deployment. |
| 6 | **Edge / geo-LB** | **Cloudflare is permanent** — **DNS + Load Balancing (geo-steering)** always live there, and the **operator reconciles them via the Cloudflare API** (`spec.cloudflare`, default on). Each CF resource is an **owned child CRD** (child controller = the CF API call + a finalizer; the main loop never mutates CF directly): `CloudflareDNSRecord`/`CloudflareKVNamespace`/`CloudflareR2Bucket`, and — for the geo-LB itself — **`CloudflareLoadBalancer`** ([operator#73](https://github.com/oramasearch/orama-operator/issues/73)): one CR → a health **Monitor** + origin **Pool(s)** + the zone **Load Balancer**, with geo/proximity steering + failover. Auto-populating pool origins from the live wan-accessible node set is [operator#74](https://github.com/oramasearch/orama-operator/issues/74). Worker *logic* runs in-cluster. |
| 7 | **Managed SaaS** | Brought **in-cluster** via upstream operators/charts: Postgres (CloudNativePG), ClickHouse (Altinity operator), Redis, RabbitMQ (plain StatefulSet + our own `RabbitMQTopology` CRD — the cluster-operator was dropped, see #22), Typesense, Mongo (HARVEST). Each is toggleable to `external` (point at real SaaS). |
| 8 | **Auth / IdP** | **Configurable**: `spec.idp: none \| keycloak \| firebase \| clerk`. |
| 9 | **Secrets** | **In-cluster Kubernetes Secrets** — the operator generates per-component secrets (dummy values, create-if-absent); edit them for real values. **No External Secrets Operator.** No plaintext in the CR. A config **file** that must embed a secret (OramaCore's `master_api_key`) keeps a `__PLACEHOLDER__` in the ConfigMap and is rendered by a **`render-config` init container** from the Secret it references into an `emptyDir` at pod start — so the credential lives only in the Secret, never the ConfigMap. The broker and Redis passwords are generated stack-wide Secrets and the master key a referenced one (decision 60). |
| 10 | **Images** | **Reuse** published `oramasearch/*` images where they exist (`oramacore`). Components with **no** published image (`embeddings-server-py`, `dashboard`, `docs`, `orama-workers`, `harvest`, `disco`, `index-builder`) are built by the bridge's [`build/images`](https://github.com/oramasearch/orama-cloud-v1-bridge/tree/main/build/images) tooling — local `docker build` from submodule source (**can't trigger prod CI**), pushed to **private** Docker Hub repos under `oramasearch` (the embeddings image as `cpu-latest`/`gpu-latest`). The operator pulls them via `spec.images.tag` + `spec.images.pullSecretName`. Still no build-from-source *in the operator repo*. |
| 11 | **Cross-cluster net** | **No service mesh** for now — read tiers reach the primary via configured endpoints (`spec.peers`) over public ingress + mTLS. |
| 12 | **"Working" bar** | Operator optionally **seeds a demo project+index** (`spec.demoSeed`) so a fresh install answers queries out of the box. |
| 13 | **GPU / LLM** | The **writer** requests `nvidia.com/gpu` only for its **built-in embeddings** (ONNX+CUDA; set `writer.gpu: false` for CPU on a non-GPU node). The *other* GPU consumer is an optional in-cluster **vLLM** (`spec.llm.gpu`). LLM is a **list** — `spec.llm.providers[]` (multiple; users pick per query) + `spec.llm.default` + the optional `spec.llm.automaticEmbeddingsSelector`, rendered into the engine's `ai_server` (decision 58); in-cluster `vllm` is not implemented and is refused. |
| 14 | **Profiles / replication** | `spec.profile: light \| medium \| heavy` presets replication + sizing (light=dev/no-repl, medium=single-tenant prod, heavy=multi-tenant). Per-store override: `placement: local \| central` (e.g. RabbitMQ **central** = one cluster hosts it) + `replicate` (e.g. Postgres read-replica on read tiers). |
| 15 | **e2e suite** | The `OramaCloudV1E2ETest` runs a **comprehensive functional suite** (`internal/controller/assets/e2e-functional.sh`) embedded via `go:embed` and shipped in a ConfigMap; the Job's runner (default `alpine:3.20`, `spec.image`) installs curl+jq and runs it. Chosen over the prior single-purpose `oramacore-test-e2e` image so coverage lives **in-repo**, is editable without an image rebuild, and can assert **every** critical function (~70 assertions in variations) against the live engine. The suite self-bootstraps a clean-slate collection each run for determinism; commit-dependent or unwired functions (batch-get, analytics) SKIP-and-track rather than fail. Coverage backlog: [operator#44](https://github.com/oramasearch/orama-operator/issues/44). |
| 16 | **Zetta CRD** | `OramaZettaCluster` (separate top-level CRD) deploys a **headless Orama Zetta cluster** — a StatefulSet of equal-peer CRDT nodes + a headless Service (peer DNS 7777) + a client Service (HTTP API 4800), each node a per-node PVC at `--data-dir`. **Step 1 of One Orama** ([orama-bridge#130](https://github.com/oramasearch/orama-bridge/issues/130)): the operator only *runs* Zetta headless — no operator↔Zetta symbiosis, no Zetta MCP changes. every node shares one operator-minted cluster join token (row 22) and peers join `node-0` via a pod-ordinal wrapper. The image is built from the Zetta source in `zetta-bridge/build/images/zetta-headless` (C++26, clang-19, cmake ≥3.30 for `cxx_std_26`). |
| 17 | **Zetta e2e CRD** | `ZettaClusterE2ETest` (separate top-level CRD) runs the **live-cluster zetta e2e suite** as a Job against a deployed `OramaZettaCluster` and reflects pass/fail in status — mirroring `OramaCloudV1E2ETest`, but with the **opposite script-location choice**. The v1 suite is **embedded in the operator** (`go:embed` of `assets/e2e-functional.sh`) because it targets OramaCore, a stable dependency the operator already models. The Zetta suite instead **lives in the zetta repo** (`tests/e2e/zetta-e2e.sh`) and is **baked into the `oramasearch/zetta-e2e` image** (its `ENTRYPOINT` runs it) — the CRD only *triggers* it and passes the cluster addressing as `ZETTA_E2E_*` env (base URL pinned to node-0, peer URLs for ordinals 1..N-1, levels, optional MCP token). **Why:** the Zetta engine is under rapid, coupled development (SQL/MCP/serving/CRDT surfaces all moving) — the test must **evolve with the engine repo** and its L2 `zetta::testkit` catalog, so co-locating it with the engine (script → zetta-bridge image → operator CRD) keeps coverage honest without an operator recompile for every engine change. Runs L2 (in-app testkit) + L3 (black-box integration); the forcing-function rule holds (never soften an assertion). |
| 18 | **Elastic capacity (Zetta pool)** | **First slice of [operator#69](https://github.com/oramasearch/orama-operator/issues/69).** Opt-in `spec.capacity.karpenter` on `OramaZettaCluster`. The operator **owns a Karpenter `NodePool`** (modelled as **`unstructured`** — no dependency on Karpenter's Go types, matching the CNPG `Cluster` pattern) and **references** a platform-owned provider `NodeClass` (`EC2NodeClass`/`AKSNodeClass` via `nodeClassRef` — the NodeClass carries cloud specifics the operator can't invent). Scale is **scheduling-driven**: the Zetta pods are pinned to the pool (dedicated taint/toleration + pool nodeSelector), so raising `spec.replicas` past node capacity ⇒ Pending pods ⇒ Karpenter provisions ⇒ pods join. The NodePool is **cluster-scoped** so it can't be owner-GC'd by a namespaced CR — cleaned up via a **finalizer** + label identity instead. Stateful-safe disruption (`WhenEmpty`, `nodes:"1"` budget, `expireAfter: Never`, pod `do-not-disrupt` + a PDB). **Karpenter-absent (bare metal/k0s) = graceful no-op** (RESTMapper check ⇒ `CapacityReady=KarpenterNotInstalled`). The **Zetta-signal-driven** trigger (`orama_control.scale_requests`) + drain-safe scale-down are **later** slices. |
| 19 | **Operator owns the Karpenter install (cloud-gated)** | **Second slice of [operator#69](https://github.com/oramasearch/orama-operator/issues/69) ([operator#75](https://github.com/oramasearch/orama-operator/issues/75)), extending #18.** #18 reconciles a `NodePool` *assuming Karpenter is installed*; opt-in `spec.capacity.karpenter.install` makes the operator **own the install** too — it **server-side-applies the pinned upstream Karpenter manifests** (controller Deployment + ServiceAccount + RBAC + the CRDs) as **`unstructured`** objects (vendored via `go:embed` under `assets/karpenter/<version>/`, regenerated by `hack/fetch-karpenter-manifests.sh`; **still no Karpenter Go types**). **Cloud-gated** via the node `providerID`: no-op on **bare-metal/k0s** (`BareMetalNoCloud`) and on **AKS** (`ManagedByAKSNAP` — Node Auto Provisioning already manages Karpenter); the self-install path targets **EKS**. **Boundary (documented, not owned):** Karpenter's **cloud IAM identity** (the controller's IRSA role / the nodes' instance profile / an Azure role assignment) is a **cloud-account prerequisite the in-cluster operator cannot mint** — same class as the image pull secret. The reconciler **surfaces `KarpenterInstalled=CloudIdentityMissing` and refuses to deploy the controller (no crash-loop)** rather than fail. Cluster-singleton, ref-counted across CRs via a finalizer; **CRDs are applied but never deleted** (deleting one cascades to every NodePool/NodeClaim cluster-wide). Not live-tested — needs an EKS/AKS-NAP cluster. **Injection-safe rendering ([operator#79](https://github.com/oramasearch/orama-operator/issues/79)):** the two CR values are validated (CRD pattern + reconciler re-check, `InvalidInstallSpec`) and set on the *parsed* objects at one field each, never pasted into YAML text; the rendered bundle must be exactly the expected object set; and the operator's RBAC writes, `bind` and `escalate` are scoped by `resourceNames` to the bundle's roles, bindings and CRDs. Full detail: [`docs/karpenter-cloud-iam-prerequisite.md`](docs/karpenter-cloud-iam-prerequisite.md). |
| 20 | **Zetta node reachability** | A Zetta slice **declares** how siblings reach it (`spec.reachability: wan-accessible \| dial-out-only`, default `dial-out-only`; `spec.ephemeral` for churn-y burst capacity), per the corrected mesh model ([zetta#739](https://github.com/oramasearch/zetta/issues/739), [operator#74](https://github.com/oramasearch/orama-operator/issues/74)). A **wan-accessible** slice is a rendezvous — the operator advertises its routable address as `.status.wanAddress` (from `spec.wanAddress` / `hostNetwork` host IP / peer-LB IP); **dial-out-only** slices only `--peer` OUT (`spec.externalPeers`) and **never** get an inbound LoadBalancer (`spec.exposePeerLoadBalancer` is honored ONLY on wan-accessible, else ignored + warned). This **supersedes** the earlier inbound-LB-to-reach-a-private-node approach ([operator#70](https://github.com/oramasearch/orama-operator/issues/70)/[#71](https://github.com/oramasearch/orama-operator/issues/71) predate the correction). The wan-accessible set feeds both siblings' `externalPeers` and the Cloudflare LB origin pool ([operator#73](https://github.com/oramasearch/orama-operator/issues/73)). |
| 21 | **Auth is mandatory — always seed + inject + authenticate** | **Superseded by [zetta#799](https://github.com/oramasearch/zetta/issues/799):** the engine made auth **mandatory** and **removed** the `--require-auth`/`--mcp-token`/`--cluster-plaintext` flags (passing any is now an unknown-option crash), so what was an opt-in `spec.requireAuth` profile is now the **unconditional** default. The operator (a) renders NEITHER removed flag in the node entrypoint (and, since [operator#279](https://github.com/oramasearch/orama-operator/issues/279), no `--admin-token` either — the engine reads the token from env); (b) **ALWAYS** mints a 64-hex admin token (Secret `<name>-zetta-admin`, mint-once) and injects it as `ZETTA_ADMIN_TOKEN` → `--admin-token` on every node — a fresh node otherwise auto-generates an owner credential the operator can't read; (c) **authenticates its OWN Zetta SQL client** — the coarse state-sync client (`zetta_statesync.go`, `Authorization: Bearer <admin>`) and the schema-provisioning curl Job (`zetta_controlplane.go`, admin token via env → `-H "Authorization: Bearer …"`), which would otherwise 401 against the auth-on engine; and (d) the `ZettaClusterE2ETest` **always** runs the authz-enforcement level (`ZETTA_E2E_REQUIRE_AUTH=1` + the admin token as `ZETTA_E2E_TOKEN`). If the admin Secret lags on a reconcile the SQL sync **retries** rather than falling back to an unauthenticated call. `spec.requireAuth`/`spec.mcpTokenAuth` are kept as **deprecated no-ops** (API compat). The target's image MUST be an **auth-capable build** (post-#799). Multi-node authz needs no new field — the e2e derives `ZETTA_E2E_PEER_URLS` from `spec.replicas`. Status also carries **best-effort `pass`/`fail`/`skip` counts** parsed from the Job's pod logs (needs a clientset for `pods/log`). Pairs with a coordinated engine image rebuild; the zetta repo's `tests/e2e/zetta-e2e.sh` must also always authenticate. Refs: [operator#88](https://github.com/oramasearch/orama-operator/issues/88). |
| 22 | **Shared cluster join token; mTLS-only (no plaintext)** | The join token **is** the Zetta cluster's identity: the engine derives the cluster CA deterministically from it (`SHA256(token ‖ "zetta-cluster-ca-v1")`), so only nodes holding the **same** token trust each other. With no shared token every node minted its **own** on first boot → a different CA → each node formed a **cluster-of-one** ([operator#92](https://github.com/oramasearch/orama-operator/issues/92)). The operator now mints **one** token per cluster (32 random bytes → 64 hex, Secret `<name>-zetta-cluster`, **minted once, never rotated** — rotating re-derives the CA and orphans every node cert) and injects it into **every** node (node-0 included) as `ZETTA_CLUSTER_TOKEN`, provisioned **before** the StatefulSet so its `secretKeyRef` resolves. Mirrors the `-zetta-admin` token reconciler, and like it is **UNCONDITIONAL** (the shared CA is fundamental — no "off" state). Injected **env-only, not as a `--join-token` flag** — the engine reads the env directly (`src/main.cpp` provisioning), and an unknown env var is safely ignored by an image that predates the feature, whereas an unknown flag crashes the node. **This retired `spec.clusterPlaintext`:** once real mTLS clustering worked, an unencrypted-peer mode was a security hole, so it was **removed entirely** (peer traffic is always mTLS) rather than left as a footgun. NOTE: a *multi-node* cluster only fully converges once the engine's DNS-dial + mTLS-sync fixes land ([zetta#785](https://github.com/oramasearch/zetta/issues/785)/[#786](https://github.com/oramasearch/zetta/issues/786)) — the token seeding is necessary but not sufficient alone. Detail: [`docs/zetta-cluster-mtls.md`](docs/zetta-cluster-mtls.md). |
| 23 | **Datastore state as declarative CRDs** | **[operator#40](https://github.com/oramasearch/orama-operator/issues/40).** Each datastore's schema/topology is modelled as its **own owned, reconciled CRD** (deterministic, idempotent, auditable, GC'd) instead of imperative one-shot Jobs or app-boot side effects. First landed: **`RabbitMQTopology`** — the broker's vhosts/users/permissions/streams reconciled via the **management HTTP API** ([#41](https://github.com/oramasearch/orama-operator/issues/41)), same owned-child pattern as the Cloudflare CRDs. **Own CRD over vendor operator (principle #3):** the bitnami RabbitMQ Cluster/Topology operators were evaluated and **dropped** (images 404'd, `ErrImagePull`) — a purpose-built CRD we control beats an unstable dependency. The `OramaCloudV1`-owned instance declares the `oramacore-operations` replication stream + **least-privilege** per-service users (`oramacore-writer`/`oramacore-reader`, principle #4). The stream is declared **bare** (no retention) because RabbitMQ's stream-protocol `Create` — which OramaCore issues on connect — is idempotent only when properties match, and stream retention is declaration-time-only; the engine still uses the shared admin user for now (per-service adoption is a fast-follow). Full design: [`docs/datastore-crds.md`](docs/datastore-crds.md). Sibling CRDs (`PostgresSchema`, `ClickHouseSchema`, `Typesense`/`Mongo`) + image-pinning + DR ([#33](https://github.com/oramasearch/orama-operator/issues/33)) are the remaining epic slices. |
| 24 | **Cross-cluster Zetta topology THROUGH Zetta** | **[operator#105](https://github.com/oramasearch/orama-operator/issues/105), building on #20.** Cross-cluster peering is no longer hand-wired (an admin copying each slice's `.status.wanAddress` into siblings' `spec.externalPeers`). Each operator **WRITES** its slice's wan-accessible node endpoints (+ the global cluster name, its operator id, reachability, node_type) into a new **`orama_control.topology`** table, Zetta **CRDT-syncs** that table across every cluster for free, and each operator **READS** it back (latest-wins per node by `updated_at`, scoped to rows sharing this slice's `spec.clusterName`) to **DERIVE** its `--peer` set from the OTHER slices' wan endpoints — so peering **self-forms**. `spec.externalPeers`, when set, still **wins** (explicit override); the derived set fills the gap (union, deduped, excluding this operator's own nodes + own advertised addresses). **Same anti-flap discipline as `components`** (append only on change) and same best-effort/retry posture (the node HTTP server is flaky, [zetta#731](https://github.com/oramasearch/zetta/issues/731)) — a topology read/write error never fails the reconcile. **Append-only model** (no UPDATE/DELETE, [zetta#735](https://github.com/oramasearch/zetta/issues/735); no IF NOT EXISTS): a departed wan node (scale-down / flip to dial-out) is expressed with a **`status='gone'` marker row**, and latest-wins drops it from the derived set next reconcile (failover). **GC is BLOCKED and out of scope:** removing a departed `node:<id>` from the engine's **membership CRDT** cannot be done over SQL and there is no node-removal API yet — the `gone` marker only affects the operator's derived `--peer` set, **not** Zetta's own node-list. Code: `zetta_topology.go` (+ `zettaSQLQuery` in `zetta_statesync.go`); detail: [`docs/zetta-datastore.md`](docs/zetta-datastore.md). |
| 25 | **Deployment intake through the operator's Zetta control plane** | **[operator#124](https://github.com/oramasearch/orama-operator/issues/124), implementing liquid-bridge decision 22.** Liquid writes an append-only `desired` event to `orama_control.deployments`; the operator materializes it into a Lake-owned `LakeEnvironment` CR, and Kubernetes is authoritative after that boundary. One CR reconciles a k0s decision-31 namespace profile and an `untrusted` runtime workload. The operator appends `status` events only when phase, URL or message changes, so anti-flap survives restarts. Withdrawal or preview change closure writes one `TornDown` event and deletes the verified owned Namespace. Rollback is another desired event naming an older immutable image. Detail: [`docs/lake/environments.md`](docs/lake/environments.md). |

| 30 | **Lake managed services through lake's control Postgres** | **Implementing liquid-bridge decision 46; supersedes #29; workspace ownership corrected by #219.** A customer runs any number of services — Zetta and Postgres clusters — on the Lake's cluster. lake writes the `services` table in its own control Postgres and never touches Kubernetes; the operator reads it with pgx through the CloudNativePG application Secret (`lake-<lake>-controldb-app`, key `uri`), creates one Lake-controlled `OramaZettaCluster` or CloudNativePG `Cluster` `<lake>-<slug>` per present service, and upserts `service_status` only on change. | 31 | **The managed-services catalog runs through upstream operators** | **Implementing [liquid-bridge decision 47](https://github.com/oramasearch/liquid-bridge/blob/main/docs/decisions.md), per lake `docs/control-plane/services.md` at `0a701ef`; extends #30.** Kafka (Strimzi 1.2.0), ClickHouse (Altinity 0.27.4), TiDB (TiDB Operator v1.6.6, stable 1.x), Cassandra (K8ssandra 1.33.0) and Valkey (valkey-operator 0.6.0, preview) are each run by their own upstream operator; the Orama operator writes that operator's resources and never runs the database. It writes them as **unstructured objects with GVK constants and never imports the upstream Go modules**, so the operator carries no dependency on five other projects' release trains; the price is that field names are checked against each pinned CRD by hand (and in tests), not by the compiler. One `catalogKind` interface per kind (`lake_service_<kind>.go`) supplies the objects, readiness, credential and PVC selector; ownership, adoption refusal, the quota, `Ready` gated on the credential and status-only-on-change are #30's, shared. A kind whose CRD is not installed fails only its own services (`the <kind> operator is not installed on this cluster`): the objects are read uncached, so nothing is watched and the manager never needs those CRDs. ## Region topology (mirror-prod default)

```
   Cloudflare geo-LB  (DNS steering to nearest cluster ingress)
        │                        │                         │
   ┌────▼─────────┐        ┌─────▼──────┐            ┌──────▼─────┐
   │ us-east      │        │ eu         │            │ ap         │
   │ role=primary │        │ role=read  │            │ role=read  │
   ├──────────────┤        ├────────────┤            ├────────────┤
   │ writer(GPU)  │        │ readers    │            │ readers    │
   │ pg PRIMARY   │──repl─▶│ pg replica │            │ pg replica │
   │ clickhouse   │        │ envoy      │            │ envoy      │
   │ rabbitmq     │        │ workers RO │            │ workers RO │
   │ index-builder│        └────────────┘            └────────────┘
   │ HARVEST      │           ▲                         ▲
   │ dashboard    │           └──── spec.peers ─────────┘
   │ workers RW   │        (read tiers point at primary writer/pg)
   └──────────────┘
```

`role=primary` runs the write path + stateful stores; `role=read` runs the
regional read path and points at the primary via `spec.peers`. A single-cluster dev
install uses `role=primary` with everything enabled.
